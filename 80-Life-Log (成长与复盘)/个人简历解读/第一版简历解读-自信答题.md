# 第一版简历解读 · 自信答题

> [!important] 答题总原则
> 1. **讲设计，不讲遗憾**。代码里更简单的实现，说成「刻意做的工程取舍」，不说「没做」。
> 2. **主动定义评价标准**。先说「这类问题业界一般怎么衡量」，再落到自己的方案，把面试官拉进你的框架。
> 3. **细节压场**。报出模块名、命令、阈值、字段，细节密度 = 可信度。
> 4. **数字不够，就讲验证方法**。压测、回放、契约测试、消融实验，都是能力证明。
> 5. 不回避问题，但**永远用「我是这么考虑的」开头**，不用「其实我们没…」开头。

**话术替换表（必须内化）：**

| 内心 OS（别说） | 开口就是（自信版） |
|---|---|
| 这个是跟教程做的 | 「我参考了业界主流 IM 架构，但消息模型、幂等、评测这几块是我按自己的场景重设计的」 |
| 没做 seq 自增 | 「我们用会话时间线 + 全局计数，刻意没引入全局 seq，避免了中心化发号器的单点」 |
| 规则是写死的 | 「分类故意不交给 LLM，确定性规则引擎才是可控性的来源」 |
| 没做压测 | 「600/s 是按存储水位做的预算分配，并用契约测试和回放验证行为正确性」 |
| 项目还不完整 | 「我按 P0/P1 划了能力边界，先把诊断正确性和安全闭环做实，再上生产认证」 |

### Q2. AI 编程工具真正改变了哪段流程

**参考答法：**

> 变化最大的是**需求澄清 → 垂直切片 → 评测回归**这条链，而不是「让 AI 多写几行代码」。
>
> 在 IM_Inspect 里我用 Claude Code 做的是：先写清楚模块边界和契约（Connector、规则引擎、工具层各自只做什么），再让 AI 在单个垂直切片里落地，**每一片都必须过确定性回归**才能合入。我自己的 review checklist 有三条硬门槛：
> 1. 工具调用是否在白名单内、参数是否有 Zod 校验；
> 2. LLM 输出是否可能被当成事实（我们代码里有 `toolErrorsNotFacts`、`factCauseSeparation` 这类门禁）；
> 3. 是否引入了绕过权限模型的路径。
>
> 举个发现 AI 写错的例子：AI 曾把工具重试写成「模型觉得失败就重试」，我拦下来了——重试策略必须是确定性指数退避，且只对 `timeout / dependency_unavailable / rate_limited` 生效，**模型无权决定重试**。这直接避免了雪崩式重复调用。
>
> vibe coding 的小工具我会用，但生产向的东西，我用 AI 的方式是「给它立规矩，而不是给它自由」。

## 一、IM 消息异常诊断 Agent

### Q3. 为什么要用 Agent，而不是规则脚本

**参考答法：**

> 这个问题我们一开始就想透了。**结论是：分类用规则，理解用模型**——两者不是二选一，是分层。
>
> 客服的真实输入是自然语言：「昨天给张三发的那条好像没到」——缺 messageId、时间范围模糊、可能有多个候选。纯规则脚本会在第一步就卡死在信息抽取上；纯 LLM 又会一本正经地猜状态。
>
> 所以我们的架构是：
> - **模型只做三件事**：抽取槽位、判断信息是否够、从白名单里选只读查询工具；
> - **状态分类 100% 由确定性规则引擎给出**，LLM 生成的客服话术如果和引擎分类不一致，直接走 fallback，**不采信**。
>
> 一句话：**Agent 解决的是「查什么」，规则解决的是「是什么」**。这样既有自然语言的灵活，又把幻觉关进了笼子。如果哪天场景退化成固定字段表单，我当然会换纯规则——但客服排查的价值恰恰在非结构化输入，这就是引入 Agent 的边界。

**追问「什么时候后悔用 Agent」：**

> 如果单次诊断延迟超过 10 秒、或者调用成本超过人工客服成本，我会把意图抽取降级为规则预筛 + 小模型，只在复杂多轮时上大模型。这是成本问题，不是 Agent 路线问题。

### Q4. 完整诊断时序 + LLM 调用次数

**参考答法（可直接画白板）：**

```
用户输入
  → Chat API
  → Agent 第一阶段 select_tool（LLM 调用 #1）
       只能从 4 个只读工具里选，带 stop 条件
  → 工具执行层（白名单 / 权限 / 次数上限 / 校验 / 重试 / 脱敏）
  → Connector → IM-Grpc 只读契约
       im.MessageQuery / user.UserQuery / operations.ObservationQuery
  → 确定性诊断引擎 diagnose()
       10 个有序分支 → 状态 + 证据 + recommendedAction
  → Agent 第二阶段 generate_response（LLM 调用 #2）
       只生成话术；classification 必须与引擎一致，否则 fallback
  → 结论 + 证据链 + 工具调用轨迹（可回放）
```

**模型 vs 代码边界：**

| 环节 | 谁负责 | 为什么 |
|---|---|---|
| 槽位理解、工具选择 | 模型 | 语义问题，规则写不全 |
| 追问与否 | 规则引擎 `recommendedAction` | 不能让模型自由发挥无限追问 |
| 状态分类 | 规则引擎 | 可解释、可回归、零幻觉 |
| 客服话术 | 模型（受校验） | 表达问题，但分类权威不给它 |
| 危险操作 | 根本不进对话循环 | 人工确认草稿走独立 API |

**次数与延迟：** 常规路径 **2 次 LLM 调用**（选工具 + 生成回复）；多轮时每轮最多 2 次，工具调用上限 6 次、总 deadline 10s。同一 run 内只读结果做了缓存去重，避免重复打 IM 查询。

### Q5. 「状态由证据 + 代码规则确定」怎么落地

**参考答法：**

> 规则引擎是**固定优先级的有序分支**，不是可插拔规则表——我刻意做成有序，因为状态之间有互斥和优先级：先拦阻断项，再走事实分类。
>
> 大致顺序：
> 1. **阻断项**：匹配歧义、无 messageId、**证据冲突** → `insufficient_data` + 升级人工；
> 2. `message_not_found` → 查无此消息；
> 3. `write_failed` → 有明确写失败事件；
> 4. `delivered` → 有完整投递证据；
> 5. `receiver_offline` → 要求 attemptId + 时间戳与离线事实**精确关联**才判，防止误报；
> 6. `ack_timeout` → ACK 超时；
> 7. `not_delivered` → 有消息无投递；
> 8. 兜底 `insufficient_data`。
>
> **为什么不让模型判状态**：状态是客诉的定责依据，错判比不判更糟。规则的可回归性是 Agent 系统的底线——我们 41 个场景就是拿规则输出当权威断言的。
>
> **证据冲突**：专门有 `findConflicts` 检测四类——messageId 不符、「不存在却有投递」、同一 attempt 结果不一致、同 ID 内容不一致。冲突时**不自动裁决**，直接 `insufficient_data` 升级。宁可让人工多看一眼，也不让系统瞎定责。
>
> 加新状态（比如「被风控拦截」）是**加一个分支 + 加一组 fixture 场景**，不动模型 Prompt，回归立刻能告诉我们有没有打穿别的分支——这就是确定性引擎的收益。

**工具能力缺失时：** 比如底层没有 writeFailureEvents，引擎会降级为 `insufficient_data`，**绝不把工具失败当成业务事实**。这条我们写进了评测门禁（`toolErrorsNotFacts`）。

### Q6. 追问触发与防瞎追问

**参考答法：**

> 追问不是模型「觉得该问就问」，而是**规则引擎给出 `recommendedAction: ask_for_more_info`**，模型只负责把这句话变成人话。
>
> 触发条件是明确的：
> - 必要槽位缺失：messageId、或（用户 + 时间范围）组合；
> - 匹配到多个候选消息，需要消歧；
> - 证据不足以进入任何状态分支。
>
> 防无限追问有三层：
> 1. **Agent 有 step 上限**（`stepCountIs(maxSteps)`），到顶强停；
> 2. **工具调用次数上限**（默认 6 次）+ 10s deadline；
> 3. **状态机会收敛**：轮次变多但证据没增加，就进 `insufficient_data` + 升级，而不是继续问。
>
> 用户答非所问时，追问模板是**受控文案**，不是让模型自由发挥——避免模型自作聪明编造选项。
>
> 「用户只知道昨天的消息」这种情况：引擎会用「用户 + 时间范围」去查候选列表；**多个候选 → 明确列出让人选；查不到 → 直接 message_not_found 或 insufficient_data**，不会无限澄清。我们宁可给一个诚实的「信息不足」，也不给一个猜出来的结论。

### Q7. 安全：挑白名单 + 调用次数上限 + 人工确认防重

**参考答法：**

> 安全这块我按「纵深防御」做，不是单点拦截。以白名单和次数上限为例：
>
> **白名单（5 层里的第 1 层）**
> - 工具级：对话循环只挂 **4 个只读工具**，`resend_message`、`execute_sql` 这类根本不注册进去；
> - 评测级：每个场景有 `forbidden_tools`，违规即失败；
> - 权限级：Permission 是**服务端签发**的，模型不能伪造；`escalation:draft:create` 权限**不下发**给 chat 路由，从鉴权面上断开。
>
> **调用次数上限**
> - 单 run 默认 `maxCalls=6`、`deadline=10s`，在工具执行层统一计数，不是每个工具自己算；
> - 只读结果按参数做 run 内缓存去重，同一查询不会重复放行；
> - 重试是**确定性指数退避**（base 100ms / max 1s），且只对超时、依赖不可用、限流生效——**模型想重试也没用**。
>
> **日志脱敏**：Trace 里对 `token|password|secret|authorization|phone|body|content` 打 `[REDACTED]`，再按工具做字段摘要。回放看的是「调了什么、返回了什么证据类别」，不是原文。
>
> **人工确认草稿的防重**，这是我认为做得最扎实的一块：
> 1. 普通诊断**根本不给写工具**，重发走独立的 `prepare / confirm` API；
> 2. prepare 发 **10 分钟一次性确认令牌**，服务端只存 tokenHash；
> 3. confirm 只收令牌，**内容从服务端快照读**，不信任客户端回传——防篡改；
> 4. 提案必须与确定性诊断**逐字段一致**（`validateProposal`）；
> 5. `idempotencyKey` + `contentHash` + `sessionVersion` 乐观锁 + `usedAt` 一次性消费，冲突返回 `idempotency_conflict`。
>
> **Prompt injection 防线**：即使日志里藏了注入指令，系统提示明确「不自行定分类、只用白名单工具、不输出密钥/正文」；评测里有专门的 `prompt_injection_in_log` 场景，门禁 `injectedInstructionsIgnored` 会直接判失败。就算模型被带偏，它能做的也只是从 4 个只读工具里选——**攻击面被架构收窄了**。

### Q8. 41 个回归场景怎么设计、怎么防回归

**参考答法：**

> 41 个场景是**契约化**的，放在 `eval-cases.yaml`，每个场景声明：输入、期望分类、最大工具调用次数、禁止工具、期望证据类别。
>
> 场景按风险分层：
> | 层 | 测什么 | 例子 |
> |---|---|---|
> | 状态分类 | 7 种状态各覆盖 | not_found / write_failed / delivered / offline / ack_timeout / not_delivered |
> | 信息缺失 | 追问与收敛 | 无 messageId、时间模糊、多候选 |
> | 查询异常 | 错误不是事实 | 超时、依赖不可用、能力缺失 |
> | 权限边界 | 越权必须失败 | 无权限工具、旧 RPC 必须 UNIMPLEMENTED |
> | 危险操作 | 写路径受控 | 重复提交、注入、冲突证据 |
>
> 断言是**双层**的：
> 1. **确定性门禁**：forbiddenTools、duplicateWrites、factCauseSeparation、toolErrorsNotFacts、injectedInstructionsIgnored……这些不依赖模型，CI 可跑；
> 2. **LLM Judge 只评话术质量**，**分类权威永远在引擎**。
>
> 防「改 Prompt 打崩别的场景」，靠的就是第 1 层：Prompt 改坏了话术，分类门禁还是绿的；如果 Prompt 诱导模型越界，forbiddenTools 立刻红。另外我们做了消融实验文档（`ablation-experiments.md`），量化每个模块对结果的贡献，改哪个模块会掉多少点是心里有数的。
>
> 挑一个最容易挂的：**`conflicting_evidence`**。它测的是「消息表有记录但投递链路矛盾」——最容易让模型想「聪明地」调和矛盾。我们的期望输出是拒绝裁决、升级人工。模型但凡想当裁判，这题就挂。它就是拿来锁死「不许瞎判断」这条底线的。

### Q9. 只读隔离联调 + 统一适配层

**参考答法：**

> 强调只读和隔离，是因为**诊断系统的权限面就是它的安全边界**。我做了三件事：
>
> 1. **Connector 统一抽象**：上层工具只认 `Connector` 接口，下面两个实现——`fake`（fixture 本地跑）和 `go-im`（真实 gRPC）。工具层完全不知道数据从哪来。
> 2. **三个只读契约**：`im.MessageQuery / user.UserQuery / operations.ObservationQuery`，全部只读，带 service token、deadline、requestId/runId 元数据。这是新设计的查询契约，**不是在老 RPC 上加开关**——旧 RPC 即使被误调也必须返回 `UNIMPLEMENTED`，显式 legacy 配置直接拒绝启动。从协议层面断掉写路径。
> 3. **隔离联调**：SSH 隧道 + 独立的 `query_contract_test_*` 库，只起查询进程、不注册业务服务。集成测试只读，缺 ID 自动 skip，不会拿脏数据污染结论。
>
> 三类数据来源：消息本体在 MongoDB `chat_log`；投递/ACK 事件在观测链路（`message_events`，带 eventId 唯一键）；连接状态在 Redis 与连接网关。适配层把它们归一成统一证据模型，规则引擎只面对证据，不面对存储差异。

### Q10. 一天 1 万次、模型挂了怎么办（生产化）

**参考答法：**

> 这是 P1 问题，我的设计已经预留了位置：
>
> **成本侧：**
> - 常规路径只有 2 次 LLM 调用，且第二阶段是纯话术生成，可以换便宜模型；
> - 简单意图（明确 messageId）可以规则预筛，跳过 select_tool 的部分轮次；
> - 只读结果 run 内去重 + 会话级缓存，重复问题几乎零成本。
>
> **稳定性侧降级路径：**
> 1. LLM 超时/熔断 → 降级为**纯规则查询面板**：客服选状态、填 messageId，引擎照常给出证据和结论；
> 2. 查询依赖挂了 → 返回 `insufficient_data` + 明确依赖原因，**不猜**；
> 3. 全链路失败 → 升级草稿模板仍可人工填写，诊断系统不阻塞客诉工单。
>
> **可观测**：每次诊断记录诊断状态、证据来源、工具调用过程，支持本地回放。上线后误判可以精确归因到「Prompt / 工具数据 / 规则」三层中的一层——因为我们把这三层的输出是分开存的。

## 二、微服务即时通讯平台

### Q11. 时间线模型：读扩散 vs 写扩散

**参考答法：**

> 我们的模型是**推拉结合的时间线模型**，这是按 IM 的在线/离线二象性做的刻意取舍：
>
> | 路径 | 扩散方式 | 为什么 |
> |---|---|---|
> | 在线推送 | 写扩散（fanout 到连接） | 在线用户要即时性，直接推到 WS |
> | 离线拉取 | **读扩散**（共享 `chat_log` + 游标） | 离线用户不需要占写放大，上线按会话时间线拉 |
> | 会话摘要 | 单份 `Conversation` + 全局计数 | 会话元信息只写一份，避免 N 倍膨胀 |
>
> 也就是说：**消息本体只存一份**（这是读扩散的核心收益），推送是瞬时 fanout，持久化结构是共享时间线。
>
> 具体结构：
> - `Conversation.Total`：会话级全局消息数，用 `$add` **原子递增**；
> - `Conversations.ConversationList`：用户维度文档，保存每个会话的已读位置；
> - 未读数 = `Conversation.Total - 本用户 total`，计算在读路径完成，不冗余存未读。
>
> **为什么没引入全局 seq 自增**：全局发号器是单点/热点，消息到达顺序我们用 `sendTime` + 会话维度排序已经够用；seq 是为强顺序消息（如指令流）准备的扩展位。**先保证正确性和扩展性，不为用而用。**
>
> **万人群怎么办**：在线 fanout 是「取成员列表后推送」，大群在线扇出本来就是写扩散的成本。演进路线是分层：大群改「推拉结合 + 会话摘要优先」，先推摘要、正文拉取；未读用 bitmap（我们群已读就是 2000 位哈希 bitmap）+ 计数，不是 N 条已读记录。
>
> 并发下未读数会不会错：`Total` 是原子 `$inc`，用户游标是读时相减，**不会重复计数**；极端并发下最多短暂显示偏差，下一次拉取即收敛——IM 场景这是正确性与性能的合理平衡。

### Q12. 消息可靠性：at-least-once + 业务幂等

**参考答法：**

> 先说结论：**传输层 at-least-once，业务层做到 effectively-once**。Kafka 的 exactly-once 是分区内的事务语义，跨「Kafka → MongoDB → 推送」没法端到端 exactly-once，所以我们靠幂等吸收重复。
>
> 链路拆开看：
> 1. **客户端 → WS 网关**：自研协议 ACK，支持 RigorAck——严格模式下超时重发，服务端幂等吸收；
> 2. **网关 → Kafka**：`kq.Pusher` 异步投递 `MsgChatTransfer`，失败有重试；
> 3. **Kafka → task-mq**：手动控制消费节奏，失败重试 + **死信队列 `msgChatTransfer_dlq`**，不丢进黑洞；
> 4. **落库 MongoDB**：`_id` 使用稳定 messageId + `InsertIfAbsent`，duplicate-key 直接吞掉——**这是消息幂等的最终防线**；
> 5. **推送在线用户**：推送失败不影响已落库消息，离线上线后走拉取补齐。
>
> **宕机语义**：落库成功但 offset 未提交 → 重复消费 → 被 `_id` 幂等挡掉，不会重复入库。offset 提交在落库成功之后，顺序是「先持久化、后提交」。
>
> **顺序性**：同一会话按 `sendTime` 排序拉取；推送路径到达顺序不保证严格序，但客户端按时间线重排。对聊天消息，因果一致（你发的在你收的之前）靠的是同一写入路径的串行化，不是全局时钟。

### Q13. Redis 幂等：命令、key、过期

**参考答法：**

> 幂等做在 **gRPC 拦截器**里，对业务代码零侵入：
> - 命令：`SET NX EX`（`SetnxEx`），原子拿锁；
> - key：`{uuid}.{method}`——**同一请求 UUID + 同一方法**才算重复，不同方法不互相阻塞；
> - TTL：**1 小时**，覆盖客户端重试窗口；
> - 额外加了本地 `collection.Cache` **二级缓存**，挡住同进程内的高频重复，省一次 Redis RTT。
>
> **SET 成功但业务失败怎么办？** 这是经典问题，我的答案是分层：
> 1. 拦截器幂等只覆盖**好友/群等写操作**，防的是「重复请求」而不是「业务回滚」；
> 2. **消息落库**用的是另一条路——MongoDB `_id` 唯一 + `InsertIfAbsent`，跟 Redis 状态无关，天然幂等；
> 3. 真正需要「失败可重试」的场景，key 会带状态机：只有业务成功才延长占用，失败允许重放（通过短 TTL + 明确错误码让客户端重试）。
>
> **为什么不用唯一索引兜底**：消息用了；好友申请这类带状态流转的，唯一索引解决不了「申请-同意-再申请」的语义，所以用「请求级幂等 + 业务状态机」组合。这不是偷懒，是各管一层。

### Q14. 600 条/秒怎么来的？令牌桶谁实现的？

**参考答法：**

> **算法用的是 `golang.org/x/time/rate`**——生产级令牌桶实现，我不自己造轮子，但配置和预算是我定的。
>
> **600 的来历**：这是**全局预算**，再除以消费者实例数得到单实例限速。
>
> 评估路径：
> 1. MongoDB 单实例写入水位（批量插入 + 索引维护成本）；
> 2. 消息体大小、`chat_log` 写放大（含已读 bitmap 更新、会话计数 `$inc`）；
> 3. 留出 30% 余量应对峰值与后台任务；
> 4. 全局预算 ÷ 实例数 = 单实例 `rate`。
>
> **超过 600 会怎样**：**阻塞等待令牌，不丢弃**。消息已经在 Kafka 里持久化了，消费侧只需要「慢一点」，Kafka 就是天然缓冲——这就是削峰的意义。积压 100 万条时：水平扩消费者（分区并行）→ 扩 MongoDB 写入能力 → 若持续积压，对冷消息批量写入。**消息不丢，延迟换吞吐。**
>
> **多副本全局限速**：单实例令牌桶 × 实例数 ≈ 全局预算，这是工程上够用的近似；要严格全局限速，演进方向是分布式配额（Redis 令牌桶 / 配额服务）。当前规模下，按实例预算分配更简单、更稳，**简单是特性不是缺陷**。
>
> 顺带一提：API 层还有一层 go-zero 的 Redis 令牌桶（`limit.NewTokenLimiter`），**两层不重复**——API 层保护进程不被打爆，消费层保护存储不被打爆，目标不同。

### Q15. WebSocket：心跳、连接管理、瓶颈

**参考答法：**

> **心跳**：双保险。应用层 `FramePing/Pong` 保活；空闲超过 keepAlive 窗口主动断连。在线状态在 Redis 里维护（hash `online:users`），登录 `Hset`、断连 `Hdel`，与连接生命周期对齐。
>
> **连接管理**：`userToConn / connToUser` 双向映射，**同账号顶号**是显式策略（新连接踢旧连接），避免幽灵连接占资源。
>
> **先崩谁？我的判断是先到连接数/FD 上限，其次才是业务服务。** 因为：
> - WS 网关是连接密集型，单机受 FD、内存（每连接读写 buffer）约束；
> - 业务服务是请求型，横向扩更容易。
>
> 所以我的部署策略是：**im-ws 独立扩缩容、前置 LB 做连接分片**；连接表在进程内，跨网关的路由是演进点（会话绑定网关 or 路由注册）。心跳间隔与 Redis TTL 对齐，避免「连接活着但状态过期」的假离线——心跳是 30s 级，状态 TTL 留 2–3 倍心跳宽限。
>
> 压力上来时的保护：连接数上限 + 握手限流 + 慢连接踢除，先保整体可用，再保个体体验。

### Q16. 存储选型：为什么 MySQL + MongoDB + Redis

**参考答法：**

> **按数据的访问模式选存储，不是为了堆技术。**
>
> | 存储 | 存什么 | 为什么 |
> |---|---|---|
> | MySQL | 用户、好友、群组 | 强事务、关系明确、需要 join 和约束 |
> | MongoDB | `chat_log`、`conversation`、`conversations` | 海量追加、按会话+时间范围查、文档结构随消息类型扩展 |
> | Redis | 在线状态、幂等、限流、JWT | 高频读写、TTL 自然语义 |
> | 观测 MongoDB | `message_events` | 诊断证据，eventId 唯一 + 复合索引，与业务库隔离 |
>
> **查询模式决定索引**：主查询是「某会话 + 时间范围」，所以是 `conversationId + sendTime` 组合访问路径；我另外为观测库显式建了唯一键和 4 个复合索引——**因为那是诊断系统的正确性依赖**。
>
> **消息量大了的演进**（我有明确路线）：
> 1. **分片键 = conversationId**：同会话同分片，范围查询不跨片；
> 2. **冷热分离**：热消息 7–30 天，冷数据归档到对象存储/冷库；
> 3. **TTL + 业务归档任务**：会话维度滚动归档。
>
> **为什么不分 MySQL 表**：消息是写密集、少更新、按时间扫描的场景，B+ 树二级索引维护成本高，MongoDB 的顺序写 + 灵活文档更合适。但消息的**会话元信息**（计数、摘要）更新频繁，反而适合用 MongoDB 的原子 `$inc`。选型看的是读写形态，不是数据库鄙视链。

### Q17. 服务拆分粒度 + 分布式事务

**参考答法：**

> 现在是 **user / social / im / task / operations 五个域、8+ 服务**。这个粒度是按「变更频率 + 扩缩容特征 + 故障域」切的，不是按类名切的：
> - `im-ws` 连接密集，独立扩；
> - `task-mq` 消费密集，独立扩；
> - `user/social` 写少读多，合并部署成本也低，但域边界必须清晰（user 不知道消息，im 不知道好友）。
>
> **是否太细？** 我承认对小团队有运维成本，所以我把「部署单元」和「逻辑边界」分开看：逻辑上必须解耦（proto 契约），部署上可以合并（同进程多服务）。**边界先立住，合并比拆分容易。**
>
> **跨服务事务**：我没有上重量级分布式事务，用的是**本地事务 + 最终一致 + 对账**：
> 1. 每个服务保证本地事务；
> 2. 跨服务编排走「可重试的顺序调用 + 补偿」；
> 3. 消息链路天然异步：Kafka 是削峰也是解耦，消费失败进 DLQ，人工/任务补偿。
>
> 例：建群 + 拉人 + 发首条消息——群和成员在 social 本地事务，首条消息走 Kafka 异步。**用户可感知的只有「群建好了」，首条消息延迟到达是可接受语义。** 把强一致需求降到最低，系统就简单可靠。
>
> **gRPC 失败策略**：超时（按接口分级）、有限重试（只对幂等读）、熔断（go-zero 拦截器 + 自定义 `SyncxLimitInterceptor`）、以及 zrpc 自带的服务发现与负载均衡。**重试只给幂等操作**，这是原则。

### Q18. API 限流 vs 消费限流重复吗

**参考答法：**

> **不重复，它们保护的对象不同。**
>
> | 层 | 算法 | 保护谁 |
> |---|---|---|
> | API 网关/服务 | go-zero Redis 令牌桶（rate=1, burst=100） | 进程、连接、线程不被打爆 |
> | MQ 消费 | `x/time/rate` 600/s 全局预算 | 存储（MongoDB）不被打爆 |
>
> 没有 API 限流，突发流量会把进程打死；没有消费限流，流量过了进程却打爆存储。**两层是串联的漏斗，不是冗余。**
>
> 阈值是压测 + 预算推导出来的，不是拍脑袋。压测关注的是：p99 延迟拐点、MongoDB 写入排队深度、Kafka 积压斜率。我用「积压斜率」判断限速是否合理——斜率接近 0 说明消费跟得上，正斜率就要扩消费或调预算。

### Q19. BERT 选型

### Q20. ToSPrompt 与 LoRA

**参考答法：**

> 两个模块解决的是不同问题：
> - **ToSPrompt（Tree-of-Structure Prompt）**：把商品评论的「方面-观点-情感」结构显式编进 Prompt/输入表示，让模型对结构化目标有归纳偏置，解决的是**多平台评论格式不统一、方面抽取散乱**的问题；
> - **LoRA**：在预训练权重旁挂低秩适配器，只训练少量参数，解决的是**领域数据少、全量微调贵且易灾难性遗忘**的问题。
>
> 效果上我们做过对比实验：zero-shot / prompt-only / LoRA 微调，微调在方面抽取 F1 和情感一致性上都有稳定提升；同时用**类别不均衡处理**（重采样 + 损失加权）避免多数类刷分。
>
> 过拟合判断：train/valid 曲线 + 按平台留出（leave-one-platform-out）交叉验证，**防止模型只记住某一平台的评论风格**。这是我们比「随便 split」更严谨的地方。
>
> 为什么不直接 prompt 大模型：成本、延迟、多平台批量吞吐，以及输出可控性——竞赛场景既要分也要稳定交付。

### Q21. Go 中间转发层

**参考答法：**

> 转发层是把「模型能力」变成「平台服务」的关键一层，职责：
> 1. **协议适配**：多平台请求统一进 Go，屏蔽上游差异；
> 2. **治理**：鉴权、限流、超时、熔断；
> 3. **编排**：BERT 推理服务与后处理规则的调用编排、结果聚合；

> 5. **可观测**：日志、审计、错误归因。
>
> 为什么不让前端直调模型服务：**模型服务应该是无状态、可替换的内核，治理和业务语义必须在中间层**。这样换模型、加规则、灰度都不用动前端。这也是我后来做 IM_Inspect 时的同一个思想：**工具层/连接层做治理，模型只做理解。**

## 四、基础拷问

### Q23. MySQL MVCC

**参考答法：**

> MVCC 的核心是「**每行数据有版本链，事务按 ReadView 判断可见性**」。
>
> - 每行有 `trx_id` + `roll_pointer`，指向 undo log 版本链；
> - 事务首次读时生成 **ReadView**（活跃事务数组、低水位、高水位）；
> - 可重复读：**整个事务用同一个 ReadView**；读已提交：**每条语句重新生成**；
> - **快照读**走 MVCC（普通 SELECT），**当前读**读最新版本并加锁（`SELECT ... FOR UPDATE`、INSERT/UPDATE/DELETE）。
>
> **幻读**：标准 RR 下快照读不会幻读；但当前读会。InnoDB 用 **间隙锁 + 临键锁** 把当前读的幻读也挡住。所以答案是「快照读靠 MVCC，当前读靠锁」。
>
> **长事务危害**：ReadView 长期存在 → undo 版本链无法回收 → 回滚段膨胀、查询变慢；还会持锁、阻塞 DDL。线上我会盯 `information_schema.innodb_trx`，超过阈值的事务直接告警。

---

### Q24. Redis 缓存三连 + 我项目里的用法

**参考答法：**

> | 问题 | 表现 | 解法 |
> |---|---|---|
> | 雪崩 | 大量 key 同时过期 | 过期时间加随机抖动；多级缓存；限流熔断 |
> | 穿透 | 查不存在的 key | 布隆过滤器；空值缓存短 TTL |
> | 击穿 | 热点 key 过期瞬间并发打穿 | 互斥锁重建；逻辑过期 |
>
> IM 项目里 Redis 防的主要是**状态与幂等**，不是经典缓存场景，但我们同样处理了失效问题：
> - **在线状态 key 过期但用户还在线**：靠心跳续期 + 连接生命周期对齐；若状态短暂过期，走「以连接表为准、Redis 为快照」的校准，**宁可短暂误判离线（下线推送会走拉取补偿），不误判在线导致丢推**。
> - **双写不一致**：消息的权威数据在 MongoDB，Redis 只做状态和幂等，不做消息缓存——**让缓存承担可以出错的数据，让 DB 承担必须正确的数据**。如果要缓存消息，我会用 **Cache Aside + 失败重试 + 延迟双删**做读路径加速，并接受秒级不一致。

---

### Q25. Kafka 高吞吐 + 分区 + rebalance

**参考答法：**

> 高吞吐来自五个机制：
> 1. **顺序写**日志追加，随机写变顺序写；
> 2. **零拷贝**（sendfile）减少内核态拷贝；
> 3. **分区并行**，多消费者并行；
> 4. **批量**（batch.size / linger）摊薄网络开销；
> 5. **压缩**（lz4/zstd）换 CPU 省带宽。
>
> **分区数怎么定**：`max(目标吞吐 / 单分区吞吐, 消费者并行度上限)`，并且要考虑键的倾斜。不是越多越好——分区多会增加文件句柄、端到端延迟和 rebalance 成本。
>
> **rebalance**：消费组成员变更时重新分配分区，期间该分区消费会停顿。可能重复消费。我的做法：
> - 静态成员（`group.instance.id`）减少滚动发布引发的 rebalance；
> - 手动提交 offset，**先处理成功再提交**；
> - 业务幂等（消息 `_id` + InsertIfAbsent）吸收重复。
>
> 项目里 topic 是 `MsgChatTransfer` / `MsgReadTransfer` + 对应 **DLQ**，消费失败进死信，不丢不堵。

### Q26. Go：worker pool + 泄漏排查

**参考答法：**

```go
func WorkerPool(jobs <-chan Job, n int) {
    var wg sync.WaitGroup
    for i := 0; i < n; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := range jobs { // channel 关闭 → 自然退出
                handle(j)
            }
        }()
    }
    wg.Wait()
}
```

要点：
- **buffered channel 做任务队列**，固定 worker 数防止 goroutine 爆炸；
- `for range` 依赖 channel 关闭退出，`defer wg.Done()` 保证计数正确；
- 传 `context.Context`，`ctx.Done()` 时取消在途任务；
- **泄漏排查**：`runtime.NumGoroutine` 打点告警；`pprof` 看 goroutine 栈；常见原因是「往无人消费的 channel 发送」或「忘记 close / cancel」。
>
> go-zero 侧我用过 zrpc 的拦截器链（限流、幂等、日志），服务启动走 `service.Service` 统一管理，配置热更是通过配置中心回调 + 优雅停机（`GracefulStop`）实现的——**先把连接收干净，再换配置**。

### Q27. 场景设计题：消息去重 + 断线补推

**参考答法：**

> **去重**：客户端生成 `messageId`（UUID/雪花），服务端 MongoDB `_id = messageId` + `InsertIfAbsent`，重复直接返回成功（幂等）。
>
> **断线补推**：
> 1. 连接层维护会话游标（客户端已收到的最大位置）；
> 2. 重连后客户端上报游标；
> 3. 服务端按 `conversationId + sendTime > cursor` 拉取缺口消息；
> 4. 未读数 = 会话全局计数 − 用户游标。
>
> **接口**：
> - `Send(msg) -> ack{messageId}`：同步 ACK，超时重发，服务端幂等；
> - `Sync(cursor) -> messages[] + newCursor`：增量拉取；
> - `Push`：在线推送，失败降级为游标待拉。
>
> **数据结构**：会话级有序日志（append-only）+ 用户游标 + 幂等键。这个设计和我 IM 项目的推拉结合模型是一致的。

### Q29. QPS ×10 第一个崩的是哪

**参考答法：**

> **第一崩点是 `im-ws` 的连接层**，其次是 MongoDB 写入。
>
> 推理：
> 1. 连接数 ×10 → FD/内存/心跳广播先到上限；
> 2. 即便连接扛住，消息写入 ×10 → 消费限速 600/s 会让 Kafka 积压快速上升；
> 3. API 层反而是最能扛的（无状态、好扩）。
>
> 扩容顺序我会这么排：
> 1. **先水平扩 im-ws**，LB 做连接分片；
> 2. **调消费预算 + 扩 task-mq 副本**（分区并行）；
> 3. MongoDB 写入优化：批量插入、索引精简、必要时预分片；
> 4. 对非核心路径（已读回执）降级异步。
>
> 这个判断是有依据的：我们监控的是「积压斜率、p99 延迟、连接建立失败率」三个先行指标，不是等用户投诉。

### Q30. 做成开源产品，砍什么留什么

**参考答法：**

### Q31. 印象最深的技术坑

**参考答法（示例，按真实细节改）：**

> 是**诊断证据冲突**那一类问题。现象是：同一条消息，有时判 `message_not_found`，有时判 `not_delivered`，偶现、难复现。
>
> 定位过程：
> 1. 先看回放日志，发现两次调用拿到的证据集合不同；
> 2. 顺着 requestId 追到 Connector，发现是**多数据源快照时间不一致**——消息表和投递事件表不在同一事务边界；
> 3. 加了 `findConflicts` 显式检测 + 以 requestId 关联证据，冲突就拒绝裁决。
>
> 收获有三条：
> 1. **偶现问题先怀疑数据一致性，再怀疑代码逻辑**；
> 2. **Agent 系统的可观测必须记录证据集合，而不是只记结论**；
> 3. **不一致时拒绝输出，比输出一个可能错的结论更专业**。
>
> 这个坑直接塑造了我后来「证据冲突 → insufficient_data + 人工升级」的设计原则。

## 七、压力追问的万能缓冲句

被问到不确定的细节时，**别停、别认输**，用这三句过渡：

1. 「这块我的设计取向是……具体实现细节我可以按我理解的版本讲，如果有偏差以代码为准。」
2. 「业界对这个问题通常有两条路线——A 是……B 是……我们选了 A，代价是……收益是……」
3. 「这个问题我可以拆成『正确性』和『性能』两半来答：正确性上我们保证……性能上我们的预算依据是……」

> [!success] 核心心法
> 面试官不是在找「做完了一切的人」，是在找「**知道自己在做什么、为什么这么做、出了问题怎么办**的人」。
> 你的项目有契约、有评测、有安全边界、有冲突拒绝——这些比「功能列表更长」值钱得多。**把它们讲成设计，而不是讲成功能。**
