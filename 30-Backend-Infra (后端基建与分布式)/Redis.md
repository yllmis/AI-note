# Redis

## 缓存三剑客（穿透 / 击穿 / 雪崩）

**一句话区分**：穿透是查**不存在**的数据，击穿是**单个热点**过期，雪崩是**大批 key**同时失效（或 Redis 挂了）。

| | 穿透 | 击穿 | 雪崩 |
|---|---|---|---|
| **数据是否存在** | 不存在 | 存在 | 存在 |
| **失效范围** | 从不命中 | 单个热点 key | 大批 key / 整个 Redis |
| **流量特征** | 持续打 DB | 瞬时打 DB | 瞬间全打 DB |
| **核心方案** | 空值、布隆 | 互斥锁、逻辑过期 | 随机 TTL、集群、限流 |

**总口诀**：**雪崩随机、击穿互斥、穿透布隆**。

### 缓存穿透

**问题本质**：查询一个**缓存和数据库都不存在**的数据。缓存永远不命中，请求每次都打到 DB。恶意攻击、爬虫、业务 bug（非法 ID）都可能触发。

**答案**：
1. **缓存空对象**：查库也查不到时，写入空值并设较短 TTL（30s~5min）。
   - 优点：实现简单；缺点：占内存，数据写入后有短暂不一致（需主动删空值）
2. **布隆过滤器**：key 先过 Bloom Filter（bit 数组 + 多个 hash）。
   - 任一位为 0 → **一定不存在**；全为 1 → **可能存在**（有误判）
   - **判不存在是确定的，判存在可能误报**
3. **参数校验 + 限流/黑名单**：入口拦非法 ID，封恶意 IP

**记忆**：**穿透查不存在，空值 + 布隆拦**。

### 缓存击穿

**问题本质**：某个**热点 key** 突然过期，大量并发请求瞬间全部落到 DB。注意：数据是**存在的**，只是缓存没了。

**答案**：
1. **互斥锁（SETNX / 分布式锁）**：只让一个请求查库重建缓存，其余等待或返回旧值。一致性好，但有等待开销，锁要设过期防死锁
2. **逻辑过期**：value 存逻辑过期时间，key **不设物理 TTL**。读到过期值先返回旧值，异步线程重建。不阻塞、吞吐高，但短暂不一致
3. **热点 key 永不过期 + 后台定时刷新**
4. **多级缓存**：本地缓存（`sync.Map` / bigcache / Ristretto）兜住热点

**记忆**：**击穿热点过期，互斥锁或逻辑过期**。

### 缓存雪崩

**问题本质**：**大量 key 同时过期**，或 **Redis 整体宕机**，请求全部砸到 DB。

| 情形 | 原因 | 典型场景 |
|------|------|----------|
| 大批 key 同时过期 | 批量写入设了相同 TTL | 缓存预热、定时任务重建 |
| Redis 宕机 | 单点故障、内存打满 | 未做集群、bigkey、被穿透打爆 |

**答案**：
1. **过期时间加随机值**：`TTL = base + rand(0, delta)`，打散过期点
2. **高可用**：Redis Cluster（16384 slot）/ 哨兵 + 主从
3. **多级缓存**：本地缓存挡一层
4. **限流降级熔断**：DB 前令牌桶限流，触发降级返回兜底
5. **缓存预热**：上线前提前加载热点

**记忆**：**雪崩大批失效，随机 TTL + 集群 + 限流**。

## 缓存不一致

**问题本质**：DB 和 Cache 是两套存储，读写不同步就会脏数据。核心矛盾是 **「读线程把旧值写回缓存」** 的竞态窗口。

两种更新策略的脏读窗口：

| 策略 | 竞态过程 | 问题 |
|------|----------|------|
| **先更新 DB，再删缓存** | A 读缓存 miss → 读 DB 旧值 → B 更新 DB + 删缓存 → A 把旧值写回缓存 | 脏数据（概率低，但存在） |
| **先删缓存，再更新 DB** | A 删缓存 → B 读 miss → 读 DB 旧值 → A 更新 DB → B 把旧值写回缓存 | 脏数据（窗口更大） |

### 延迟双删

**答案**：
1. 先删除缓存
2. 更新数据库
3. **延迟一段时间**（通常 500ms~1s）
4. **再次删除缓存**

**为什么有效**：第二次删除，正好把并发读请求在「删缓存 → 更新 DB」窗口内写回的旧值清掉。延迟时间要 **大于一次读请求耗时**（缓存 miss → 读 DB → 写回缓存的全程）。

**遗留问题**：
- 第二次删除失败怎么办？→ 重试队列 / 订阅 binlog 补偿
- 仍是**最终一致**，非强一致；延迟时间只能靠经验值
- 删除期间若有读，仍可能读到旧值（短暂）

**记忆**：**删、更、等、再删**。

### 缓存不一致的其他方案

**答案**：
1. **先更新 DB，再删缓存**（Cache-Aside，业界主流）：脏读窗口比先删缓存更小，配合延迟双删更稳
2. **订阅 binlog 异步删缓存**：Canal / Debezium 订阅 MySQL binlog → MQ → 删除缓存。与业务解耦，可靠性高（推荐生产方案）
3. **串行化 / 分布式锁**：读写互斥，一致性最强但吞吐差
4. **设过期时间兜底**：脏数据最多存活一个 TTL，简单有效的兜底
5. **直接更新缓存而非删除**：仍有并发覆盖问题，一般不推荐

**对比**：

| 方案 | 一致性 | 性能 | 复杂度 |
|------|--------|------|--------|
| 延迟双删 | 最终一致 | 高 | 低 |
| 先更 DB 再删缓存 | 最终一致 | 高 | 低 |
| 订阅 binlog | 最终一致（可靠） | 高 | 中 |
| 分布式锁串行 | 强一致 | 低 | 中 |
| TTL 兜底 | 弱一致 | 最高 | 最低 |

**记忆**：**主流先更后删，可靠靠 binlog，强一致才上锁，TTL 是保底**。

### 为什么先更 DB 再删缓存

两种顺序的竞态窗口对比：

| 顺序 | 竞态过程 | 窗口大小 |
|------|----------|----------|
| 先删缓存，再更 DB | A 删缓存 → B 读 miss 读到旧值 → A 更新 DB → B 写回旧值 | **大**：整个 DB 更新期间的读都会踩中，几乎必脏，必须延迟双删 |
| 先更 DB，再删缓存 | B 读 DB 旧值 → A 更新 DB + 删缓存 → B 写回旧值 | **极小**：B 必须横跨 A 的整个写请求，只有「读极慢写极快」才可能 |

**三个理由**：
1. **脏读窗口小得多**：读请求要横跨整个写请求才可能踩中
2. **删缓存是「失效」不是「重建」**：失败可重试 / 等 TTL 兜底，DB 永远是真相源
3. **避免更新缓存的并发覆盖**：两个写同时改缓存，后写的可能不是最新值；删掉让下次读重建更安全

**记忆**：**先更后删窗口小，删是失效好补偿**。

### Binlog 是什么

**答案**：MySQL 的**二进制日志**，记录所有**改数据**的操作（INSERT / UPDATE / DELETE），不记录 SELECT。

**三个用途**：

| 用途 | 说明 |
|------|------|
| 主从复制 | 主库写 binlog → 从库回放 |
| 数据恢复 | 按时间点恢复（PITR），配合全量备份 |
| 数据订阅 | Canal / Debezium / Flink CDC 订阅，同步到 ES / Redis / 数仓 |

**三种格式**：
- **Statement**：记 SQL 语句（省空间，但 `now()` 等函数可能主从不一致）
- **Row**：记每行变更前后值（准确，推荐）
- **Mixed**：混合，默认 Statement，不安全时切 Row

**如何解决缓存不一致**：

```
业务：更新 DB（删缓存失败？无所谓）
        ↓
MySQL：强制写 binlog
        ↓
Canal 订阅 → MQ → 消费者删缓存
```

- **解耦**：业务只管写 DB，删缓存交给订阅方
- **不丢**：binlog 强制落盘，应用挂了照样有
- **最终一致**：最可靠的补偿手段，生产推荐

**记忆**：**binlog 记变更，主从恢复订阅三用；Canal 订阅删缓存，解耦不丢**。
