# 第一版简历解读提问

> [!info] 视角说明
> 以下问题以**资深后端 / Agent 工程师面试官**身份，基于《杨锦松_南昌大学_后端｜Agent工程师》简历提出。
> 面试时长约 60 分钟：开场 5 分钟 → 项目深挖 30 分钟 → 基础拷问 15 分钟 → 反问 10 分钟。
> 每题标注 ==考察点== 与 ==追问方向==，方便针对性准备。

---

## 〇、开场与求职动机（5 分钟）

### Q1. 请做一个 2 分钟自我介绍，重点讲你为什么同时投「后端」和「Agent 工程师」两个方向。

**考察点**：表达结构、自我认知、岗位匹配度。简历写「后端｜Agent工程师」双意向，我会看你到底是「后端为主、Agent 为加分」还是「两个都当主线」。

**追问**：
- 如果只能二选一，你选哪个？为什么？
- 你是 2028 届（大三），这次投的是实习还是秋招提前批？能实习多久、每周几天？

### Q2. 简历上写了熟练使用 Claude Code、Codex、Copilot，还提到 vibe coding 开源小工具。这些工具在你的项目里**真正改变了哪一段开发流程**？

**考察点**：是否只是「用过 AI」，还是形成了自己的 AI 工作流。这是 Agent 岗的核心信号。

**追问**：
- 举一个 AI 写错、你如何发现并纠正的案例。
- 你怎么判断 AI 生成的代码可以合入？有没有自己的 review checklist？

## 一、IM 消息异常诊断 Agent（重点，15～20 分钟）

> [!important]
> 这是简历里**最新、最贴合 Agent 岗**的项目（2026.08–2026.10），我会用一半时间深挖。凡是写在简历上的词——「受控诊断」「规则引擎」「白名单」「41 个回归场景」「人工确认草稿」——都会被逐个拆开验证是不是你亲手做的。

### Q3. 为什么这个场景要用 Agent，而不是写死的规则脚本 / 关键词匹配？

**考察点**：Agent 的适用边界。客服排查本质是「多条件组合查询 + 状态归因」，纯规则也能做。我要看你是否想清楚了引入 LLM 的收益（自然语言理解、多轮澄清、信息补全）和代价（不确定、成本、误判）。

**追问**：
- 什么情况下你会**后悔**用了 Agent，改回规则？
- 如果没有 LLM，用 ES / 规则引擎能做到什么程度？差距具体在哪？

### Q4. 画出一次完整诊断的时序图：从用户输入「昨天给张三发的消息没收到」到给出结论，中间经过哪些模块？模型调用几次？

**考察点**：整体架构是否清晰、链路是否自己实现。要求能画出：`用户 → 对话管理 → LLM(抽取/追问/工具选择) → 统一查询接口 → IM-Grpc 适配层 → 规则引擎 → 结论/证据`。

**追问**：
- 哪些步骤是模型做的，哪些是代码做的？**边界怎么划的**，为什么这么划？
- 一次诊断平均几次 LLM 调用？延迟大概多少？有没有做过缓存或并行？

### Q5. 「消息状态由查询证据和代码规则确定」——这句话怎么落到代码里？为什么不让模型直接判断状态？

**考察点**：**幻觉控制**是 Agent 工程的核心。你要说清楚：模型只负责「查什么、缺什么信息」，状态分类是确定性规则（如「查无记录 → 不存在」「有记录无投递事件 → 未投递」）。

**追问**：
- 规则引擎的规则你怎么组织的？多少条？加一条新状态（比如「被风控拦截」）要改几处？
- 证据冲突时（比如消息表有记录但投递链路没有）怎么处理？谁优先？为什么？

### Q6. 「信息不足或存在多个候选时自动追问」——追问的触发条件是什么？怎么防止无限追问或瞎追问？

**考察点**：多轮对话状态机设计。期望回答包括：槽位（messageId / userId / 时间范围）填充度、候选消歧规则、最大追问轮数、超时兜底。

**追问**：
- 用户答非所问怎么办？追问模板是模型生成的还是固定模板？
- 如果用户就是不知道 messageId，只说「昨天的消息」，系统怎么收敛？

### Q7. 安全这块写得很细：参数校验、白名单、超时、有限重试、调用次数上限、日志脱敏。挑两个说：**为什么需要**，以及**怎么实现**。

**考察点**：Agent 工具面的安全意识，是加分项也是「是不是自己写的」的照妖镜。我会重点盯：
- **白名单**：是对工具名白名单，还是对查询字段/资源白名单？
- **调用次数上限**：计数器放哪？并发诊断怎么保证不超？
- **日志脱敏**：脱敏哪些字段？正则还是标注器？回放日志里还能看到原文吗？

**追问**：
- 如果模型被诱导（prompt injection）让它调用未授权工具，你有几层防线？
- 「重发等写操作不直接开放给 Agent」——那人工确认草稿的**幂等与重复提交**怎么做的？数据库唯一键？状态机？

### Q8. 41 个固定回归场景是怎么设计出来的？怎么保证改一次 Prompt 不把别的场景搞崩？

**考察点**：Agent 的可测试性与评测体系。期待：场景分层（状态分类 / 信息缺失 / 查询异常 / 权限边界 / 危险操作）、断言什么（最终状态？证据？工具调用序列？）、是否跑 CI。

**追问**：
- 41 个里挑一个最容易挂的，说说它测什么、为什么容易挂。
- 有没有量化指标（准确率、追问轮数、工具调用次数）？大概什么水平？
- 如果上线后发现误判，你怎么定位是 Prompt 问题、工具数据问题，还是规则问题？

### Q9. 「隔离环境下的只读联调」——为什么强调只读和隔离？联调时踩过什么坑？

**考察点**：对生产数据的敬畏、环境治理。顺带验证你是否真的接过 IM-Grpc。

**追问**：
- 统一查询接口 / 数据适配层，是新写一个 BFF，还是在 IM-Grpc 里加只读接口？为什么？
- 自有 IM 的消息、投递、连接三类数据分别来自哪（表 / 服务 / 存储）？

### Q10. 压力题：如果客服一天问 1 万次，模型成本和稳定性怎么扛？如果模型接口挂了，诊断还能不能降级？

**考察点**：生产化思维。期望：意图抽取用小模型/规则预筛、结果缓存、超时降级到纯规则查询、熔断、审计日志。

## 二、微服务即时通讯平台（10～15 分钟）

> [!warning] 项目真实性拷问
> 这个项目在面试中很常见，也容易被识破「跟教程做的」。我会问设计权衡、线上事故、你改过哪几行——答不上「为什么」比答不上「是什么」更致命。

### Q11. 为什么用「Timeline + 读扩散」，而不是写扩散？各适合什么场景？

**考察点**：IM 核心模型理解。要能对比：
- 读扩散：写轻读重，适合群大、在线率低；会话只存一份 + 计数/游标
- 写扩散：读轻写重，适合小群、在线率高；扇出存储爆炸

**追问**：
- 万人群用你这套会怎样？未读数怎么算？会不会算错、算重？
- `Conversation.Total` 全局计数 vs 用户已读游标，并发下怎么保证一致？

### Q12. 消息链路：WebSocket → Kafka → 落库 → 推送。说说**消息可靠性**怎么保证？是 at-least-once 还是 exactly-once？

**考察点**：不要背「exactly-once」，要讲清 Kafka 语义 + 业务侧幂等。期望：生产端 ack、消费端手动提交 offset、落库成功再 commit、消费失败重试 + 死信、客户端 ACK + 超时重发。

**追问**：
- 落库成功但 offset 没提交就宕机，会发生什么？
- 消息顺序怎么保证？同一个会话乱序了用户会看到什么？

### Q13. 「Redis 幂等控制，通过原子操作防止重复处理」——具体是哪个命令？key 怎么设计？过期时间怎么定？

**考察点**：SET NX EX / Lua 的真实使用。追问极端情况：
- SET 成功但业务失败，后续请求被永久挡掉怎么办？
- 为什么不用数据库唯一索引兜底？

### Q14. 「消费者侧通过令牌桶将消息处理速率控制在 600 条/秒」——600 这个数怎么来的？令牌桶算法你自己写的还是用库？

**考察点**：容量评估是否拍脑袋。要能说：MongoDB 写入压测 / 单分片吞吐 / 留了多少水位 / 超过 600 之后是阻塞、丢弃还是堆积。

**追问**：
- 令牌桶放消费者进程内，多副本部署时全局限速还成立吗？
- 削峰之后积压了 100 万条，你怎么恢复？

### Q15. WebSocket 长连接：心跳怎么做？连接数上来之后**网关先崩还是服务先崩**？

**考察点**：长连接工程能力。追问：连接管理结构（map 分片？）、单机连接数上限、连接迁移 / 负载均衡（sticky？）、心跳超时与 Redis 在线状态 TTL 的一致性。

### Q16. 存储选型：消息为什么放 MongoDB，用户/关系放 MySQL？MongoDB 的分片、索引、写入瓶颈考虑过吗？

**考察点**：多存储不是为了「显得技术多」。要能给出取舍理由，以及 MongoDB `chat_log` 的索引设计（会话+时间？）。

**追问**：
- 消息量大了之后 MongoDB 单集合扛不住，你的演进路线是什么（分片键 / 冷热分离 / 归档）？
- 为什么不用 MySQL 分表？

### Q17. 服务拆分：user / social / im / task 四个服务，是不是拆得太细了？分布式事务怎么处理？

**考察点**：架构成熟度。追问：
- 跨服务创建群聊 + 拉人 + 发首条消息，失败了怎么回滚？
- gRPC 调用失败的重试、超时、熔断策略是怎样的？go-zero 里怎么配？

### Q18. 「接入限流、令牌桶限流」——API 层限流和消费者限流是不是重复了？限流阈值压测过吗？

**考察点**：能否发现简历表述里可能的冗余，并给出清晰分层（网关 QPS 限流 vs MQ 消费限速）。

## 三、VIVO AIGC 竞赛项目（5～8 分钟）

### Q19. BERT 选型：当时对比了哪些模型？为什么是 BERT 而不是 LLM / RoBERTa / 业务关键词规则？

**考察点**：模型选型的业务约束（数据量、延迟、成本、可解释）。追问训练数据规模、类别不均衡怎么处理。

### Q20. ToSPrompt 和 LoRA 链路分别解决什么问题？LoRA 的秩、数据量、效果提升是多少？

**考察点**：是否真做过微调，而不是只挂了名词。答不上超参和效果曲线会大扣分。

**追问**：
- 为什么不直接 prompt 一个大模型？成本？延迟？私有化？
- 微调后过拟合了吗？怎么判断？

### Q21. Go 中间转发层的职责是什么？为什么不直接让前端调模型服务？

**考察点**：工程分层。期望：鉴权、限流、多平台适配、结果聚合、缓存、日志审计。

### Q22. 「多平台商品口碑」——跨平台数据怎么对齐？评价指标是什么？复赛第 13 名，差在哪？

**考察点**：业务理解 + 复盘能力。追问：bad case 分析、如果重来会改什么。

## 四、基础拷问（结合简历「专业技能」，10～15 分钟）

> [!note]
> 简历写了 MVCC、缓存三连、Kafka 高吞吐，必问。答不上 = 简历注水。

### Q23. MySQL MVCC：说一下 ReadView、undo log、可重复读如何实现？当前读和快照读的区别？

**追问**：
- 可重复读下会不会幻读？间隙锁解决的是什么场景？
- 长事务对 MVCC 的危害是什么？

### Q24. Redis：缓存雪崩、穿透、击穿分别是什么？你在 IM 项目里用 Redis 防的是哪一种？

**追问**：
- 在线状态的 key 过期了但用户还在线，怎么办？
- Redis 和 MySQL 双写不一致，你的方案是什么（Cache Aside / 延迟双删 / binlog）？

### Q25. Kafka 高吞吐靠什么？顺序写、零拷贝、分区、批量、压缩各解决什么问题？

**追问**：
- 一个 topic 分区数怎么定？
- 消费组 rebalance 时会发生什么？你项目里怎么避免重复消费？

### Q26. Go：写一个 goroutine 安全的 worker pool，说说 channel 的用法和 goroutine 泄漏怎么排查。

**追问**：
- `context` 在超时取消里怎么传？
- go-zero 的 `core/service` 启动流程、拦截器机制了解吗？

### Q27. 算法（可选，视时间）：手写 / 口述一道中等题 + 一个场景设计题。

**示例场景题**：设计「消息去重 + 断线重连补推」的接口与数据结构（可对照你的 IM 项目）。

## 五、压力测试 & 反思题（5 分钟）

### Q28. 两个项目里，哪一段是你**独立设计**、而不是看教程/开源项目改的？说说为什么这么设计。

**考察点**：真实性与独立思考。这是全场面**最重要**的一题。

### Q29. 你的 IM 项目如果 QPS 突然 ×10，系统第一个崩的是哪里？为什么？

**考察点**：瓶颈识别（WebSocket 网关连接数？MongoDB 写入？Kafka 积压？）与扩容策略。

### Q30. 如果让你把「IM 异常诊断 Agent」做成一个开源产品，你会砍掉什么、保留什么？

**考察点**：产品取舍、MVP 思维。

### Q31. 最近半年踩过印象最深的技术坑是什么？怎么定位、怎么解决的？

**考察点**：实战深度、调试能力、总结能力。

### Q32. 你的简历里没写 FlexiRAG Engine（自我介绍里有）。是有意不写吗？它现在是什么状态？

**考察点**：项目取舍与作品一致性。若是项目下线 / 未完成，要能坦诚说明；若是亮点被埋没，面试时要主动讲。

## 七、面试官视角的「风险点」速查

> [!warning] 容易被抓住的软肋
> 准备时优先补齐这些：

| 风险点 | 简历原文线索 | 应对建议 |
|---|---|---|
| Agent 与规则边界不清 | 「模型负责理解…消息状态由规则确定」 | 准备一张「模型 vs 代码」职责图 |
| 项目像跟练 | IM 平台时间跨度仅 2 个月，技术点密集 | 能讲出「我自己改的 3 处」和失败案例 |
| 量化数据薄弱 | 「600 条/秒」只有这一个数字 | 补：QPS、消息延迟、消息量级、Agent 准确率 |
| 双岗位意向 | 「后端｜Agent工程师」 | 明确主次，避免两头不靠 |
| 在读身份 | 2028 届本科 | 说清可实习时间、课程安排、转正意向 |
| 竞赛深度 | BERT/LoRA/ToSPrompt 名词多 | 准备超参、数据量、效果对比表 |
| AI 工具使用 | 熟练 Claude Code 等 | 从「使用者」升级到「工程化使用者」（规范、评测、防幻觉） |

## 八、建议的答题框架（STAR + 权衡）

回答项目题时统一用这个结构，避免背稿感：

1. **背景/约束**：什么场景、什么规模、什么痛点
2. **方案对比**：至少 2 个候选，说明为什么选 A 不选 B
3. **实现细节**：落到组件/命令/数据结构
4. **效果**：有数字，没有数字就说「如何验证过」
5. **不足与演进**：哪里还不够好，下一步怎么做

> [!quote]
> 面试官真正想听的不是「用了什么」，而是「==为什么这么用、还能怎么用、出了问题怎么办==」。
