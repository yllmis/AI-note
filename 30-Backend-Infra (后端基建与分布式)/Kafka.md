# Kafka

## 削峰填谷

**结论先行**：Kafka **本身没有「削峰」功能**，本质是**持久化缓冲池**（追加写日志）。削峰填谷是**架构模式**：生产方快速写入积压，消费方按自身能力匀速拉取，流量曲线被抹平。

```
生产（快、突发）→ Kafka（追加写、持久化缓冲）→ 消费（慢、匀速）
                        ↑
              积压在这里 = 流量抹平
```

### 削峰填谷的准确含义

词来自电力系统：
- **削峰**：峰值流量不直接打下游，先进 Kafka 排队
- **填谷**：低峰时匀速消化积压，下游按**平均流量**规划资源，不用按峰值扩容

### 消费速率谁来定（两个维度）

| 维度 | 谁控制 | 作用 |
|------|--------|------|
| **批大小**（一次拉多少条） | `max.poll.records` / `fetch.max.bytes` | 控单批内存、单批耗时 |
| **速率**（每秒多少条） | **pull 不直接控** | 靠处理耗时被动背压，或**主动限流** |

**关键认知**：pull 模式限的是「一次拿多少」，**不是「每秒多少」**。

```
rate ≈ max.poll.records / (poll + 处理耗时)
```

- 处理很快（只是转发）→ 一秒 poll 几百次，**照样打爆下游**
- 处理含写 DB → 写库慢会天然背压，但这是「靠 DB 慢保护 DB」，不靠谱

**保护 DB QPS 的正确姿势**：

```
Kafka → pull(max.poll.records=200) → 令牌桶(1000 QPS) → 写 DB
            ↑ 批大小兜底                    ↑ 每秒硬上限
```

1. **`max.poll.records`**：批大小兜底，防单批太大、内存打爆、poll 超时触发 rebalance
2. **令牌桶（Guava RateLimiter）**：写 DB 前 `acquire()`，硬性保证每秒不超过 N 条
3. 更狠：DB 写用**固定线程池 + 有界队列**，队列满阻塞 poll，天然背压

**记忆：pull 管批不管秒，护 DB 要靠令牌桶；批大小防爆内存，QPS 靠桶**。

### 积压与磁盘风险

Kafka 顺序写吞吐极高，设计上能扛**几天**积压。真正的风险不是写入太快，而是：
- **consumer lag 持续增长**没人管
- **磁盘水位**打满导致写失败

**对策**：
1. 监控 consumer lag（Kafka Manager / Prometheus + kafka-lag-exporter）
2. lag 告警 → 扩消费者实例 / 增分区
3. 调整 retention（过期删除或按容量删）
4. 磁盘水位告警

**记忆**：**Kafka 不削峰，只当缓冲池；pull 管批不管秒，护 DB 靠令牌桶；lag 磁盘要盯住**。
