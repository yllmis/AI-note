### Go 基础

#### Q1：数组和 slice 区别，slice 扩容机制

**答案**：

**数组 vs Slice**：

| | 数组 | Slice |
|---|------|-------|
| 长度 | 固定，编译期确定 | 动态可变 |
| 赋值 | 值拷贝 | 引用类型，底层指向数组 |
| 函数传参 | 值拷贝（开销大） | 传引用（只复制 slice header） |
| 声明 | `var a [5]int` | `var s []int` |

**Slice 扩容机制**（Go 1.18+）：
1. 如果新容量 > 旧容量 2 倍，直接用新容量
2. 否则，如果旧容量 < 256，新容量 = 旧容量 × 2
3. 如果旧容量 ≥ 256，新容量 = 旧容量 × 1.25 + 192（渐进式增长，避免内存浪费）
4. 最终容量会根据内存对齐规则向上取整到合适的 class size

**记忆**：**数组固定值拷贝，slice 动态引用类型；扩容：小于 256 翻倍，大于 256 涨 1.25 倍 + 192**。

#### Q2：Go 的 init 函数

**答案**：

- 每个包可以有多个 `init` 函数，甚至同一个文件中也可以有多个
- 执行顺序：全局变量初始化 → `init()` → `main()`
- 多个包的 `init` 按 import 依赖关系执行（被依赖的包先初始化）
- 不能被手动调用，也没有参数和返回值
- 常用于注册驱动、初始化配置、注册路由等

**记忆**：**init 自动执行，顺序：变量 → init → main；不能手动调，用于包级初始化**。

#### Q3：两个 interface 能比较吗

**答案**：

可以比较，但有条件：
- 两个 interface 相等需要：**动态类型相同** 且 **动态值相等**
- 如果动态类型不可比较（如 slice、map、func），会 **panic**

```go
var a interface{} = []int{1}
var b interface{} = []int{1}
fmt.Println(a == b) // panic: comparing uncomparable type []int
```

**记忆**：**interface 可比较，但动态类型必须可比较；slice/map/func 比较会 panic**。

#### Q4：局部变量是分配在栈上还是堆上的（内存逃逸）

**答案**：

Go 编译器通过 **逃逸分析（Escape Analysis）** 决定分配位置：
- **栈上分配**：变量生命周期不超出函数范围（默认优先）
- **堆上分配（逃逸）**：变量被外部引用、返回指针、赋值给接口类型、闭包捕获等

常见逃逸场景：
1. 函数返回局部变量的指针
2. 变量被赋值给 `interface{}`（编译器无法确定大小）
3. 变量占用空间过大
4. 闭包引用的局部变量
5. 发送到 channel 的变量

用 `go build -gcflags="-m"` 可以查看逃逸分析结果。

**记忆**：**默认栈分配；返回指针、赋给接口、闭包捕获、大对象会逃逸到堆**。

#### Q5：介绍 Go 的 interface

**答案**：

Go 的 interface 是隐式实现的鸭子类型：

**底层结构（iface / eface）**：
- `eface`（空接口 `interface{}`）：`(_type, data)` — 类型指针 + 数据指针
- `iface`（非空接口）：`(tab, data)` — itab 包含类型信息和方法集 + 数据指针

**两种接口**：
| | 空接口 `interface{}` | 非空接口 |
|---|---|---|
| 底层结构 | eface | iface |
| 方法要求 | 无 | 必须实现所有方法 |
| 例子 | `any` | `io.Reader` |

**隐式实现**：不需要 `implements` 关键字，只要类型实现了接口的所有方法，就自动满足该接口。

**记忆**：**interface 隐式实现，底层 eface/iface 存类型+数据指针；空接口存任意类型，非空接口要求实现所有方法**。

### Go 并发

#### Q6：GMP 模型、每个 P 的缓存队列和全局缓存队列，局部饥饿问题、全局饥饿问题

**答案**：

**GMP 模型**：
- **G（Goroutine）**：协程，包含栈、PC、状态
- **M（Machine）**：系统线程，执行 G 的实体
- **P（Processor）**：逻辑处理器，持有本地运行队列，数量 = `GOMAXPROCS`

**队列结构**：
- **P 本地队列**：每个 P 持有一个最多 256 个 G 的本地队列（无锁，LRQ）
- **全局队列**：所有 P 共享的队列（有锁，GRQ）

**调度策略**：
1. 优先从 P 本地队列取 G
2. 本地队列空了，从全局队列取一批（每次取 1/GRQ 长度，避免饥饿）
3. 全局队列也空了，触发 work stealing：从其他 P 偷一半
4. 每执行 61 个 G，强制检查一次全局队列（防止全局队列饥饿）

**局部饥饿**：某个 P 的本地队列长时间没有 G 执行 → work stealing 机制解决
**全局饥饿**：全局队列中的 G 长时间得不到执行 → 每 61 次调度强制检查全局队列

**记忆**：**P 本地队列 256 上限 + 全局队列；每 61 次调度查全局队列防饥饿；work stealing 偷一半防局部饥饿**。

#### Q7：Golang 的 CSP 模型

**答案**：

CSP（Communicating Sequential Processes）= 通信顺序进程，Go 的并发哲学：

- **核心思想**：Don't communicate by sharing memory; share memory by communicating
- **实现**：goroutine（并发执行单元）+ channel（通信管道）
- **特点**：goroutine 之间不直接共享内存，通过 channel 传递数据

**与共享内存模型的区别**：
| | CSP（Go） | 共享内存（Java/C++） |
|---|-----------|---------------------|
| 通信方式 | channel 发送/接收 | 共享变量 + 锁 |
| 同步 | channel 天然同步 | 需要 mutex/semaphore |
| 数据竞争 | 设计上避免 | 需要开发者自己保证 |

**记忆**：**CSP = goroutine + channel；用通信共享内存，不用共享内存通信**。

#### Q8：goroutine + channel 使用场景剖析，有无缓存通道问题（抠细节）

**答案**：

**无缓冲 channel**（`make(chan T)`）：
- 发送和接收必须同时就绪，否则阻塞
- 保证同步：发送方确认接收方已收到
- 场景：goroutine 间同步信号、确保任务完成

**有缓冲 channel**（`make(chan T, n)`）：
- 缓冲区满时发送阻塞，空时接收阻塞
- 异步：发送方不等接收方
- 场景：生产者-消费者模式、限流、批处理

**使用场景**：
1. **任务分发**：多个 worker 从同一个 channel 取任务
2. **结果收集**：多个 goroutine 把结果发到同一个 channel
3. **信号通知**：`done := make(chan struct{})` 通知退出
4. **超时控制**：`select` + `time.After`
5. **限流**：有缓冲 channel 做信号量

**记忆**：**无缓冲同步（阻塞等对方），有缓冲异步（满阻塞发/空阻塞收）；场景：任务分发、结果收集、信号通知、超时、限流**。

#### Q9：如果一个 buffer 正在写入，把它 close 了会怎么样？close 的 buffer，一直读会一直空吗

**答案**：

**close 正在写入的 channel**：
- close 后不能再发送数据，否则 **panic**（send on closed channel）
- 但 close 前已经发送到缓冲区的数据仍然可以正常接收

**close 后一直读**：
- 如果缓冲区还有数据，继续读会拿到数据，`ok = true`
- 缓冲区读完后，继续读不会阻塞，会返回 **零值**，`ok = false`
- 不会 panic，也不会一直阻塞

```go
ch := make(chan int, 3)
ch <- 1; ch <- 2
close(ch)
fmt.Println(<-ch) // 1, true
fmt.Println(<-ch) // 2, true
fmt.Println(<-ch) // 0, false（零值，ok=false）
```

**记忆**：**close 后不能再发（panic）；已发的数据能读完；读完后返回零值不阻塞**。

#### Q10：goroutine 会不会泄露，怎么泄露，泄露以后是怎么表现

**答案**：

**会泄露**，常见泄露场景：
1. **channel 阻塞**：goroutine 在无接收者的 channel 上发送，或在无发送者的 channel 上接收
2. **死锁**：goroutine 等待永远不会到来的信号
3. **无限循环**：goroutine 中有无退出条件的 for 循环
4. **锁未释放**：goroutine 持有 mutex 后 panic 或死循环

**泄露后的表现**：
- 内存持续增长（goroutine 栈 + 关联的变量无法 GC）
- goroutine 数量不断上升（`runtime.NumGoroutine()` 监控）
- 极端情况导致 OOM（Out of Memory）

**预防**：
- 使用 `context.WithCancel` 控制 goroutine 生命周期
- channel 操作加 `select` + `ctx.Done()` 或 `time.After`
- 使用 `errgroup` 管理一组 goroutine

**记忆**：**goroutine 会泄露：channel 阻塞、死锁、无限循环；表现：内存增长、goroutine 数量上涨；用 context 控制生命周期**。

### 计算机网络

#### Q11：http/https 的区别（抠细节）

**答案**：

| | HTTP | HTTPS |
|---|------|-------|
| 端口 | 80 | 443 |
| 安全性 | 明文传输 | TLS/SSL 加密 |
| 证书 | 不需要 | 需要 CA 证书 |
| 性能 | 快 | 多了 TLS 握手，稍慢（约 1-2 RTT） |
| SEO | 无优势 | 搜索引擎优先收录 |

**HTTPS 详细流程**：
1. 客户端发起请求，发送支持的加密套件列表 + 随机数 Client Random
2. 服务端返回选定的加密套件 + 随机数 Server Random + 证书
3. 客户端验证证书（CA 链），生成 Pre-Master Secret，用服务端公钥加密发送
4. 双方用 Client Random + Server Random + Pre-Master Secret 生成对称密钥
5. 后续通信用对称密钥加密（性能好）

**TLS 1.3 改进**：1-RTT 握手，移除不安全算法，支持 0-RTT 恢复。

**记忆**：**HTTP 明文 80 端口，HTTPS 加密 443 端口；HTTPS 握手：随机数交换 → 证书验证 → 密钥协商 → 对称加密通信**。

#### Q12：叙述一下从你访问连接到返回数据的服务器的全过程（问的很深很细）

**答案**：

1. **浏览器解析 URL**：提取协议、域名、端口、路径
2. **DNS 解析**：浏览器缓存 → OS 缓存 → hosts 文件 → 本地 DNS → 根 DNS → 权威 DNS，得到 IP
3. **ARP 解析**：如果目标 IP 在同一子网，用 ARP 查 MAC 地址；否则查网关 MAC
4. **TCP 三次握手**：建立连接（HTTPS 还有 TLS 握手）
5. **发送 HTTP 请求**：构造请求报文，经过 TCP 分段 → IP 封包 → 数据链路层帧 → 物理层比特流
6. **路由转发**：经过多个路由器，每个路由器查路由表转发
7. **服务器接收**：Nginx 反向代理 → 负载均衡 → 应用服务器
8. **应用处理**：解析请求 → 路由匹配 → 业务逻辑 → 查数据库/缓存 → 构造响应
9. **返回 HTTP 响应**：状态码 + 响应头 + 响应体
10. **浏览器渲染**：解析 HTML → DOM 树 → CSSOM → 渲染树 → 布局 → 绘制 → 合成
11. **连接管理**：HTTP/1.1 Keep-Alive 复用 / HTTP/2 多路复用 / 四次挥手关闭

**记忆**：**URL 解析 → DNS → ARP → TCP 握手 → HTTP 请求 → 路由转发 → 服务器处理 → 响应 → 渲染 → 连接管理**。

#### Q13：网络拥塞状态下 TCP 数据传输，从流量控制角度聊聊

**答案**：

**流量控制（Flow Control）**：接收方通过 **滑动窗口** 告诉发送方自己还能接收多少数据
- 接收方在 ACK 中携带 `rwnd`（接收窗口大小）
- 发送方发送的数据量 ≤ rwnd
- 如果 rwnd = 0，发送方暂停发送，但定期发 **窗口探测** 以防 rwnd 恢复

**拥塞控制（Congestion Control）**：防止网络过载
- **拥塞窗口 cwnd**：发送方维护的窗口大小
- 实际发送窗口 = min(cwnd, rwnd)

**四个算法**：
| 算法 | 触发条件 | cwnd 变化 |
|------|----------|-----------|
| 慢启动 | 连接开始 | 指数增长（1→2→4→8...） |
| 拥塞避免 | cwnd ≥ ssthresh | 线性增长（+1/RTT） |
| 快重传 | 3 个重复 ACK | 立即重传 |
| 快恢复 | 快重传后 | ssthresh = cwnd/2，cwnd = ssthresh |

**记忆**：**流量控制用 rwnd 防接收方溢出，拥塞控制用 cwnd 防网络过载；实际窗口 = min(cwnd, rwnd)；慢启动指数、拥塞避免线性、快重传快恢复处理丢包**。

#### Q14：TCP 如何保证高可靠的

**答案**：

1. **序列号 + ACK 确认**：每个字节编号，接收方确认收到
2. **超时重传**：超时未收到 ACK 则重传，RTO 动态计算（基于 RTT）
3. **滑动窗口**：控制发送速率，避免淹没接收方
4. **校验和**：检测数据在传输中是否损坏
5. **流量控制**：接收方通告窗口大小，发送方遵从
6. **拥塞控制**：慢启动、拥塞避免、快重传、快恢复
7. **数据重排**：接收方缓冲区重排乱序到达的报文
8. **去重**：序列号识别重复报文并丢弃

**记忆**：**序列号+ACK 确认到达、超时重传、滑动窗口流控、校验和纠错、拥塞控制防过载、缓冲区重排**。

### 操作系统

#### Q15：进程和协程区别，具体到上下文切换，哪些资源共享哪些不共享

**答案**：

| | 进程 | 协程（Goroutine） |
|---|------|-------------------|
| 调度 | OS 内核调度 | 用户态调度（Go runtime） |
| 上下文切换 | 保存/恢复 PCB（页表、寄存器、栈指针等） | 保存/恢复少量寄存器（PC、SP、BP 等） |
| 切换开销 | 微秒级（需陷入内核） | 纳秒级（用户态完成） |
| 共享资源 | 不共享（独立地址空间） | 共享进程地址空间、文件描述符、全局变量 |
| 不共享 | 地址空间、文件描述符表、信号处理 | 栈（每个 goroutine 独立栈） |

**进程上下文切换**：
1. 保存当前进程的寄存器到 PCB
2. 切换页表（刷新 TLB）
3. 加载新进程的寄存器
4. 切换内核栈

**协程上下文切换**：
1. 保存当前 goroutine 的 PC、SP、BP 等到 g 结构体
2. 加载新 goroutine 的 PC、SP、BP
3. 无需切换页表，无需陷入内核

**记忆**：**进程切换重（切页表+进内核），协程切换轻（用户态换寄存器）；协程共享地址空间和文件描述符，不共享栈**。

### MySQL

#### Q16：MySQL 的不同索引类型

**答案**：

**按数据结构分**：
| 类型 | 说明 | 适用 |
|------|------|------|
| B+ 树索引 | InnoDB 默认，叶子节点双向链表 | 等值、范围、排序、前缀 |
| 哈希索引 | Memory 引擎，O(1) 查找 | 仅等值查询 |
| 全文索引 | 倒排索引 | 文本搜索 |
| R 树索引 | 空间数据索引 | GIS 地理位置 |

**按逻辑功能分**：
| 类型 | 说明 |
|------|------|
| 主键索引 | 唯一 + NOT NULL，聚簇索引 |
| 唯一索引 | 值唯一，允许 NULL |
| 普通索引 | 无限制 |
| 联合索引 | 多列组合，遵循最左前缀原则 |
| 覆盖索引 | 查询字段全在索引中，无需回表 |

**记忆**：**B+ 树是默认；主键/唯一/普通/联合/覆盖是逻辑分类；联合索引遵循最左前缀**。

#### Q17：聊聊 MySQL 事务，隔离级别（结合具体实例讲解）

**答案**：

**ACID**：原子性（Undo Log）、一致性（目标）、隔离性（锁+MVCC）、持久性（Redo Log）

**四种隔离级别**：

| 级别 | 脏读 | 不可重复读 | 幻读 |
|------|------|-----------|------|
| READ UNCOMMITTED | 有 | 有 | 有 |
| READ COMMITTED | 无 | 有 | 有 |
| REPEATABLE READ（默认） | 无 | 无 | InnoDB 通过 MVCC+间隙锁解决 |
| SERIALIZABLE | 无 | 无 | 无 |

**实例**：
- **脏读**：事务 A 读到事务 B 未提交的修改，B 回滚后 A 读到的数据无效
- **不可重复读**：事务 A 两次读同一行，中间事务 B 修改了该行，A 两次读结果不同
- **幻读**：事务 A 两次查同一范围，中间事务 B 插入了新行，A 两次查结果行数不同

**MVCC（多版本并发控制）**：
- 每行有隐藏列：`DB_TRX_ID`（最后修改的事务 ID）、`DB_ROLL_PTR`（回滚指针）
- Read View 记录活跃事务列表，根据可见性规则判断哪个版本对当前事务可见
- RC 每次 SELECT 生成新 Read View；RR 只在第一次 SELECT 生成

**记忆**：**RC 解决脏读，RR 解决不可重复读（默认），InnoDB RR 通过 MVCC+间隙锁也解决幻读；MVCC 用 Read View 判断版本可见性**。

### Redis

#### Q18：Redis 底层数据类型，具体实现，使用场景

**答案**：

| 类型 | 底层实现 | 使用场景 |
|------|----------|----------|
| String | SDS（Simple Dynamic String） | 缓存、计数器、分布式锁 |
| List | quicklist（ziplist + 双向链表） | 消息队列、最新列表 |

| Stream | radix tree + listpack | 消息队列（支持消费者组） |

**记忆**：**String(SDS) 缓存计数、List(quicklist) 队列、Hash 对象、Set 去重、ZSet(skiplist) 排行榜**。

#### Q19：Redis 的可持久化机制

**答案**：

**RDB（Redis Database Snapshot）**：
- 定时生成内存快照，写入 `.rdb` 文件
- 触发方式：`SAVE`（阻塞）/ `BGSAVE`（fork 子进程，COW）
- 优点：恢复快、文件紧凑
- 缺点：可能丢失最后一次快照后的数据

**AOF（Append Only File）**：
- 记录每条写命令，追加到 `.aof` 文件
- 同步策略：`always`（每条）/ `everysec`（每秒，默认）/ `no`（OS 决定）
- AOF 重写：`BGREWRITEAOF` 压缩文件体积
- 优点：数据更安全（最多丢 1 秒）
- 缺点：文件大、恢复慢

**混合持久化**（Redis 4.0+）：
- AOF 重写时，前半段写 RDB 格式，后半段写增量 AOF
- 兼顾恢复速度和数据安全

**记忆**：**RDB 定时快照（可能丢数据）、AOF 记命令（更安全但文件大）、混合持久化结合两者优点**。

#### Q20：说一下 ElasticSearch 的理解，你会怎么用 ES

**答案**：

**核心概念**：
- **倒排索引**：词项 → 文档 ID 列表，实现全文搜索
- **Index**：类似数据库的表
- **Document**：JSON 文档，类似一行记录
- **Shard**：分片，数据水平拆分（Primary + Replica）
- **Cluster/Node**：集群节点

**使用场景**：
1. **全文搜索**：商品搜索、日志搜索、站内搜索
2. **日志分析**：ELK（Elasticsearch + Logstash + Kibana）
3. **聚合分析**：统计、分组、趋势分析

**与 MySQL 对比**：
- ES 擅长搜索和分析，MySQL 擅长事务和精确查询
- 通常 MySQL 做主存储，ES 做搜索层，数据双写或通过 Canal 同步

**记忆**：**ES 核心是倒排索引；用于全文搜索、日志分析、聚合；通常 MySQL 主存 + ES 搜索层**。

#### Q21：可以说一下 Prometheus 和 Grafana 的使用吗

**答案**：

**Prometheus**（监控系统）：
- **Pull 模型**：主动拉取指标（HTTP `/metrics` 端点）
- **时间序列数据库**：存储带标签的指标数据
- **PromQL**：查询语言，支持聚合、计算、告警规则
- **Alertmanager**：告警管理，支持分组、抑制、静默

**Grafana**（可视化）：
- 连接多种数据源（Prometheus、MySQL、ES 等）
- 丰富的图表：折线图、仪表盘、热力图、表格
- Dashboard 模板、变量、告警可视化

**典型架构**：应用暴露 `/metrics` → Prometheus 定时拉取 → Grafana 可视化 + Alertmanager 告警

**记忆**：**Prometheus 拉模式采集指标 + PromQL 查询 + 告警；Grafana 连数据源做可视化仪表盘**。

#### Q22：Prometheus 有两种获取数据的方式，你觉得这两种方式的异同点，在公司里用推还是拉

**答案**：

**Pull（拉取，Prometheus 原生）**：
- Prometheus 主动访问目标的 `/metrics` 端点
- 优点：服务发现简单、便于调试（直接 curl）、Prometheus 控制采集频率
- 缺点：目标在 NAT 后面或短生命周期任务（Job）不好拉

**Push（推送，Pushgateway）**：
- 应用主动推送到 Pushgateway，Prometheus 再从 Pushgateway 拉
- 优点：适合短生命周期任务（CronJob、批处理）
- 缺点：Pushgateway 单点、指标可能过期不准确、丢失服务发现优势

**公司选择**：
- 长期运行的服务（微服务、API）→ **Pull**（主流选择）
- 短任务/批处理 → **Push** 到 Pushgateway
- 现代方案：Pull + 服务发现（Kubernetes SD、Consul SD）

**记忆**：**Pull 是主流（Prometheus 主动拉），Push 适合短任务；长服务用 Pull + 服务发现**。

### 其他

#### Q23：说一下 API 网关中的鉴权是怎么做的，展开说一下 JWT

**答案**：

**API 网关鉴权流程**：
1. 客户端携带 Token（通常在 `Authorization: Bearer <token>`）请求 API 网关
2. 网关拦截请求，验证 Token 的签名和有效期
3. 验证通过，提取用户信息，转发给后端服务
4. 验证通过，拒绝并返回 401

**JWT（JSON Web Token）结构**：
```
Header.Payload.Signature
```
- **Header**：`{"alg": "HS256", "typ": "JWT"}`
- **Payload**：用户信息（`sub`, `iat`, `exp` 等 claims）
- **Signature**：`HMACSHA256(base64(header) + "." + base64(payload), secret)`

**JWT 特点**：
- 无状态：服务端不需要存储 Session
- 自包含：用户信息在 Token 里
- 不可篡改：签名保证

**注意**：
- JWT 不能存储敏感信息（Payload 只是 Base64，不是加密）
- 需要配合 HTTPS 防止中间人攻击
- Token 过期后需要 Refresh Token 机制续期

**记忆**：**JWT = Header.Payload.Signature；无状态自包含；网关拦截验证签名+有效期，通过则转发**。
