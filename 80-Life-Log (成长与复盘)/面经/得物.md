# 个人面经

## 08.03 一面

### MySQL

#### Q1：MySQL 的索引的原理

**答案**：

MySQL（InnoDB）索引的底层数据结构是 **B+ 树**。

**B+ 树结构特点**：
- **非叶子节点**：只存储索引键（key），不存储数据，一个节点可以存放多个 key，降低树高
- **叶子节点**：存储完整数据（聚簇索引）或主键值（二级索引），所有叶子节点通过**双向链表**连接
- **树高通常 2-4 层**：一个三层的 B+ 树大约可以存储 2000 万行数据

**索引类型**：
| 类型 | 说明 |
|------|------|
| **聚簇索引（主键索引）** | 叶子节点存整行数据，表数据按主键顺序物理存储 |
| **二级索引（非聚簇索引）** | 叶子节点存主键值，查到主键后需要**回表**查聚簇索引 |
| **覆盖索引** | 查询字段全在索引中，不需要回表 |

**相关**：[MySQL索引原理——一篇文章搞懂 - 掘金](https://juejin.cn/post/6844903671783981069) | [B+树详解 - CSDN](https://blog.csdn.net/qq_21993785/article/details/105246957)

**记忆**：**InnoDB 索引是 B+ 树；非叶子节点只存 key，叶子节点存数据且用双向链表连接；聚簇索引存整行，二级索引存主键需回表**。

---

#### Q2：为什么用 B+ 树？用了索引为什么会快？

**答案**：

**索引为什么快**：
- 没有索引：全表扫描 O(n)，逐行比较
- 有索引：B+ 树查找 O(log n)，三层树高即可覆盖千万级数据，只需 3 次磁盘 IO

**为什么选 B+ 树**（对比其他数据结构）：

| 特性 | B+ 树的优势 |
|------|------------|
| **矮胖树** | 非叶子节点只存 key，一个节点容纳更多 key → 树高更低 → 磁盘 IO 更少 |
| **叶子链表** | 叶子节点双向链表连接，范围查询只需遍历链表，不需要中序遍历 |
| **稳定性** | 所有数据都在叶子节点，查询路径长度一致（都是根到叶），性能稳定 |
| **磁盘友好** | 节点大小通常等于磁盘页（16KB），一次 IO 读取一个节点 |

**相关**：[为什么MySQL用B+树而不是B树？- 知乎](https://zhuanlan.zhihu.com/p/149407171) | [面试官：为什么MySQL用B+树做索引？- 掘金](https://juejin.cn/post/6961600860778160165)

**记忆**：**B+ 树矮胖（非叶子只存 key）→ IO 少；叶子链表 → 范围查询快；查询路径等长 → 性能稳定**。

#### Q3：为什么用 B+ 树而不是 B 树或者二叉树？

**答案**：

核心视角：MySQL 是**磁盘数据库**，索引设计的本质是**减少磁盘 IO 次数**。磁盘 IO 是毫秒级操作，比内存慢 10 万倍，所以索引结构必须围绕"如何用最少的 IO 找到目标数据"来设计。

**为什么不选 B 树？**

B 树的每个节点都存数据（key + value），而 B+ 树只有叶子节点存数据。这个区别带来三个关键劣势：

1. **节点能放的 key 更少 → 树更高 → IO 更多**
   - 磁盘页大小 16KB，假设一个 key+value 占 1KB，B 树每个节点只能放 16 个 key
   - B+ 树非叶子节点只放 key（假设 16 字节），一个节点能放 **1000 个 key**
   - 同样 2000 万数据：B 树需要 4-5 层，B+ 树只需 3 层，差一次 IO 就是毫秒级差距

2. **范围查询必须中序遍历整棵树**
   - 数据库最常见的查询是范围查询（`WHERE age BETWEEN 20 AND 30`、`ORDER BY time LIMIT 100`）
   - B 树做范围查询：从根节点中序遍历，反复回溯父节点，IO 跳跃
   - B+ 树做范围查询：定位到叶子节点后，**沿链表顺序扫描**，磁盘顺序读，极快

3. **查询性能不稳定**
   - B 树可能在任意层命中（根节点、中间节点、叶子），路径长度不等
   - B+ 树**所有查询都走到叶子**，路径等长，性能可预测

**为什么不选二叉树（AVL、红黑树）？**

二叉树每个节点最多 2 个子节点：
- 树高 O(log₂n)，2000 万数据需要 **25 层** → 25 次磁盘 IO（B+ 树只需 3 次）
- 每个节点只存 1 个 key，一次磁盘 IO 读 16KB 却只用了几十字节，**严重浪费磁盘带宽**
- 二叉树适合内存数据结构（如 Go 的 `map` 底层红黑树），但不适合磁盘存储

**为什么不选 Hash？**

- Hash 只支持等值查询（=），**不支持范围查询**（`>`、`<`、`BETWEEN`）、排序（`ORDER BY`）、最左前缀
- Hash 存在哈希冲突，极端情况下退化为 O(n)
- 适用场景有限：只有等值查询的场景（如 Redis、HashMap）

**总结**：

| 考量维度 | B+ 树的优势 |
|----------|------------|
| **磁盘 IO** | 非叶子节点只存 key，节点容量大，树高 3 层覆盖千万数据 |
| **范围查询** | 叶子节点双向链表，顺序扫描，磁盘顺序读 |
| **查询稳定性** | 所有查询都到叶子，路径等长，性能可预测 |
| **空间利用** | 非叶子节点不存数据，一个节点容纳更多 key |

**通俗理解**：

先记住一句话：**MySQL 用 B+ 树，是因为它要尽量少读磁盘。树越矮，查得越快。**

**红黑树**：一个节点只放一个数字，只有两个分支。一亿数据要走 25+ 层，每层一次磁盘 IO → 太慢。

**B 树**：一个节点放很多数字，树变矮了。但每个节点都存了完整数据（id + name + age...），一个 16KB 的磁盘页只能放 100 个节点。

**B+ 树**：中间节点只放"路牌"（key），不放数据。同样 16KB 能放 1000 个 key。三层就能管 **10 亿数据**（1000×1000×1000）。

```
B+ 树结构：

         [50]              ← 路牌：50 以下去左边，以上去右边
        /    \
   [10 20]  [50 80]        ← 路牌：只负责导航
   /  |  \   /  |  \
  ↓   ↓   ↓  ↓   ↓   ↓
 10  20  50  50  80  ...    ← 叶子节点：存真正数据，且用链表串起来
 张三 李四 王五 ...         ← 100→101→102→...→200 范围查询直接顺序扫
```

就像去图书馆：目录只写章节名字（路牌），不写书的内容。目录很薄，翻几下就找到了。最后一层按顺序排好，范围查找直接往后翻。

**记忆**：**B+ 树非叶子只存 key → 节点密树矮 IO 少；叶子链表 → 范围查询顺序读；所有查询到叶子 → 性能稳定。三个字：矮、快、稳**。

#### Q4：ACID 讲一下

**答案**：

| 特性 | 含义 | 实现机制 |
|------|------|---------|
| **A（Atomicity）原子性** | 事务是最小执行单元，要么全做，要么全不做 | Undo Log（回滚日志） |
| **C（Consistency）一致性** | 事务前后数据满足完整性约束（如余额不能为负） | 由 AID 共同保证 |
| **I（Isolation）隔离性** | 并发事务之间互不干扰 | MVCC + 锁 |
| **D（Durability）持久性** | 事务提交后数据永久保存 | Redo Log（重做日志） |

**隔离级别**（从低到高）：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---------|------|-----------|------|
| READ UNCOMMITTED | 有 | 有 | 有 |
| READ COMMITTED | 无 | 有 | 有 |
| **REPEATABLE READ（默认）** | 无 | 无 | MVCC+间隙锁解决 |
| SERIALIZABLE | 无 | 无 | 无 |

**相关**：[MySQL事务ACID实现原理 - 掘金](https://juejin.cn/post/7555438283062001714)| [MySQL的四种事务隔离级别 - 腾讯云](https://cloud.tencent.com/developer/article/1534837)

**记忆**：**A 原子靠 Undo Log，C 一致靠 AID 共同保证，I 隔离靠 MVCC+锁，D 持久靠 Redo Log**。

#### Q5：ACID 是怎么实现的？

**答案**：

**原子性 — Undo Log**：
- 事务修改数据前，先将旧值写入 Undo Log
- 事务回滚时，从 Undo Log 恢复旧值
- Undo Log 还用于 MVCC 的版本链

**持久性 — Redo Log**：
- 事务修改数据时，先写 Redo Log（WAL，Write-Ahead Logging），再写数据页
- 即使数据页还没刷盘，数据库崩溃后也能通过 Redo Log 恢复（crash recovery）
- Redo Log 是顺序写，比随机写数据页快得多

**隔离性 — MVCC + 锁**：
- 读操作通过 MVCC 的快照读，不加锁，不阻塞写
- 写操作通过行锁（Record Lock）、间隙锁（Gap Lock）、临键锁（Next-Key Lock）保证互斥

**一致性**：
- 由原子性、隔离性、持久性共同保证
- 应用层也需要保证（如业务校验、约束检查）

**相关**：[MySQL中ACID的实现原理 - 知乎](https://zhuanlan.zhihu.com/p/96944674) | [详解MySQL中的Redo Log和Undo Log - 掘金](https://juejin.cn/post/6844903696202367502)

**记忆**：**Undo Log 回滚保原子，Redo Log 先写保持久，MVCC+锁保隔离，三者共同保一致**。

#### Q6：展开讲一下 MVCC

**答案**：

MVCC（Multi-Version Concurrency Control，多版本并发控制）实现**读写不阻塞**。

**核心组件**：

1. **隐藏字段**（每行数据都有）：
   - `DB_TRX_ID`：最后修改该行的事务 ID
   - `DB_ROLL_PTR`：回滚指针，指向 Undo Log 中该行的上一个版本

2. **Undo Log 版本链**：
   ```
   当前行 [TRX_ID=300, data="new"] → [TRX_ID=200, data="old"] → [TRX_ID=100, data="older"] → NULL
   ```
   每次修改都会把旧版本通过 `ROLL_PTR` 串成链表

3. **Read View（读视图）**：
   事务在做快照读时生成，包含：
   - `m_ids`：生成 Read View 时所有活跃（未提交）事务 ID 列表
   - `min_trx_id`：活跃事务中最小的 ID
   - `max_trx_id`：下一个要分配的事务 ID
   - `creator_trx_id`：创建该 Read View 的事务 ID

**可见性判断**：遍历版本链，对每个版本的 `DB_TRX_ID` 判断：
1. `DB_TRX_ID == creator_trx_id` → 自己修改的，可见
2. `DB_TRX_ID < min_trx_id` → 在 Read View 生成前已提交，可见
3. `DB_TRX_ID >= max_trx_id` → 在 Read View 生成后才开始，不可见
4. `min_trx_id ≤ DB_TRX_ID < max_trx_id` → 看是否在 `m_ids` 中：在则未提交不可见，不在则已提交可见

**RC vs RR 的区别**：
- **READ COMMITTED**：每次 SELECT 都生成新的 Read View → 能读到其他事务已提交的修改
- **REPEATABLE READ**：只在事务第一次 SELECT 时生成 Read View，后续复用 → 读到的始终是同一个快照

**相关**：[MySQL MVCC机制详解 - 掘金](https://juejin.cn/post/6844903778606669838) | [理解MVCC - 知乎](https://zhuanlan.zhihu.com/p/66823815)

**记忆**：**MVCC = Undo Log 版本链 + Read View；遍历版本链用 Read View 判断可见性；RC 每次生成新 Read View，RR 只在首次 SELECT 生成**。

#### Q7：事务里读出数据加一再写回去，会有什么问题？（MVCC 快照读下的更新丢失）

**答案**：

这是一个经典的**丢失更新（Lost Update）** 问题。

场景：
```
事务A: SELECT qty FROM products WHERE id=1;  -- 快照读，qty=100
事务B: SELECT qty FROM products WHERE id=1;  -- 快照读，qty=100
事务A: UPDATE products SET qty=101 WHERE id=1;  -- 提交
事务B: UPDATE products SET qty=101 WHERE id=1;  -- 提交，期望是 102，实际是 101
```

**根本原因**：MVCC 的快照读（SELECT）不加锁，两个事务都读到旧值，各自加一后写回，后写的覆盖先写的。

注意：这不是 MVCC 的 bug，而是**快照读 + 手动更新**的错误用法。MVCC 保证了读一致性，但不保证"读-改-写"这种组合操作的原子性。

**相关**：[MySQL丢失更新问题 - 掘金](https://juejin.cn/post/6844903986354585608) | [MySQL的锁机制详解 - 知乎](https://zhuanlan.zhihu.com/p/149928382)

**记忆**：**快照读不加锁，两个事务都读到旧值，各自+1写回导致丢失更新；本质是读-改-写不是原子操作**。

#### Q8：如果要实现上面说的功能（读出数量加一再写回），该怎么做？

**答案**：

**方案1：SELECT FOR UPDATE（当前读 + 排他锁）**
```sql
BEGIN;
SELECT qty FROM products WHERE id=1 FOR UPDATE;  -- 加 X 锁，其他事务读写都阻塞
UPDATE products SET qty = qty + 1 WHERE id=1;
COMMIT;
```
其他事务在该事务提交前会被阻塞，保证串行执行。

**方案2：直接用 SQL 原子操作**
```sql
UPDATE products SET qty = qty + 1 WHERE id=1;  -- 数据库内部保证原子性
```
不需要先读再写，一条 SQL 搞定，最简洁。

**方案3：乐观锁（CAS）**
```sql
-- 表中加 version 字段
SELECT qty, version FROM products WHERE id=1;  -- 读到 qty=100, version=5
UPDATE products SET qty=101, version=6 WHERE id=1 AND version=5;  -- 版本匹配才更新
-- 如果 affected rows=0，说明被别人改了，重试
```

**面试官纠正的关键点**：延迟双删应该在**更新完数据库之后再删缓存**，而不是之前。之前的思路是错误的——先删缓存会增大数据不一致的窗口期。

**相关**：[MySQL中SELECT FOR UPDATE的使用 - 掘金](https://juejin.cn/post/6844903752367530056) | [乐观锁与悲观锁 - 知乎](https://zhuanlan.zhihu.com/p/59879887)

**记忆**：**SELECT FOR UPDATE 当前读加锁；或直接 UPDATE qty=qty+1 原子操作；或乐观锁 CAS 版本号**。

### Redis

#### Q9：缓存击穿、穿透、雪崩的成因和解决方案

**答案**：

| 问题 | 成因 | 解决方案 |
|------|------|---------|
| **缓存穿透** | 请求的数据**缓存和数据库都不存在**，每次请求都打到 DB | 1. 缓存空值（设短 TTL）<br>2. 布隆过滤器拦截不存在的 key<br>3. 参数校验拦截非法请求 |
| **缓存击穿** | 某个**热点 key 过期**，大量并发请求同时打到 DB | 1. 热点数据不设过期，后台异步更新<br>2. 互斥锁（SETNX）：只让一个请求查 DB 并回填缓存<br>3. 逻辑过期：缓存中存过期时间，发现过期时异步更新 |
| **缓存雪崩** | **大量 key 同时过期**或 Redis 宕机，请求全部打到 DB | 1. 过期时间加随机值，避免同时失效<br>2. 多级缓存（L1 本地 + L2 Redis）<br>3. 限流降级，保护数据库<br>4. Redis 高可用（哨兵/集群） |

**相关**：[缓存穿透、击穿、雪崩区别与解决方案 - 掘金](https://juejin.cn/post/6844903970668838920) | [Redis缓存三大问题详解 - 知乎](https://zhuanlan.zhihu.com/p/152654892)

**记忆**：**穿透：数据不存在，缓存空值+布隆过滤器；击穿：热点 key 过期，互斥锁+不过期；雪崩：大量 key 同时过期，随机 TTL+多级缓存**。

---

#### Q10：击穿和雪崩的本质区别是什么？

**答案**：

- **击穿**：**单个热点 key** 过期，大量请求集中打到 DB 的**同一行数据**
- **雪崩**：**大量 key 同时过期**（或 Redis 整体不可用），大量请求分散打到 DB 的**多张表/多行数据**

本质区别：
- 击穿是**点**的问题（一个 key），解决方向是保护单个热点
- 雪崩是**面**的问题（一批 key 或整个缓存层），解决方向是分散过期时间 + 提升缓存层可用性

**记忆**：**击穿是一个热点 key 的点问题；雪崩是一批 key 的面问题**。

#### Q11：缓存和 DB 的数据一致性怎么保证？

**答案**：

**方案对比**：

| 方案 | 流程 | 优点 | 缺点 |
|------|------|------|------|
| **先更新 DB，再删缓存（推荐）** | 更新 DB → 删缓存 | 一致性强，实现简单 | 极端情况下仍有短暂不一致 |
| **先删缓存，再更新 DB** | 删缓存 → 更新 DB | - | 不一致窗口大：删后有请求读到旧值并回填 |
| **延迟双删** | 删缓存 → 更新 DB → 延迟再删缓存 | 解决上面方案的问题 | 延迟时间难精确控制 |
| **Canal 监听 binlog** | DB 变更 → binlog → Canal → 更新缓存 | 业务代码无侵入，最终一致 | 架构复杂，依赖中间件 |

**最简方案：先更新 DB，再删缓存**（Cache Aside Pattern）：
1. 读：先读缓存，miss 则读 DB 并回填缓存
2. 写：先更新 DB，再删缓存

为什么不是"更新缓存"而是"删缓存"：避免并发写时缓存和 DB 的值顺序不一致。

**相关**：[缓存与数据库一致性解决方案 - 掘金](https://juejin.cn/post/6844904031460605965) | [Cache Aside Pattern - 知乎](https://zhuanlan.zhihu.com/p/59459836)

**记忆**：**先更新 DB 再删缓存（Cache Aside）；不更新缓存而是删缓存避免顺序不一致；强一致用 Canal 监听 binlog**。

#### Q12：延迟双删再描述一下 / 为什么不是在更新完数据库之后再删？

**答案**：

**面试官纠正的核心点**：先删缓存再更新 DB 是错误的，正确的做法是**先更新 DB 再删缓存**。

**错误的先删缓存再更新 DB 的问题**：
```
1. 事务A 删缓存（旧值删了）
2. 事务B 读请求 → 缓存 miss → 读 DB（旧值）→ 回填缓存（旧值）
3. 事务A 更新 DB（新值）
结果：DB 是新值，缓存是旧值，不一致
```

**正确的先更新 DB 再删缓存**：
```
1. 事务A 更新 DB（新值）
2. 事务A 删缓存
结果：即使删缓存前有请求读到旧值，下次读也会从 DB 拿到新值
```

**延迟双删**（如果仍想用先删缓存方案）：删缓存 → 更新 DB → **延迟 N 毫秒** → 再删缓存。第二次删是为了清理在第一步和第二步之间被其他请求回填的旧缓存。

但延迟时间难以精确控制，实际工程中**先更新 DB 再删缓存**更简单可靠。

**记忆**：**先更新 DB 再删缓存是最简方案；先删缓存会增大不一致窗口；延迟双删的第二次删是为了清理并发回填的旧缓存**。

#### Q14：map 并发安全吗？想要并发安全要怎么弄？

**答案**：

**map 不是并发安全的**，Go 的 map 检测到并发读写会直接 `panic: concurrent map read and map write`。

**方案1：sync.RWMutex**
```go
var mu sync.RWMutex
var m = make(map[string]int)

// 读
mu.RLock()
v := m[key]
mu.RUnlock()

// 写
mu.Lock()
m[key] = value
mu.Unlock()
```
适用场景：通用方案，读多写少时 RWMutex 比 Mutex 效率高。

**方案2：sync.Map**
```go
var sm sync.Map
sm.Store(key, value)
v, ok := sm.Load(key)
```
适用场景：读多写少、key 集合相对稳定。内部用 read+dirty 双 map 实现无锁读。

**面试补充**：还可以说一下 `sync.Map` 的原理（read map 无锁读 + dirty map 写入 + promotion 提升机制），体现深度。

**相关**：[Go sync.Map原理详解 - 掘金](https://juejin.cn/post/6844904063131869198) | [Go Map并发安全 - 知乎](https://zhuanlan.zhihu.com/p/373373512)

**记忆**：**map 并发读写会 panic；方案：RWMutex（通用）或 sync.Map（读多写少）**。

#### Q2：TCP 三次握手，四次挥手的过程

**答案**：

**三次握手（建立连接）**：
1. 客户端 → 服务端：`SYN=1, seq=x`（我要连接）
2. 服务端 → 客户端：`SYN=1, ACK=1, seq=y, ack=x+1`（收到，我也确认）
3. 客户端 → 服务端：`ACK=1, seq=x+1, ack=y+1`（收到，连接建立）

**四次挥手（关闭连接）**：
1. 客户端 → 服务端：`FIN=1, seq=u`（我要关了）
2. 服务端 → 客户端：`ACK=1, ack=u+1`（收到，但我还有数据没发完）
3. 服务端 → 客户端：`FIN=1, seq=w`（我也没数据了，可以关了）
4. 客户端 → 服务端：`ACK=1, ack=w+1`（收到，等 2MSL 后关闭）

为什么握手三次挥手四次：握手时 SYN+ACK 可以合并；挥手时服务端可能还有数据要发，ACK 和 FIN 分开发送。

**记忆**：**握手三次：SYN → SYN+ACK → ACK；挥手四次：FIN → ACK → FIN → ACK；挥手多一次因为服务端要等数据发完**。

---

#### Q3：TCP 释放连接为什么要等待 2MSL 时间

**答案**：

MSL（Maximum Segment Lifetime）是报文最大生存时间，2MSL = 2 × MSL（通常 60s）。

两个原因：
1. **保证最后一个 ACK 到达**：如果服务端没收到最后的 ACK，会重发 FIN。等待 2MSL 确保如果 ACK 丢失，客户端能收到重发的 FIN 并重新发送 ACK
2. **让旧连接的报文消亡**：防止上一次连接的延迟报文被新连接误收。等待 2MSL 确保本次连接的所有报文在网络中消失

**记忆**：**等 2MSL 两个目的：一是 ACK 丢了能补发，二是让旧报文在网络中消亡，防止影响新连接**。

---

#### Q4：TCP 如何保证它的数据的顺序性

**答案**：

1. **序列号（Sequence Number）**：每个字节都有编号，接收端按序号重组
2. **确认应答（ACK）**：接收端告诉发送端"我收到了多少号之前的"，`ack=N` 表示 N 之前的数据都收到了
3. **超时重传**：发送端启动定时器，超时未收到 ACK 则重传
4. **滑动窗口**：接收端通告窗口大小，发送端只发送窗口内的数据，窗口随 ACK 滑动
5. **接收端缓冲区**：乱序到达的数据先缓存，等齐了再按序交付给应用层

**记忆**：**序列号排序 + ACK 确认 + 超时重传 + 滑动窗口流控 + 接收端缓存重组**。

---

#### Q5：TCP 进行拥塞控制的手段有哪些

**答案**：

四种经典算法：

| 算法 | 阶段 | 作用 |
|------|------|------|
| 慢启动（Slow Start） | 连接初期 | cwnd 从 1 开始指数增长，探测可用带宽 |
| 拥塞避免（Congestion Avoidance） | cwnd ≥ ssthresh | cwnd 线性增长，谨慎探测 |
| 快重传（Fast Retransmit） | 收到 3 个重复 ACK | 立即重传丢失报文，不等超时 |
| 快恢复（Fast Recovery） | 快重传之后 | ssthresh = cwnd/2，cwnd = ssthresh，进入拥塞避免 |

整体流程：慢启动指数增长 → 达到 ssthresh 切换拥塞避免线性增长 → 丢包时 ssthresh 减半，cwnd 重置（或快恢复）。

**记忆**：**慢启动指数涨，拥塞避免线性涨；3 个重复 ACK 触发快重传+快恢复；超时丢包 cwnd 回 1 重新慢启动**。

### Golang

#### Q7：Golang 的 GMP 调度 / 说下 GMP 的整个过程

**答案**：

- **G（Goroutine）**：协程，包含栈、PC、状态等
- **M（Machine）**：系统线程，执行 G 的实体
- **P（Processor）**：逻辑处理器，持有本地运行队列，数量默认等于 CPU 核数（`GOMAXPROCS`）

调度流程：
1. P 持有一个本地队列（最多 256 个 G），M 必须绑定 P 才能执行 G
2. M 从 P 的本地队列取 G 执行
3. 本地队列空了，从**全局队列**取
4. 全局队列也空了，触发 **work stealing**：从其他 P 的本地队列偷一半 G
5. G 执行系统调用阻塞时，M 与 P 解绑，P 去找或创建新的 M 继续执行其他 G
6. G 执行完毕，回到空闲状态，M 尝试获取新的 G

**记忆**：**G 是协程，M 是线程，P 是逻辑处理器；P 持有本地队列，M 绑 P 执行 G；队列空了偷其他 P 的 G**。

---

#### Q8：M 发生系统调用了 G 和 P 会怎么样

**答案**：

G 进入系统调用（如文件 IO、网络阻塞调用），M 会阻塞在内核态。此时：

1. **P 与该 M 解绑**（hand off）：P 不能闲着，它会去找一个空闲的 M（或新建一个 M）来继续执行本地队列中的其他 G
2. **G 绑定在原 M 上**：G 跟着阻塞的 M 一起等待系统调用返回
3. 原 M 完成系统调用后，G 变为可运行状态，但此时 M 可能已经没有 P 了

**记忆**：**M 阻塞时 P 会 hand off 找新 M 继续干活；G 跟着原 M 等；P 不会闲置**。

---

#### Q9：M 系统调用结束以后会怎么样

**答案**：

M 从系统调用返回后：
1. M 尝试获取一个空闲的 P：优先获取之前 hand off 的 P
2. **有 P**：M 绑定 P，把 G 放入 P 的本地队列，继续调度
3. **没有空闲 P**：G 被放入**全局队列**，M 进入休眠状态（放入空闲 M 队列），等待后续有 P 需要时再唤醒

**记忆**：**调用结束 M 找 P；找到 P 就继续绑上干活；找不到 P 则 G 放全局队列，M 休眠**。

#### Q11：介绍一下使用 JWT 进行鉴权的过程

**答案**：

JWT（JSON Web Token）由三部分组成：`Header.Payload.Signature`

**登录流程**：
1. 用户提交账号密码
2. 服务端验证通过，生成 JWT（Header + Payload + 用密钥签名），返回给客户端

### Gin 框架

#### Q12：说一下 Gin 的拦截器的原理

**答案**：

Gin 没有传统意义的"拦截器"，用的是 **中间件（Middleware）** 机制。

本质：中间件就是一个 `func(c *gin.Context)` 函数，通过 `c.Next()` 将控制权交给下一个 handler。

```go
func AuthMiddleware() gin.HandlerFunc {
    return func(c *gin.Context) {
        token := c.GetHeader("Authorization")
        if token == "" {
            c.JSON(401, gin.H{"error": "unauthorized"})
            c.Abort() // 终止后续 handler
            return
        }
        c.Next() // 执行后续 handler
        // c.Next() 之后的代码在所有后续 handler 执行完后才执行（洋葱模型）
    }
}
```

执行顺序：中间件1 前半段 → 中间件2 前半段 → Handler → 中间件2 后半段 → 中间件1 后半段（**洋葱模型**）

`c.Abort()` 终止调用链，后续 handler 不会执行。

**记忆**：**Gin 中间件本质是 handler 函数链；c.Next() 传递，c.Abort() 终止；洋葱模型：进→执行→出**。

---

#### Q13：说一下 Gin 的路由怎么实现的 / Gin 的路由使用的数据结构（字典树）

**答案**：

Gin 使用 **基数树（Radix Tree / 压缩前缀树）** 实现路由，底层库是 `httprouter`。

核心特点：
- 路由按 `/` 分割成节点，公共前缀合并压缩
- 支持参数路由：`/user/:id`、通配符：`/files/*filepath`
- 路由查找 O(k)，k 是 URL 路径长度，与注册的路由数量无关

示例：注册 `/user/list`、`/user/detail`、`/order/list`，树结构：
```
/
├── user/
│   ├── list
│   └── detail
└── order/
    └── list
```

同一 HTTP 方法（GET/POST 等）共享一棵树。查找时从根节点沿路径匹配，遇到参数节点（`:id`）则提取参数值。

**记忆**：**Gin 路由用基数树（压缩前缀树），公共前缀合并，查找 O(k)；支持参数 `:id` 和通配符 `*`**。

#### Q2：项目里有哪些认为的难点 / 为什么用 WebSocket，除了 WebSocket 还有哪些方式可以实现？

**答案**：

**难点**：（按个人项目回答，参考 Q10）

**为什么用 WebSocket**：
- 全双工通信，服务端可主动推送
- 建立连接后通信开销小（无 HTTP 头部重复开销）
- 适合即时通讯、实时通知等场景

**其他实现方式**：

| 方式 | 原理 | 优缺点 |
|------|------|--------|
| **长轮询（Long Polling）** | 客户端发请求，服务端 hold 住直到有数据才返回 | 兼容性好，但延迟高、资源浪费 |
| **短轮询** | 客户端定时发请求查询 | 实现简单，但大量无效请求 |
| **SSE（Server-Sent Events）** | 服务端单向推送，基于 HTTP | 简单轻量，但只能服务端→客户端 |
| **HTTP/2 Server Push** | 服务端主动推送资源 | 主要用于静态资源，不适合业务消息 |

**记忆**：**WebSocket 全双工实时通信；替代方案：长轮询 hold 住连接、短轮询定时查、SSE 单向推、HTTP/2 推资源**。

### Go 并发

#### Q4：为什么有了 Sync.Mutex 还需要 Sync.RWMutex？

**答案**：

`sync.Mutex` 是互斥锁，读写都互斥。`sync.RWMutex` 是读写锁，**读读不互斥，读写互斥，写写互斥**。

场景：读多写少时，Mutex 会让所有读操作串行化。RWMutex 允许多个 goroutine 并发读。

```go
var rw sync.RWMutex

rw.RLock()   // 读操作
data := cache[key]
rw.RUnlock()

rw.Lock()    // 写操作
cache[key] = newValue
rw.Unlock()
```

注意：RWMutex 有额外开销（维护读者计数），读写比例接近 1:1 时可能不如 Mutex。

**记忆**：**RWMutex 读读不互斥，读多写少时比 Mutex 高效；读写比接近时 Mutex 可能更优**。

---

#### Q5：修改 Int64 类型数据需要怎么操作？写时读怎么操作？没加锁读会有什么问题？

**答案**：

**修改 Int64**：
```go
// 方法1：互斥锁
var mu sync.Mutex
mu.Lock()
data = newValue
mu.Unlock()

// 方法2：原子操作（推荐，性能更好）
atomic.StoreInt64(&data, newValue)
```

**写时读**：
- 用 `sync.RWMutex`：写加 `Lock()`，读加 `RLock()`
- 或用 `atomic.LoadInt64(&data)` 原子读

**没加锁读的问题**：
- **数据竞争（Data Race）**：读到写了一半的值（Int64 在 32 位平台上可能不是原子操作）
- **可见性问题**：CPU 缓存/编译器优化导致读到旧值
- **未定义行为**：Go 的 race detector 会报警，实际运行可能偶现诡异 bug

**记忆**：**Int64 修改用 atomic 或锁；读写并发要加锁或用原子操作；不加锁会有数据竞争和可见性问题**。

#### Q6：Sync.Map 是如何保证并发安全的？

**答案**：

`sync.Map` 内部维护两个 map：
- **read（只读 map）**：支持无锁并发读（atomic 操作）
- **dirty（脏 map）**：写入时先写 dirty

核心机制：
1. **读操作**：先从 read 中无锁查找，找不到再加锁查 dirty
2. **写操作**：如果 key 已在 read 中，用 CAS 更新；否则加锁写入 dirty
3. **提升（promotion）**：dirty 积累到一定量时，将 dirty 提升为新的 read，dirty 清空
4. **miss 计数**：read 查不到时 miss++，达到阈值触发提升

适用场景：**读多写少、key 集合相对稳定**。写多的场景不如 `map + RWMutex`。

**记忆**：**sync.Map 双 map（read + dirty）；读无锁从 read 取，写先进 dirty；积累够了 dirty 提升为 read；读多写少才适用**。

### 分布式

#### Q7：有一个订单生成需要保存在当前服务中，同时其他服务也需要知道，该怎么实现？如果其中有一个服务写入失败该怎么办？

**答案**：

**跨服务通知方案**：
1. **消息队列（推荐）**：订单服务写入本地 DB 后发消息到 MQ，其他服务消费。利用事务消息保证本地写入和消息发送的一致性
2. **分布式事务（2PC/TCC）**：强一致性场景，但性能差、实现复杂
3. **最终一致性（Saga）**：每个服务执行本地事务，失败时触发补偿操作

**写入失败处理**：
- **消息队列重试**：消费失败自动重试（注意幂等）
- **死信队列**：多次重试仍失败的消息进入死信队列，人工介入
- **本地事务消息表**：订单写入和消息记录在同一个本地事务中，后台任务轮询发送未确认的消息

**关键**：消费者必须**幂等**（用唯一 ID 去重），防止重复消费。

**记忆**：**跨服务用 MQ 异步通知 + 本地事务消息表保证可靠投递；失败重试 + 死信队列兜底；消费者必须幂等**。

#### Q9：了解什么是 Redis 的大 Key 吗？大 Key 有什么问题？

**答案**：

**大 Key 定义**：
- String 类型：value > 10KB
- Hash/List/Set/ZSet 类型：元素数量 > 10000 个，或总大小 > 10MB

**大 Key 的问题**：
1. **阻塞**：DEL 大 Key 会阻塞 Redis（O(n) 操作），导致其他请求超时
2. **内存不均**：集群模式下数据倾斜，某个节点内存暴增
3. **网络带宽**：大 Key 传输占用大量带宽
4. **主从同步延迟**：大 Key 序列化传输耗时

**解决方案**：
- 拆分：Hash 按 field 分桶、List 分段
- 异步删除：Redis 4.0+ 用 `UNLINK`（异步 DEL）
- 压缩：对 String value 压缩
- 监控：用 `redis-cli --bigkeys` 扫描

**记忆**：**大 Key：String >10KB 或集合 >1 万元素；问题：阻塞删除、内存倾斜、网络瓶颈；拆分 + UNLINK 异步删除**。

#### Q10：数据库主键索引和唯一索引有什么区别？

**答案**：

| | 主键索引（Primary Key） | 唯一索引（Unique Index） |
|---|---|---|
| NULL | 不允许 NULL | 允许 NULL（MySQL 中可多个 NULL） |
| 数量 | 每表只能有一个 | 可以有多个 |
| 聚簇 | InnoDB 主键索引是聚簇索引（叶子节点存整行数据） | 非聚簇索引（叶子节点存主键值） |
| 用途 | 行的唯一标识 | 业务唯一性约束 |
| 自增 | 常用自增 ID 保证有序插入 | 不保证有序 |

InnoDB 中：主键索引 = 聚簇索引，其他索引都是二级索引（先查二级索引拿到主键，再回表查聚簇索引）。

**记忆**：**主键唯一且非空，每表一个，是聚簇索引存整行；唯一索引允许多个 NULL，是非聚簇索引存主键值**。

#### Q11：如果要对表设计索引，需要考虑什么？

**答案**：

1. **选择性（区分度）**：列的唯一值占比越高，索引效果越好。性别（低选择性）不适合单独建索引
2. **查询模式**：索引应匹配 WHERE、JOIN、ORDER BY 的常用字段
3. **联合索引顺序**：遵循**最左前缀原则**，高选择性字段放前面
4. **覆盖索引**：查询字段都在索引中，避免回表
5. **索引数量**：不是越多越好，写操作需要维护索引，影响写性能
6. **索引下推（ICP）**：MySQL 5.6+ 在存储引擎层过滤，减少回表
7. **避免索引失效**：函数操作列、隐式类型转换、LIKE '%xx'、OR 条件等会导致索引失效

**记忆**：**索引设计五要素：选择性高、匹配查询、最左前缀、覆盖索引、数量适度；注意避免索引失效的写法**。

### 安全

#### Q12：了解什么是 SQL 注入吗？该怎么防范？

**答案**：

**SQL 注入**：用户输入被拼接进 SQL 语句，改变原意执行恶意 SQL。

```sql
-- 正常查询
SELECT * FROM users WHERE name = 'alice';

-- 注入：输入 name = ' OR '1'='1
SELECT * FROM users WHERE name = '' OR '1'='1';  -- 返回所有用户
```

**防范**：
1. **参数化查询（预编译）**：SQL 和参数分离，数据库不会把参数当 SQL 执行
   ```go
   db.Query("SELECT * FROM users WHERE name = ?", userName)
   ```
2. **ORM 框架**：GORM 等 ORM 默认使用参数化查询
3. **输入验证**：白名单校验、过滤特殊字符
4. **最小权限**：数据库账号只给必要权限，禁止 DROP/ALTER
5. **WAF**：Web 应用防火墙拦截可疑请求

**核心**：永远不要拼接用户输入到 SQL 中，用参数化查询。

**记忆**：**SQL 注入：用户输入拼进 SQL 改变语义；防范核心：参数化查询（预编译），永远不拼接用户输入**。

#### Q1：LRU 的底层结构是什么？更新 LRU 里已有的数据会涉及哪些动作？

**答案**：

**底层结构**：**哈希表 + 双向链表**
- 哈希表（`map[key]*Node`）：O(1) 查找
- 双向链表（`list.List`）：维护访问顺序，最近访问的在头部，最久未访问的在尾部

**更新已有数据的动作**：
1. 哈希表 O(1) 找到节点
2. 将该节点从链表当前位置**摘除**
3. 将节点**插入链表头部**（标记为最近使用）
4. 更新 value

**淘汰策略**：容量满时，删除链表尾部节点（最久未访问），同时从哈希表中删除对应 key。

**记忆**：**LRU = 哈希表 + 双向链表；哈希表 O(1) 查找，链表维护访问顺序；更新时摘除节点移到头部；满时淘汰尾部**。

#### Q2：Go 里 slice 的底层结构是什么？make([]int, 2) 和 make([]int, 3, 5) 有什么区别？

**答案**：

|---|---|---|
| len | 2 | 3 |

#### Q3：map 并发安全吗？多协程环境下使用 map 怎么写？

**答案**：

**map 不是并发安全的**。Go 的 map 检测到并发读写会直接 panic：`fatal error: concurrent map read and map write`。

**多协程方案**：

```go
// 方案1：sync.RWMutex
var mu sync.RWMutex
var m = make(map[string]int)

mu.RLock()
v := m[key]
mu.RUnlock()

mu.Lock()
m[key] = newValue
mu.Unlock()

// 方案2：sync.Map（读多写少场景）
var sm sync.Map
sm.Store(key, value)
v, ok := sm.Load(key)
```

**选择**：读写比高用 `sync.Map`；写多或需要遍历用 `map + RWMutex`。

**记忆**：**map 不并发安全，并发读写会 panic；用 RWMutex 或 sync.Map；写多用 RWMutex，读多用 sync.Map**。

#### Q4：Go 的协程为什么能轻松支持百万高并发？

**答案**：

1. **极小的栈空间**：goroutine 初始栈仅 **2-8KB**（线程默认 1-8MB），百万 goroutine 只需 2-8GB 内存
2. **用户态调度**：Go runtime 的 GMP 模型在用户态调度，goroutine 切换不需要陷入内核，切换成本仅需**保存/恢复几个寄存器**（约 100ns，线程切换约 1-10μs）
3. **非阻塞 IO**：Go 的网络库基于 epoll/kqueue，goroutine 阻塞在网络 IO 时，底层是非阻塞的，M（线程）不会被真正阻塞
4. **动态栈增长**：goroutine 栈按需增长（最大 1GB），不需要预先分配大栈
5. **GMP 调度高效**：work stealing 保证负载均衡，系统调用时 P hand off 不浪费计算资源

**记忆**：**goroutine 高并发四要素：栈小（2-8KB）、切换快（用户态 100ns）、IO 非阻塞、动态增长不浪费内存**。

#### Q5：主协程里有多个子协程一起处理任务，怎么实现优雅退出？

**答案**：

```go
var wg sync.WaitGroup

for i := 0; i < n; i++ {
    wg.Add(1)
    go func(id int) {
        defer wg.Done()
        // 执行任务
    }(i)
}

wg.Wait() // 等待所有子协程完成
```

**带信号通知的优雅退出**（收到信号后通知所有子协程停止）：

```go
ctx, cancel := context.WithCancel(context.Background())

// 监听系统信号
sigCh := make(chan os.Signal, 1)
signal.Notify(sigCh, syscall.SIGINT, syscall.SIGTERM)
go func() {
    <-sigCh
    cancel() // 通知所有子协程退出
}()

var wg sync.WaitGroup
for i := 0; i < n; i++ {
    wg.Add(1)
    go func(id int) {
        defer wg.Done()
        for {
            select {
            case <-ctx.Done():
                return // 收到退出信号
            default:
                doWork()
            }
        }
    }(i)
}
wg.Wait()
```

**记忆**：**优雅退出 = WaitGroup 等待所有子协程完成 + context.Cancel 通知停止**。

#### Q6：主协程觉得子协程执行时间太长，希望提前退出，怎么实现？怎么监控 context 的取消或超时消息？

**答案**：

**超时控制**：

```go
// 方式1：WithTimeout（超时自动取消）
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()

// 方式2：WithDeadline（指定截止时间）
ctx, cancel := context.WithDeadline(context.Background(), time.Now().Add(5*time.Second))
defer cancel()
```

**监控 context 取消/超时**：

```go
go func() {
    select {
    case <-ctx.Done():
        err := ctx.Err()
        if err == context.Canceled {
            fmt.Println("被主动取消")
        } else if err == context.DeadlineExceeded {
            fmt.Println("超时了")
        }
        return
    }
}()

// 或在循环中检查
for {
    select {
    case <-ctx.Done():
        return ctx.Err()
    default:
        doWork()
    }
}
```

**记忆**：**WithTimeout 设超时时间，WithDeadline 设截止时间；ctx.Done() 返回 channel 监听取消信号；ctx.Err() 判断是取消还是超时**。

#### Q7：有 1000 个任务，只用 5 个协程执行，怎么实现？

**答案**：

**方案1：带缓冲 channel 作为任务队列（推荐）**

```go
tasks := make(chan int, 1000)
for i := 0; i < 1000; i++ {
    tasks <- i
}
close(tasks)

var wg sync.WaitGroup
for i := 0; i < 5; i++ {
    wg.Add(1)
    go func(workerID int) {
        defer wg.Done()
        for task := range tasks {
            process(task)
        }
    }(i)
}
wg.Wait()
```

**方案2：信号量控制并发数**

```go
sem := make(chan struct{}, 5) // 最多 5 个并发
var wg sync.WaitGroup

for i := 0; i < 1000; i++ {
    wg.Add(1)
    sem <- struct{}{} // 获取令牌，满 5 个则阻塞
    go func(task int) {
        defer func() {
            <-sem // 释放令牌
            wg.Done()
        }()
        process(task)
    }(i)
}
wg.Wait()
```

**记忆**：**Worker Pool 模式：channel 分发任务 + N 个 goroutine 消费；或信号量 channel 控制并发上限**。

#### Q8：Go 里哪些问题可能会导致内存泄露？

**答案**：

1. **goroutine 泄露**（最常见）：
   - goroutine 阻塞在 channel 上无人发送/接收
   - 忘记关闭 channel，goroutine 一直 `range` 等待
   - HTTP 请求未设超时，goroutine 永久阻塞

2. **time.Ticker 泄露**：
   - 忘记调用 `ticker.Stop()`，GC 无法回收

3. **slice 底层数组引用**：
   ```go
   huge := make([]byte, 1<<20)
   small := huge[:10] // small 引用整个 huge 数组，无法被 GC
   // 修复：copy 到新 slice
   ```

4. **map 持有已删除 key 的引用**：Go 的 map 删除 key 后不缩容，内存不释放

5. **闭包引用大对象**：闭包捕获了局部变量，导致大对象无法被 GC

6. **全局缓存未清理**：全局 map/slice 不断增长无淘汰机制

**排查工具**：`go tool pprof`（heap profile）、`runtime.NumGoroutine()` 监控 goroutine 数量。

**记忆**：**内存泄露 Top3：goroutine 泄露（阻塞无人收）、slice 截断引用底层数组、Ticker 忘 Stop；用 pprof 排查**。

#### Q10：I/O 多路复用有几种选择？select、poll、epoll 的区别和优点是什么？

**答案**：

| | select | poll | epoll |
|---|--------|------|-------|
| 数据结构 | fd_set（位图） | pollfd 数组 | 红黑树 + 就绪链表 |
| fd 上限 | 1024 | 无限制 | 无限制 |
| fd 拷贝 | 每次调用都拷贝全量 fd 到内核 | 同 select | `epoll_ctl` 注册一次，后续不拷贝 |
| 就绪检测 | 遍历所有 fd | 遍历所有 fd | 回调机制，只返回就绪 fd |
| 时间复杂度 | O(n) | O(n) | O(1) 获取就绪事件 |
| 触发模式 | 水平触发（LT） | 水平触发（LT） | 支持 LT 和 ET |

**epoll 三大优势**：
1. **事件驱动**：通过回调将就绪 fd 放入就绪链表，`epoll_wait` 直接返回，不用遍历
2. **fd 注册一次**：`epoll_ctl(ADD)` 后内核维护，不用每次重复拷贝
3. **支持 ET 边沿触发**：减少系统调用次数，高性能场景必备

**适用场景**：少量连接用 select（兼容性好），大量连接少量活跃用 epoll。

**记忆**：**select/poll 每次遍历全部 fd（O(n)），select 有 1024 上限；epoll 红黑树+就绪链表+回调，O(1) 获取就绪 fd，大量连接首选**。

### Redis

#### Q11：Redis 五种数据结构 / ZSet 底层结构

**答案**：

**五种基本数据结构**：

| 类型 | 底层编码 | 用途 |
|------|---------|------|
| **String** | int / embstr / raw | 缓存、计数器、分布式锁 |
| **Hash** | ziplist / hashtable | 对象属性存储 |
| **List** | listpack / quicklist | 消息队列、最新列表 |
| **Set** | intset / hashtable | 去重、交并差集 |
| **ZSet** | listpack / skiplist+hashtable | 排行榜、延迟队列 |

**ZSet 底层结构**：
- **数据量小**（≤128 个元素且每个 value ≤64 字节）：**listpack**（压缩列表）
- **数据量大**：**跳表（skiplist）+ 哈希表**
  - 跳表：维护 score 有序，支持 O(log n) 的范围查询、插入、删除
  - 哈希表：O(1) 查找 member → score

为什么用跳表不用红黑树：跳表实现更简单、范围查询更自然（遍历底层链表即可）、并发友好。

**记忆**：**ZSet 小数据用 listpack，大数据用 skiplist+hashtable；跳表支持 O(log n) 范围查询，比红黑树实现简单且适合并发**。

#### Q12：Redis 的 RDB 和 AOF 持久化机制 / Redis 数据过期和数据淘汰

**答案**：

**持久化机制**：

| | RDB | AOF |
|---|-----|-----|
| 原理 | 定时生成内存快照（二进制） | 追加写命令日志 |
| 触发 | `BGSAVE`/`SAVE` 配置自动触发 | 每条写命令 / 每秒刷盘 / 系统决定 |
| 恢复速度 | 快（直接加载二进制） | 慢（重放所有命令） |
| 数据安全 | 可能丢失最后一次快照后的数据 | 最多丢 1 秒数据（everysec） |
| 文件大小 | 小（压缩的二进制） | 大（文本命令，需 rewrite 压缩） |

Redis 4.0+ 支持 **RDB + AOF 混合持久化**：重写时先写 RDB 格式，增量部分用 AOF 追加。

**数据过期**：
- 惰性删除：访问 key 时检查是否过期
- 定期删除：每 100ms 随机抽样检查，删除已过期的 key

**数据淘汰（内存满时）**：
- `noeviction`：不淘汰，写操作报错（默认）
- `allkeys-lru`：所有 key 中淘汰最近最少使用（推荐）
- `volatile-lru`：只在设置了过期时间的 key 中 LRU 淘汰
- `allkeys-lfu`：所有 key 中淘汰最不经常使用
- `volatile-ttl`：淘汰 TTL 最短的 key

**记忆**：**RDB 快照恢复快但可能丢数据，AOF 安全但文件大；混合持久化兼顾两者；过期用惰性+定期删除；淘汰策略推荐 allkeys-lru**。

### 算法

#### Q13：有 10000 个整数，找到其中最大的 10 个数，用什么数据结构比较好？

**答案**：

**最小堆（大小为 10 的最小堆）** — O(n log k)，k=10

思路：
1. 维护一个大小为 10 的最小堆
2. 遍历 10000 个数：
   - 堆未满，直接插入
   - 堆满了，如果当前数 > 堆顶（堆中最小值），替换堆顶并调整
3. 遍历结束后，堆中就是最大的 10 个数

```go
// Go 标准库没有内置堆，用 container/heap
h := &IntHeap{}
heap.Init(h)
for _, v := range nums {
    if h.Len() < 10 {
        heap.Push(h, v)
    } else if v > (*h)[0] {
        (*h)[0] = v
        heap.Fix(h, 0)
    }
}
```

**为什么用最小堆而不是最大堆**：最小堆的堆顶是堆中最小的，方便和新元素比较淘汰。如果用最大堆，需要先拿到全部 10000 个数再取前 10 大，无法流式处理。

**其他方案**：
- 快速选择（QuickSelect）：平均 O(n)，但需要修改原数组
- 全排序：O(n log n)，浪费

**记忆**：**Top K 问题用大小为 K 的最小堆；堆顶是最小值方便淘汰；O(n log k) 时间 O(k) 空间；流式处理友好**。

#### Q1：Golang 中的锁讲一下

**答案**：

Go 标准库 `sync` 包提供的锁：

| 锁类型 | 说明 | 适用场景 |
|--------|------|---------|
| `sync.Mutex` | 互斥锁，读写都互斥 | 写多、通用场景 |
| `sync.RWMutex` | 读写锁，读读不互斥 | 读多写少 |
| `sync.Once` | 只执行一次 | 单例初始化、配置加载 |
| `sync.WaitGroup` | 等待一组 goroutine 完成 | 并发任务编排 |

- 基于信号量（semaphore）实现
- 自旋 + 队列阻塞：短时间自旋等待（避免上下文切换），长时间挂起到等待队列
- Go 1.9+ 引入**饥饿模式**：等待超过 1ms 的 goroutine 优先获取锁，防止尾延迟

#### Q2：讲一下 Golang 中的 GC / GC 的算法讲一下

**答案**：

**Go GC 基本信息**：
- Go 1.5 起使用**三色标记法 + 混合写屏障**
- 并发 GC：GC 和用户 goroutine 并发执行，不长时间 STW
- GC 触发条件：内存增长到上次 GC 后的一定比例（默认 `GOGC=100`，即内存翻倍时触发）

**三色标记法**：
1. **白色**：未被扫描的对象（GC 结束后仍为白色的被回收）
2. **灰色**：已被扫描，但其引用的对象还未扫描
3. **黑色**：已被扫描，且其引用的对象也已扫描完成

流程：
1. **STW（短暂）**：标记 GC Root（全局变量、goroutine 栈上的变量）
2. **并发标记**：从 GC Root 出发，遍历引用链，白色→灰色→黑色
3. **STW（短暂）**：重新扫描可能被修改的引用（写屏障记录的）
4. **并发清扫**：回收所有仍为白色的对象

**混合写屏障（Hybrid Write Barrier）**：
- Go 1.8 引入，解决并发标记期间指针修改导致的对象丢失问题
- 规则：指针写入时，将新指向的对象标灰，旧指向的对象也标灰
- 同时保证**栈上指针**和**堆上指针**的修改都被追踪

**记忆**：**Go GC 三色标记 + 混合写屏障；白色待回收、灰色待扫描、黑色已扫描；写屏障保证并发标记不丢对象；两次短暂 STW，其余并发**。

#### Q3：冷门题：在 Golang 中如何保证不引用的变量不被垃圾回收

**答案**：

变量不被 GC 回收 = 让 GC 认为它仍然被引用。方法：

1. **保持引用链**：把变量赋值给一个不会被回收的全局变量或长期存活的结构体
   ```go
   var keepAlive interface{} // 全局变量
   func preventGC(obj *MyStruct) {
       keepAlive = obj // 全局引用，GC 不会回收
   }
   ```

2. **`runtime.KeepAlive`**（Go 1.7+）：告诉编译器"这个变量到这里之前不能被回收"
   ```go
   obj := new(MyStruct)
   use(obj)
   runtime.KeepAlive(obj) // obj 在这行之前不会被 GC
   ```

3. **`go:uintpt` 指令**（不推荐，黑魔法）：把指针转成 uintptr，骗过 GC 扫描

4. **切片/数组持有引用**：把指针存入一个长期存活的 slice 中

实际场景：`runtime.KeepAlive` 最常用，典型场景是 CGO 调用时防止 Go 对象在 C 代码使用期间被回收。

**记忆**：**`runtime.KeepAlive(obj)` 保证 obj 在此行之前不被 GC；本质是告诉编译器保持引用链不断**。

###消息队列

#### Q4：讲一下 Kafka

**答案**：

**核心概念**：

| 概念 | 说明 |
|------|------|
| **Broker** | Kafka 服务节点，一个集群有多个 Broker |
| **Topic** | 消息的逻辑分类，一个 Topic 可有多个 Partition |
| **Partition** | Topic 的物理分片，有序、不可变的消息队列 |
| **Producer** | 消息生产者，按 key 哈希决定写入哪个 Partition |
| **Consumer** | 消息消费者，以 Consumer Group 为单位消费 |
| **Consumer Group** | 一个 Group 内的消费者共同消费 Topic，每个 Partition 只分配给组内一个消费者 |
| **Offset** | 消费者在 Partition 中的消费位置，由消费者自己管理 |

**架构特点**：
- **高吞吐**：顺序写磁盘（append-only）+ 零拷贝（sendfile）+ 批量发送
- **持久化**：消息写入磁盘，按配置保留（如 7 天），支持回溯消费
- **分区并行**：多个 Partition 可被多个 Consumer 并行消费
- **副本机制**：每个 Partition 有 Leader + Follower 副本，Leader 负责读写，Follower 同步数据

**消费模型**：
- 同一 Consumer Group 内：**队列模型**（一条消息只被一个消费者消费）
- 不同 Consumer Group 之间：**发布订阅模型**（每个 Group 都收到完整消息）

**生产者写入流程**：
1. Producer 发送消息到 Partition Leader
2. Leader 写入本地日志
3. Follower 从 Leader 拉取同步
4. 所有 ISR（In-Sync Replicas）确认后，消息提交

**记忆**：**Kafka = Broker 集群 + Topic 分 Partition；顺序写磁盘 + 零拷贝高吞吐；同 Group 内队列模型，不同 Group 间发布订阅；ISR 副本保证可靠性**。
