### Go 基础与并发

#### Q1：Go 并发处理你会想到什么结构？

**答案**：

Go 并发原语：

| 原语 | 用途 |
|------|------|
| `sync.Mutex` / `sync.RWMutex` | 互斥锁 / 读写锁 |
| `sync.WaitGroup` | 等待一组 goroutine 完成 |
| `chan` | goroutine 间通信 |
| `select` | 多路复用 channel |
| `context` | 取消信号、超时、传值 |
| `sync.Map` | 并发安全 map |
| `sync.Once` | 只执行一次 |
| `atomic` | 原子操作（无锁） |
| `errgroup` | 带错误收集的 WaitGroup |

**记忆**：**锁（Mutex）、通信（channel）、同步（WaitGroup）、控制（context）、原子（atomic）**。

---

#### Q2：100 个 goroutine 等待它们都执行完

**答案**：

用 `sync.WaitGroup`：

```go
var wg sync.WaitGroup
for i := 0; i < 100; i++ {
    wg.Add(1)
    go func(id int) {
        defer wg.Done()
        // do work
    }(i)
}
wg.Wait() // 阻塞直到计数器归零
```

**记忆**：**WaitGroup — Add 启动前、Done 结束时、Wait 阻塞等待**。

---

#### Q3：不仅等待 100 个 goroutine 执行完，还要加超时机制（最多 3s）

**答案**：

`WaitGroup` + `context.WithTimeout` 组合：

```go
ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
defer cancel()

var wg sync.WaitGroup
for i := 0; i < 100; i++ {
    wg.Add(1)
    go func(id int) {
        defer wg.Done()
        select {
        case <-ctx.Done():
            return // 超时退出
        default:
            doWork()
        }
    }(i)
}

// WaitGroup 不能直接超时，用 channel 桥接
done := make(chan struct{})
go func() { wg.Wait(); close(done) }()

select {
case <-done:
    fmt.Println("全部完成")
case <-ctx.Done():
    fmt.Println("超时，部分 goroutine 未完成")
}
```

也可以用 `errgroup` + `context`：

```go
g, ctx := errgroup.WithContext(context.Background())
ctx, cancel := context.WithTimeout(ctx, 3*time.Second)
defer cancel()

for i := 0; i < 100; i++ {
    g.Go(func() error {
        // do work，检查 ctx.Done()
        return nil
    })
}
err := g.Wait()
```

**记忆**：**WaitGroup 本身不支持超时，需要 channel 桥接或用 errgroup + context**。

#### Q4：总 goroutine 怎样结束内部启动的多个 goroutine？

**答案**：

标准做法：`context.WithCancel`：

```go
func parent() {
    ctx, cancel := context.WithCancel(context.Background())
    defer cancel() // 确保退出时取消所有子 goroutine

    for i := 0; i < 10; i++ {
        go child(ctx, i)
    }

    // 某个条件触发取消
    <-someSignal
    cancel() // 所有子 goroutine 通过 <-ctx.Done() 收到通知
}

func child(ctx context.Context, id int) {
    for {
        select {
        case <-ctx.Done():
            fmt.Printf("child %d exiting\n", id)
            return
        default:
            doWork()
        }
    }
}
```

**记忆**：**context.WithCancel 父创子传，cancel() 广播取消，子 goroutine 监听 ctx.Done()**。

#### Q5：context 常用来干什么？

**答案**：

四个核心用途：

1. **取消传播**：父 goroutine 取消时，所有子 goroutine 收到通知
2. **超时控制**：`WithTimeout` / `WithDeadline` 自动取消
3. **传值**：携带请求级数据（trace ID、用户信息等）
4. **生命周期管理**：HTTP Request 的 `r.Context()` 随请求结束而取消

四种 Context 类型：

| 类型 | 创建方式 | 用途 |
|------|---------|------|
| `Background` | `context.Background()` | 根 context |
| `TODO` | `context.TODO()` | 占位符 |
| `WithCancel` | 手动调 `cancel()` | 主动取消 |
| `WithTimeout` | 自动超时取消 | 定时取消 |

**记忆**：**取消传播、超时控制、请求传值、生命周期管理**。

#### Q6：参数不确定类型怎么定义？

**答案**：

**Go 1.18 之前**：用 `interface{}`（空接口，任意类型）

```go
func process(v interface{}) {
    switch val := v.(type) {
    case int:
        // handle int
    case string:
        // handle string
    }
}
```

**Go 1.18+ 泛型**：

```go
func process[T any](v T) T {
    return v
}

// 带约束
func sum[T int | float64](nums []T) T {
    var total T
    for _, n := range nums {
        total += n
    }
    return total
}
```

**记忆**：**旧方案 interface{} + 类型断言；新方案泛型 T any 或 T 约束**。

---

#### Q7：了解 Go 新出的泛型吗？

**答案**：

Go 1.18 引入泛型（Generics），核心特性：

1. **类型参数**：函数和类型可接受类型参数
   ```go
   func Map[T, U any](s []T, f func(T) U) []U { ... }
   ```

2. **类型约束**：用 interface 定义类型集合
   ```go
   type Number interface {
       ~int | ~float64
   }
   ```

3. **`any`**：`interface{}` 的别名，作为无约束类型参数

4. **`comparable`**：约束类型可用 `==` `!=` 比较

5. **标准库新增**：`slices`、`maps`、`cmp` 包

**记忆**：**Go 1.18 泛型：类型参数 [T any]、约束 interface { ~int | ... }、comparable、slices/maps 包**。

---

#### Q8：用 type 定义 interface 代表什么？

**答案**：

```go
type Writer interface {
    Write(p []byte) (n int, err error)
}
```

这定义了一个**接口类型**，它：
- 描述了一组方法签名（方法集）
- 任何实现了这些方法的类型都**隐式满足**该接口（鸭子类型）
- 接口变量持有两个指针：类型信息（`_type`/`tab`）+ 数据指针（`data`）
- 空接口 `interface{}`（`eface`）存任意类型，非空接口（`iface`）要求实现所有方法

**记忆**：**type 定义接口类型 = 方法签名集合，隐式实现，底层 eface/iface 存类型+数据**。

---

#### Q9：接口有什么用？

**答案**：

1. **抽象**：定义行为契约，隐藏实现细节
2. **多态**：同一接口不同实现，运行时动态分派
3. **解耦**：依赖接口而非具体实现（依赖倒置）
4. **测试**：接口便于 mock，注入测试实现
5. **组合**：小接口组合成大接口
6. **标准库范例**：`io.Reader`、`io.Writer`、`http.Handler`

Go 接口设计哲学：**接口应该小**（1-3 个方法），面向行为而非数据。

**记忆**：**抽象、多态、解耦、测试 mock、组合；接口要小，面向行为**。

#### Q10：panic 异常怎么捕捉？

**答案**：

用 `defer` + `recover`：

```go
func safeFunc() {
    defer func() {
        if r := recover(); r != nil {
            fmt.Printf("recovered from panic: %v\n", r)
        }
    }()
    panic("something went wrong")
}
```

**执行顺序**：panic → 执行当前函数的 defer（逆序）→ 遇到 recover 捕获 → 继续执行 recover 之后的代码

**注意事项**：
- `recover()` 只在 `defer` 函数中有效
- 不能捕获其他 goroutine 的 panic（每个 goroutine 需要自己 recover）
- HTTP 服务通常在中间件中统一 recover

**记忆**：**defer + recover 捕获 panic；recover 只在 defer 中有效；每个 goroutine 要自己 recover**。

#### Q22：Redis 布隆过滤器怎么实现的？

**答案**：

**原理**：
- 底层是**位数组（bit array）** + **多个哈希函数**
- 添加元素：对元素计算 k 个哈希值，将对应 bit 位设为 1
- 查询元素：检查所有对应 bit 位是否全为 1
  - 有 0 → **一定不存在**
  - 全 1 → **可能存在**（假阳性）

**Redis 实现**：
- 通过 RedisBloom 模块提供：`BF.ADD`、`BF.EXISTS`、`BF.RESERVE`
- 也可用 Redis 的 `SETBIT` + 自定义哈希函数手动实现

**应用场景**：防止缓存穿透（拦截不存在的 key）。

**记忆**：**位数组 + 多哈希函数；不存在一定准，存在可能误判；用于防缓存穿透**。

#### Q23：Redis Hash 每个 field 的有效时间能单独设置吗？

**答案**：

**不能直接设置**。Redis 的过期时间（TTL）是**针对整个 key** 的，不支持单个 field 独立过期。

**变通方案**：

1. **存储时带上时间戳**：
   ```bash
   HSET user:1 name "alice" expire_at "1700000000"
   ```
   读取时检查 `expire_at`，过期则删除该 field。

2. **拆成多个 key**：
   ```bash
   SET user:1:name "alice" EX 3600
   SET user:1:email "a@b.com" EX 7200
   ```
   每个 field 独立一个 key，各自设置 TTL。

3. **定时清理**：后台任务扫描 Hash，删除过期 field。

**记忆**：**TTL 只能设整个 key；变通：存时间戳读时判断，或拆成多个独立 key**。

### MySQL

#### Q24：查询语句特别慢怎么优化？

**答案**：

系统化排查思路：

1. **EXPLAIN 分析执行计划**：看 type、key、rows、Extra
2. **检查索引**：是否缺失、是否失效、是否多余
3. **优化 SQL 写法**：
   - 避免 `SELECT *`
   - 避免索引列上用函数/运算
   - 避免隐式类型转换
   - 避免 `OR` 拆分索引
4. **表结构优化**：字段类型、范式/反范式
5. **大表优化**：分页用 id > offset、读写分离、分库分表
6. **检查 Buffer Pool**：命中率是否正常
7. **检查锁等待**：`SHOW PROCESSLIST`、`innodb_lock_wait_timeout`

**记忆**：**EXPLAIN → 索引 → SQL 写法 → 表结构 → 大表 → Buffer Pool → 锁等待**。

---

#### Q25：已经设了索引还慢，怎么排查？

**答案**：

索引失效的常见原因：

1. **违反最左前缀原则**：联合索引未从最左列开始
2. **索引列用函数/运算**：`WHERE YEAR(create_time) = 2024`
3. **隐式类型转换**：varchar 列用 int 查询
4. **前导 % 通配符**：`LIKE '%abc'`
5. **OR 条件**：`WHERE a=1 OR b=2`（除非 OR 两边都有索引）
6. **NOT IN / NOT EXISTS / !=**：可能不走索引
7. **索引选择性太低**：如性别字段，优化器选择全表扫
8. **数据量太大**：优化器认为全表扫更快
9. **ORDER BY 非索引列**：filesort

用 `EXPLAIN` 看 type 是否是 `ALL`（全表扫），key 是否为 `NULL`（未用索引）。

**记忆**：**最左前缀、函数/运算、隐式转换、前导%、OR、选择性低、数据量大**。

---

#### Q26：`WHERE a=1 AND b<>1 AND c=1` 建什么索引？

**答案**：

`<>`（不等号）会导致索引只能用到等值匹配的部分。

**推荐索引**：`(a, c, b)` 或 `(a, c)`

- `a` 和 `c` 是等值条件，放前面（能精确定位行）
- `b` 是不等号条件，放后面（只做过滤，不参与索引定位）
- 把等值列放前面，让索引尽可能缩小扫描范围

**记忆**：**等值列放前面，不等号列放后面；(a, c) 联合索引优先**。

---

#### Q27：`WHERE a=1 AND b<>1 OR c=1` 建什么索引？

**答案**：

`OR` 会导致联合索引难以命中，优化器可能全表扫。

**方案**：

1. **拆成 UNION**（推荐）：
   ```sql
   SELECT * FROM t WHERE a=1 AND b<>1
   UNION
   SELECT * FROM t WHERE c=1
   ```
   前半段走 `(a, b)` 索引，后半段走 `(c)` 索引。

2. **建单列索引**：`(a)` 和 `(c)` 各一个，依赖 Index Merge。

3. **业务层拆分**：如果可行，拆成两次查询再合并。

**记忆**：**OR 破坏联合索引；拆 UNION 让各段走各自索引；或建单列索引走 Index Merge**。

### WebSocket

#### Q28：怎样知道 WebSocket 连接是合法用户发起的？

**答案**：

1. **握手阶段验证**：WebSocket 通过 HTTP Upgrade 建立连接，在握手请求中携带 Token/Cookie 验证身份
   ```
   GET /ws HTTP/1.1
   Upgrade: websocket
   Authorization: Bearer <token>
   ```

2. **连接后第一条消息认证**：建立连接后，客户端先发认证消息，服务端验证后标记连接合法

3. **连接白名单**：维护已认证的连接集合（`sync.Map` 或 Redis Set）

4. **心跳检测**：定期 ping/pong，清理不活跃连接

5. **绑定用户信息**：连接建立后，将 conn 与用户 ID 绑定，后续消息校验身份

**记忆**：**握手阶段 HTTP 头带 Token 验证 + 连接后首条消息认证 + 心跳保活**。

### 分布式锁

#### Q29：用 Redis 怎么实现锁？

**答案**：

**基本实现**：
```bash
SET lock_key unique_value NX EX 30
```
- `NX`：不存在才设置（互斥）
- `EX 30`：30 秒过期（防死锁）

**释放锁**（必须用 Lua 保证原子性）：
```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```
不能直接 `DEL`，否则可能误删别人的锁。

**进阶**：Redlock 算法（多 Redis 节点，多数派加锁）。

**记忆**：**SET NX EX 加锁 + Lua 脚本原子释放；value 用唯一 ID 防误删**。

#### Q30：Redis 发布订阅怎么感知消息的？

**答案**：

**工作原理**：
1. 客户端执行 `SUBSCRIBE channel`，与 Redis 建立订阅关系
2. 发布者执行 `PUBLISH channel message`
3. Redis 服务端将消息**实时推送**给所有订阅该频道的客户端
4. 客户端不需要轮询，是**推送模式**（基于 TCP 长连接）

**局限**：
- 消息不持久化：客户端离线期间的消息会丢失
- 无消费确认：不知道消费者是否收到
- 无消费组：不支持多消费者分摊

需要可靠消息可用 **Stream**（支持消费组、ACK、持久化）。

**记忆**：**SUBSCRIBE 订阅 → PUBLISH 发布 → 服务端实时推送；消息不持久化，离线丢消息**。
