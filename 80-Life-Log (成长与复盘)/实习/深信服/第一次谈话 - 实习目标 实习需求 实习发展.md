## 一、数据平台为什么要做：一条 bad case 闭环

核心诉求不是"存数据"，而是让机器人产生的**问题数据快速积累成模型可用的训练数据**，形成闭环：

```
机器人产生数据/问题数据
  → 快速积累
  → 区分筛选出 bad case（重点问题 = 模型短板）
  → 采集 / 生成补足这类数据
  → 送入模型训练
  → 训练后部署回机器人
  → 验证 bad case 是否真的提升
  → 再回到第一步
```

第二条（数据侧）闭环，是为了**反制算法"一言堂"**：

```
模型效果不好
  → 算法说"数据不行"
  → 平台要求提采集需求，且必须给理由（采集标注成本很高）
  → 采集 → 数管 → 标注 → 训练
  → 同一评测集再跑，结果还是 A
  → 证明不是数据问题，是模型问题
```

> **闭环效率就是核心竞争力**：原来一个月能闭环一次，优化到一个星期闭环一次，模型迭代速度就领先了。做这些平台的本质目的就是这个。

## 二、数管平台现状与实现架构

### 模块状态（谈话时的口径）

| 模块 | 状态 |
|---|---|
| 数管平台主体 | 做了框架和大面，功能有但仍有各类问题，"用着用着去解决" |
| 采集（设备 + 上传工具） | 有 |
| 机器人本体侧采集/录制/上传 | 有 |
| 工具引擎 | 有 |
| 质检 / 审核 | 刚开始做，未完成 |
| 预标注、辅助标注（AI 工具） | 集成在平台内 |
| 2D 标注平台 | 开源平台改的 |
| 3D 标注平台 | 之前采购的 |
| 仿真系统 | 没有 |
| 模型管理 | 没有 |
| 机型管理平台 | 业务侧的东西，后面再对接 |

> 2D/3D 标注平台的细节后续找春浩讲。预标注流程：平台侧跑模型 → 产出预标注结果 → 导入标注平台 → 人工修正（预标注允许"标个大概"）。

### 分层架构

```
接入端：机器人采集 / 外采 APP / CLI 命令行 / 管理页面
   ↓
统一 HTTP 接入层（RESTful API）—— 鉴权、聚合都在这层
   ↓
底层 RPC 服务（数量还在持续增加）
   - 接入服务
   - 原始数据管理服务
   - 搜索服务
   - 数据集管理服务
   - 工作流管理服务
   - 标注管理服务
   ↓
中间件 / 存储：MySQL、Redis、S3、ES（暂未用）、Argo 工作流、Kafka、图数据库
```

**规则**：所有服务只能走统一的 HTTP 层接入；HTTP 层只请求 RPC；RPC 再访问底层中间件和存储。

### 数据来源两条链路

1. **自有采集**：拿设备去线下现场采（商场、机场、高铁站的卫生间等），用平台的上传工具上传。
2. **机器人侧**：机器人跑任务时采集/录制，**任务空闲时**上传到平台。

## 三、开发规范与工作方式

- **开发规范文档要认真看**：SQL 使用流程、proto 规范、gRPC/RPC 约定。
- 跑起来的流程在 README 里，涉及 **Data Pro** 和 **data-circle** 仓库，头一两次会有人带着讲，用一两遍就熟了。
- **前端也得自己干**：团队没有前端，所有前端活直接用 AI 生成。
- **用 AI 的纪律（重点）**：
  1. 先让 AI 输出「要改动的完整范围」；
  2. 自己确认没有风险；
  3. 再让它实现。
- 使用过程中可以**沉淀自己的 skill**，每个人的用法和开发习惯不同，但规范化的工作必须有。

## 五、mentor 对我的规划：做一个真正能用的平台级 Agent

> 原话大意："我其实更想让你做出来一个完整的、大家可供大家用、或者说平台能用的一个 Agent。"

要思考的问题：怎么调用这个 Agent、底层依赖什么、走什么协议、是平台上用还是开发时用。

### 分阶段路线（先能跑，再加能力）

**阶段 0：先接需求、熟悉平台**
下周二到岗，先接一些需求，了解平台现在长什么样、有什么东西。做需求的过程中形成大致轮廓，再聊具体业务概念。

**阶段 1：内网自嗨版 —— 命令行指令问答 + 知识库**
- 把 CLI/DP 工具的能力和参数喂给 Agent，配一个知识库让它"充分熟悉"这个工具。
- 用户提问 → Agent **输出应该用哪条指令**（不做实际操作）。
- 例："洗手间工区今天和昨天上传了哪些数据，我该用什么指令？"
- 支持就输出指令，不支持就明确说不支持。
- **目的**：验证指令输出是否稳定、知识库质量是否 OK。
- 知识库更新问题先不纠结（自动从 git 定时拉 vs 人工更新），**先考虑内网**，跑通再谈外网迁移。

**阶段 2：只读查询 Tools**
- 把 HTTP 接口封装成 tools，让 Agent 直接调，查数据。
- 例："洗手间工区昨天和今天上传了哪些 capture，把 capture ID 都输出出来" → Agent 调 tools 查询返回。

**阶段 3：直接操作**
- 给权限，Agent 自己创建工作流任务、选模板。
- 例："给洗手间工区今天和昨天的数据创建一个工作流任务，用 XX 模板" → 它自己建。

> 最终形态：平台上直接挂一个助手，点进去就能对话。数据量这么大，来回页面点很麻烦。

### 已识别的关键依赖

- **鉴权**（Agent 调接口的身份问题）
- **Tools 封装**（HTTP 接口 → tool）
- **知识库的更新与维护机制**

> 不一开始就让 AI 直接调 CLI：稳定性未知，下载数据这类操作风险高；问答/出指令更安全，也解决"人记不住指令"的真实痛点。

## 七、值得记住的几句话

- 平台的价值不在功能多少，而在**闭环效率**。
- 采集标注是**高成本动作**，所以提需求必须有说服力。
- 实习生要**自己多思考、多问**——没人会一直给你灌输，只有你问了才会讲。
- 先跑通最简单的一条流，再逐步扩充能力边界；不要一上来就做全。
