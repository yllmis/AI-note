# MySQL

## MVCC 多版本并发控制

**一句话定位**：InnoDB 给每行保留多个历史版本，**读不阻塞写、写不阻塞读**（快照读场景）。

### 三大核心组件

| 组件 | 是什么 | 作用 |
|------|--------|------|
| **隐藏字段** | 每行自带的元数据 | 记录「谁改的、旧版本在哪」 |
| **Undo Log 版本链** | 旧版本用回滚指针串成链 | 支持回滚 + 提供历史快照 |
| **ReadView** | 事务某次读的快照清单 | 判断哪个版本对「我」可见 |

**隐藏字段**：
- `DB_TRX_ID`：最后一次修改这行的事务 ID
- `DB_ROLL_PTR`：回滚指针，指向 undo log 里的上一版本
- `DB_ROW_ID`：隐含主键（表无主键时生成）

**版本链示意**：

```
当前行 (trx_id=300, roll_ptr)
    ↓
undo v3 (trx_id=200) → undo v2 (trx_id=100) → undo v1
```

**ReadView 四要素**：
- `m_ids`：生成 ReadView 时**活跃（未提交）**事务 ID 列表
- `min_trx_id`：活跃事务中最小的 ID
- `max_trx_id`：系统下一个要分配的事务 ID（当前最大 + 1）
- `creator_trx_id`：创建这个 ReadView 的事务自己

### 可见性算法（面试必背）

对某版本的 `DB_TRX_ID = trx_id`，从新到旧沿版本链找第一个可见的：

1. `trx_id == creator_trx_id` → **可见**（自己的修改）
2. `trx_id < min_trx_id` → **可见**（生成快照前已提交）
3. `trx_id >= max_trx_id` → **不可见**（快照之后才开启的事务）
4. `trx_id in m_ids` → **不可见**（生成快照时还活跃、未提交）
5. 否则 → **可见**（不在活跃列表，说明已提交）

不可见就沿 `roll_ptr` 看上一版本，直到找到可见版本或链结束（返回空）。

**记忆**：**比自己、比边界、查活跃；不可见就滚上一版**。

### RC 与 RR 的区别（高频）

| | RC 读已提交 | RR 可重复读 |
|---|---|---|
| **ReadView 生成时机** | **每次 SELECT 都新建** | **事务第一次 SELECT 建，之后复用** |
| 效果 | 能读到别人已提交的最新值 | 整个事务读到同一快照 |
| 幻读（快照读） | 会出现 | ReadView 避免 |

**记忆**：**RC 每次换眼镜，RR 一副眼镜戴到底**。

### 快照读 vs 当前读

| | 快照读 | 当前读 |
|---|---|---|
| **语句** | 普通 `SELECT` | `SELECT FOR UPDATE` / `LOCK IN SHARE MODE` / `INSERT` / `UPDATE` / `DELETE` |
| **读什么** | ReadView 历史版本 | 最新已提交版本 |
| **加锁** | 不加 | 加锁（行锁 / 间隙锁） |
| **靠什么防幻读** | ReadView 版本链 | Next-Key Lock（临键锁） |

**为什么 RR 还需要锁**：快照读靠 MVCC 解决幻读；一旦有**当前读**（如 UPDATE），读的是最新值，必须靠 Next-Key Lock 锁住间隙，防止插入新行。

### MVCC 完整流程示例

```
T1 (trx_id=100) 开启事务
T2 (trx_id=200) 开启事务
T2: UPDATE t SET name='B' WHERE id=1   （未提交）
T1: SELECT name FROM t WHERE id=1
     → 生成 ReadView: m_ids=[100,200], min=100, max=201
     → 当前版本 trx_id=200，在 m_ids 中 → 不可见
     → 沿 roll_ptr 找到旧版本（已提交）→ 读到旧值
T2: COMMIT
T1: SELECT ...  （RR：复用 ReadView，仍读旧值）
              （RC：新建 ReadView，读到 'B'）
```

### 常见追问

**Q：MVCC 能完全代替锁吗？**
不能。MVCC 只解决**快照读**的读写冲突；写写冲突（两个事务改同一行）仍靠**行锁 + 两阶段锁**。幻读的当前读场景也要靠 Next-Key Lock。

**Q：undo log 什么时候清理？**
没有活跃 ReadView 需要它时，由后台 purge 线程清理。长事务会撑大版本链 → 查询变慢、undo 膨胀。

**Q：为什么长事务是大敌？**
ReadView 一直不释放 → 版本链越拉越长 → 回滚段膨胀、查询要沿链找可见版本。

**记忆**：**MVCC = 隐藏字段 + undo 版本链 + ReadView；RC 每次新、RR 用一次；快照读靠版本，写写靠行锁**。

## ACID 与 MVCC 的关系

**结论先行**：**MVCC 只负责 ACID 里的 I（隔离性），且只是一部分**。ACID 四件套各靠各的机制。

| 特性 | 靠什么 | MVCC 的角色 |
|------|--------|-------------|
| **A 原子性** | **Undo Log**（回滚段） | 无（undo 一份两用：回滚服务 A，版本链服务 MVCC） |
| **C 一致性** | A + I + D 的**结果** + 约束（主键/外键/唯一） | 无。一致性是目的，不是机制 |
| **I 隔离性** | **MVCC + 锁** | **MVCC 只管快照读**；写写冲突、当前读靠行锁/间隙锁/Next-Key |
| **D 持久性** | **Redo Log**（WAL） | 无 |

### 各特性拆解

**A —— Undo Log**：事务中途失败沿 undo 链回滚，多条语句要么全成、要么全不成。

**C —— 不是独立机制**：靠 A/I/D 共同生效 + 主键/外键/唯一约束 + 应用层业务规则。DB 只能保证「扣和加原子」，保证不了「转账总额不变」这类业务正确性。

**I —— MVCC + 锁缺一不可**：

| 场景 | 谁负责 |
|------|--------|
| 快照读（普通 SELECT） | MVCC（ReadView 版本链） |
| 当前读（FOR UPDATE / 增删改） | 行锁 + 间隙锁 + Next-Key |
| 写写冲突（两事务改同行） | 锁排队，MVCC 不管 |

**D —— Redo Log**：提交时先写 redo 刷盘（WAL），崩溃后重放。顺序写比直接写数据页快得多；redo + binlog 两阶段提交保证主从一致。

### 一张图串起来

```
事务提交
  │
  ├─ A：写 undo（可回滚）
  ├─ I：MVCC 给快照读出版本 / 锁挡住写冲突
  └─ D：redo 落盘（崩溃可恢复）
        ↓
      C：以上全部生效后，数据一致
```

**面试一句话**：MVCC 只实现隔离性中的**快照读**；原子性靠 undo，持久性靠 redo，一致性是三者加约束的**结果**。

**记忆**：**MVCC 只管 I 的读；A 靠 undo、D 靠 redo、C 是果不是因**。

## 索引结构

### 为什么是 B+ 树（推导版）

**核心约束：磁盘 IO 是瓶颈**。一次随机 IO 毫秒级，唯一目标是把 IO 次数压到最少。
**树高 = IO 次数**。

**逐个淘汰**：

| 结构 | 为什么不行 |
|------|------------|
| 哈希 | 等值 O(1) 但范围/排序/模糊全废 |
| 二叉树/红黑树 | 一分支两路，千万数据 ≈ 23 层 = 23 次 IO |
| B 树 | 非叶节点存 data，一页放不了几个 key，**扇出小** |
| 跳表 | Redis 内存场景；层级随机，树高不可控 |
| LSM-Tree | 写友好但读放大，不适合 MySQL 读写混合 + 事务 |

**B+ 树的两个关键改造**：

1. **非叶只存 key + 指针**：一页 16KB，key+指针 ≈ 14B → **~1170 分支**
2. **数据全放叶子 + 叶子双向链表**：路径长度一致；范围查询扫链表不回溯

```
        [非叶：只放 key，指路]          ← 一页 1170 个分支
        /        |        \
   [非叶]     [非叶]     [非叶]
[叶子：key+数据] ↔ [叶子] ↔ [叶子]      ← 双向链表
```

**三层能存多少（面试算账）**：
1170 × 1170 × (16KB/1KB ≈ 16 行) ≈ **2190 万行**，只需 **3 次 IO**。

**叶子链表的作用**：

| 场景 | B 树 | B+ 树 |
|------|------|-------|
| 范围查询 | 找到后反复爬树 | 链表顺序扫 |
| ORDER BY | 中序遍历 + 回溯 | 链表天然有序 |
| LIMIT 分页 | 低效 | 链表直接截断 |

**推导链**：磁盘 IO 是瓶颈 → 要树矮 → 要扇出大 → 非叶不放数据 → 数据全在叶子 → 叶子链表扫范围。**每一步都是被约束逼出来的**。

**记忆**：**IO 定生死，扇出定树高；非叶只指路，叶子链着扫**。

### 聚簇索引 vs 二级索引

| | 聚簇索引 | 二级索引 |
|---|---|---|
| **叶子存什么** | **整行数据** | **主键值** |
| 数量 | 表只有 1 个（主键） | 可多个 |
| 查找 | 一次到位 | 二级找主键 → 聚簇捞整行（**回表**） |

**覆盖索引**：查询列都在二级索引中 → 不回表。`EXPLAIN` 显示 `Using index`。

**记忆**：**聚簇存整行，二级存主键；回表二次找，覆盖不用回**。

### 最左前缀原则

联合索引 `(a,b,c)` 相当于 `(a)`、`(a,b)`、`(a,b,c)` 三个索引。

| 查询 | 能否用上 |
|------|----------|
| `a=1 AND b=2 AND c=3` | 全用上 |
| `b=2 AND c=3` | **用不上**（跳过 a） |
| `a=1 AND c=3` | 只用上 a（c 断了） |
| `a=1 ORDER BY b` | a 等值 + b 排序，免 filesort |

**原理**：B+ 树按 (a,b,c) 顺序排序，跳过 a 无法定位区间。

**记忆**：**联合索引像字典拼音序，跳了 a 就查不了**。

### 索引类型速查

| 类型 | 说明 | 用途 |
|------|------|------|
| 主键索引 | 聚簇，唯一 NOT NULL | 行定位 |
| 唯一索引 | 唯一，允许 NULL | 唯一约束 |
| 普通索引 | 允许重复 | 加速查询 |
| 全文索引 | FULLTEXT | 文本搜索（中文一般用 ES） |
| 前缀索引 | 字符串前 N 字符 | 长字符串省空间 |

### 索引失效场景

1. 对索引列做**函数/运算**：`YEAR(create_time)=2026` ❌ → 改范围查询 ✅
2. **隐式类型转换**：`phone` 是 varchar，`WHERE phone=13800000000` ❌
3. **LIKE 左模糊**：`LIKE '%张'` ❌（`LIKE '张%'` 可以）
4. **联合索引跳过最左列**
5. `OR` 连接无索引列（可能全表扫）
6. 优化器判断**回表太多**不如全表扫

**记忆**：**函数类型转换和左模糊，跳过最左就失效**。

**总口诀**：**B+ 树矮胖三层 IO，聚簇整行二级主键；最左前缀别跳 a，覆盖索引免回表**。

## 分库分表

### 是什么

单库单表扛不住时，把数据拆开放到多个库/多张表。

| 拆法 | 维度 | 例子 | 解决什么 |
|------|------|------|----------|
| **垂直分库** | 按**业务**拆 | 用户库、订单库 | 业务隔离、降低单库并发 |
| **水平分库** | 按**数据行**拆到多个库 | 订单库1、订单库2 | 单库存储/并发到顶 |
| **垂直分表** | 按**字段**拆 | 热字段 + 大字段分表 | 一行别太大，一页放不了几行 |
| **水平分表** | 按**数据行**拆到多张表 | order_0 ~ order_3 | 单表行数太多，B+ 树变高、DDL 慢 |

**记忆**：**垂直按业务/字段切，水平按数据行切**。

### 为什么要分

| 瓶颈 | 现象 | 该拆什么 |
|------|------|----------|
| 单表数据量 | 千万~亿级，DDL 锁表久、查询慢 | 水平分表 |
| 单库并发 | QPS 打满 CPU/连接数 | 水平/垂直分库 |
| 磁盘容量 | 单实例装不下 | 水平分库 |
| 业务耦合 | 一库挂全挂，大字段拖慢 | 垂直拆分 |

**经验阈值**：单表 **500 万~1000 万行** 考虑分表；单库 **QPS 3000+** 或磁盘 **1TB+** 考虑分库。

**记忆**：**量大分表，压大分库，业务乱垂直拆**。

### 怎么做

**分片键（Sharding Key）**：高频查询带上、分布均匀、避免跨库。选错 = 灾难。

| 策略 | 例子 | 优点 | 缺点 |
|------|------|------|------|
| 哈希取模 | `user_id % 4` | 分布均匀 | 扩容要迁移 |
| 范围分片 | 按时间/ID 区间 | 扩容容易 | 热点在最新片 |
| 一致性哈希 | 哈希环 | 扩容迁移少 | 实现复杂 |
| 基因法 | user_id 尾几位写进订单 ID | 路由精准 | ID 生成复杂 |

**架构**：应用 → 中间件路由 → 多库多表
- 客户端：ShardingSphere-JDBC
- 代理：ShardingSphere-Proxy / Vitess

**分布式 ID**（主键不能再自增）：
1. **雪花算法**：时间戳 + 机器 ID + 序列，趋势递增（推荐）
2. **号段模式**：每次取一段 ID（Leaf）
3. UUID：无序破坏 B+ 树局部性，**不推荐做主键**

**记忆**：**哈希均匀难扩容，范围好扩有热点；ID 用雪花不用 UUID**。

### 带来的麻烦

| 问题 | 解决 |
|------|------|
| 跨库 JOIN | 字段冗余 / 应用层组装 / 全局表 |
| 分布式事务 | 最终一致（本地消息表 / MQ）；强一致上 Seata |
| **跨库深分页** | 各分片 LIMIT 内存归并会爆炸 → **游标分页**（`WHERE id > last_id LIMIT 20`） |
| 扩容迁移 | 一致性哈希 / 双写迁移 |
| 跨库 count | 计数表 / 异步聚合 |

**深分页为什么难**：要第 10000 页 → 每片取 10010 条 → 内存归并爆炸。业务上禁深翻页，改游标。

### 什么时候不要分

- 数据量 < 500 万、QPS 不高 → **加索引、读写分离、归档冷数据**就够了
- 过早分库分表 = 自己上分布式难度

**记忆**：**先索引后归档，再读写分离，最后才分库分表**。
