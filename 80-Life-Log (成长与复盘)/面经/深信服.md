### MySQL

#### Q7：MySQL 的 ACID 有了解过吗？

**我的原回答**：

> 四个特点：原子性、一致性、隔离性、持久性。原子性——事务要么成功要么全部回滚；一致性——事务前后要满足规则；隔离性——并发事务之间不能互相干扰；持久性——事务提交后即使突然宕机，数据也不会丢失。

**评分：7/10**

> 四个特性的**含义全部正确**，表述完整，这是基础扎实的表现。失分在只答"是什么"没答"怎么实现"——ACID 面试必被追问实现机制（Undo/Redo/MVCC+锁），答出机制能从 7 分拉到 9 分。"一致性=满足规则"略含糊，可说"从一个合法状态到另一个合法状态（如余额约束）"。

**参考答案**：

| 特性 | 含义 | 实现机制 |
|------|------|---------|
| **A 原子性** | 要么全成功要么全回滚 | **Undo Log**（回滚日志） |
| **C 一致性** | 事务前后满足完整性约束 | 由 AID 共同保证 |
| **I 隔离性** | 并发事务互不干扰 | **MVCC + 锁** |
| **D 持久性** | 提交后宕机不丢 | **Redo Log**（WAL） |

隔离级别：RU → RC → **RR（默认）** → SERIALIZABLE；InnoDB 的 RR 用 MVCC + 间隙锁解决大部分幻读。

**记忆**：**A 靠 Undo，D 靠 Redo，I 靠 MVCC+锁，C 靠三者共同保证；默认 RR**。

#### Q8：（手写 SQL）学生表（student_id, score），查成绩第三高的学生的 ID

**我的原回答**：

> （共享屏幕上写出查询：ORDER BY score DESC 配合 LIMIT/OFFSET 思路；字段名有笔误，class 列/ student_id 写错，面试官说"写错了 student ID，没事"，并确认"大概就是这个意思"。代码录音未保留。）

**评分：7/10**

> 按现场反馈：思路对（排序 + 取第三条），面试官当场确认"大概是这个意思"。失分：字段名笔误（低级失误，紧张所致）；。

**参考答案**：

**方案1：LIMIT / OFFSET**（分数不并列时最简单）

```sql
SELECT student_id, score
FROM student
ORDER BY score DESC
LIMIT 1 OFFSET 2;   -- 第 N 高就是 OFFSET N-1
```

**方案2：DENSE_RANK**（严谨，正确处理并列）

```sql
SELECT student_id, score
FROM (
    SELECT student_id, score,
           DENSE_RANK() OVER (ORDER BY score DESC) AS rk
    FROM student
) t
WHERE rk = 3;
```

**追问——并列怎么算第三高**：`RANK()` 并列跳号（1,1,3）；`DENSE_RANK()` 并列不跳号（1,1,2）——"第三高的分数"通常指这个；`ROW_NUMBER()` 强制唯一。只求分数值：`SELECT DISTINCT score ... LIMIT 1 OFFSET 2`。

**记忆**：**简单用 LIMIT 1 OFFSET N-1；严谨用 DENSE_RANK=rk；先想清楚并列语义再写**。

### Redis

#### Q9：Redis 用的多吗？分布式锁有用过吗？项目里有没有需要用锁的地方？

**我的原回答**：

> Redis 用得还行，不算很多，项目里需要缓存的地方都会用 Redis。分布式锁目前没有用过。项目里需要用锁的地方……（长时间停顿）大概应该用过，但想不起来具体在哪里了。

**评分：2/10**

> 全场最差的一题。分布式锁"没用过"可以接受，但"项目里哪里需要用锁"是**送分题**——你自己的 IM-Grpc 代码里就有现成答案：WebSocket 连接表用 `sync.RWMutex` 保护（`apps/im/ws/websocket/server.go`）、已读回执处理用 `sync.Mutex` 保护缓存（`msgReadTransfer.go`）。自己写过的锁都想不起来，面试官会怀疑项目参与度。答"想不起来"比答错更伤。

**参考答案**：

**分布式锁实现（Redis）**：

```go
// 拿锁：SET NX PX 原子操作，带过期防死锁
ok := rdb.SetNX(ctx, "lock:"+bizID, ownerToken, 10*time.Second)

// 释放：Lua 脚本原子校验持有者再删，防误删
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
end
```

要点：SET NX PX 原子；value 存唯一 token，Lua 校验再删；超时续期（Redisson watchdog）；一般业务单实例锁 + 幂等兜底够用。

**项目里需要锁的场景**（结合 IM-Grpc 真实代码）：
- **WebSocket 连接表**：多 goroutine 并发增删连接，用 `RWMutex` 保护 map（读多写少）
- **已读回执/群组回执处理**：`sync.Mutex` 保护批量缓存的并发写
- **缓存击穿**：热点 key 过期，互斥锁放一个请求查 DB 回填
- **防重复提交/消息幂等**：按业务 ID 抢锁

**记忆**：**SET NX PX 拿锁、Lua 校验释放、watchdog 续期；项目场景先想自己的代码：连接表 RWMutex、回执 Mutex、击穿互斥锁**。

#### Q11：MySQL 和 MongoDB 的区别？

**我的原回答**：

> MySQL 是关系型数据库，数据模型固定；MongoDB 是文档型，JSON/集合格式比较灵活。MySQL 适合存学生数据、交易订单这种格式固定、有关联的数据；MongoDB 适合存 JSON 格式的数据、聊天记录这种读取量比较大的数据。

**评分：7/10**

> 核心区别（关系型 vs 文档型、固定 vs 灵活、适用场景）都答对了，场景举例也贴切。失分：维度不全——没提 JOIN、事务、扩展方式（分片 vs 分库分表）、索引结构差异；被追问底层存储时露怯（见 Q12）。

**参考答案**：

| | MySQL | MongoDB |
|---|-------|---------|
| 类型 | 关系型（表/行） | 文档型（BSON） |
| Schema | 固定 DDL | 动态灵活 |
| 关联 | 强 JOIN | 无 JOIN，嵌入/冗余换读性能 |
| 扩展 | 主从/分库分表 | 原生分片水平扩展 |
| 事务 | 成熟完整 ACID | 4.0+ 多文档事务 |
| 适用 | 订单等强一致强关系 | 聊天记录/日志等海量灵活数据 |

IM 项目**两者并用**：账户/关系链在 MySQL，消息在 MongoDB。

**记忆**：**MySQL 关系固定强事务强 JOIN，Mongo 文档灵活分片扩展；一个管"关系"，一个管"内容"**。

#### Q12：（追问）它们底层存储是怎么存数据的？

**我的原回答**：

> MySQL 底层有 B+ 树索引，是 InnoDB 引擎，还有 MVCC 机制（只蹦出关键词，没有展开）。MongoDB 底层存储具体我不是很了解，没仔细了解过。（问"专业课学过数据库原理吗"：学过。）

**评分：4/10**

> MySQL 侧蹦出了三个正确关键词（B+ 树、InnoDB、MVCC）说明有存货，但一个都没展开——关键词式回答在追问下等于不会。MongoDB 底层坦白"不了解"是诚实的，但这题正是面试官最后反馈"数据库底层要加强"的直接来源。

**参考答案**：

**MySQL（InnoDB）**：
- **B+ 树聚簇索引**：叶子节点存整行、双向链表；非叶子只存 key，三层树高覆盖千万行
- **页（16KB）+ Buffer Pool**：内存缓存数据页，减少磁盘 IO
- **WAL（Redo Log）**：先写日志再刷数据页，崩溃恢复
- **MVCC**：Undo Log 版本链 + Read View 实现快照读，读写不阻塞

**MongoDB（WiredTiger）**：
- **B 树索引**（注意不是 B+ 树）：节点直接存数据，无叶子链表
- **文档级并发控制**（粒度锁），写入压缩（snappy/zstd）
- **副本集**（Raft 选举）+ **分片**（按 shard key 分布）

**对比一句话**：InnoDB 靠 B+ 树 + MVCC + WAL 换强事务；WiredTiger 靠 B 树 + 文档级锁 + 压缩换灵活写入。

**记忆**：**InnoDB：B+树聚簇、页+Buffer Pool、Redo WAL、MVCC 版本链；Mongo：WiredTiger B 树、文档级并发、压缩、副本集分片**。

### Kafka

#### Q13：Kafka 用的多吗？怎么保证数据不丢、不重复？（追问：服务挂了/网络断了，拿到的消息没处理完，丢了怎么办？）

**我的原回答**：

> Kafka 平常比较少，IM 项目里用它转发数据、削峰填谷。不丢的话——Kafka 自带机制，宕机重连后可以重试；保证要分三端：生产端、broker 端、消费端，任何一端出问题都可能丢。消费端我是手动提交 offset——业务处理成功之后才提交，如果丢失就通过它判断消息丢失，再重试拉取。

**评分：6/10**

> 三端视角（生产/broker/消费）+ **手动提交 offset、业务成功才提交**——这点答得好，而且和你项目代码完全一致（`consumer/chat.go` 里 `handle` 成功后才 `CommitMessages`），是真实经验。失分：① "Kafka 自带机制"含糊，acks/副本/ISR 没提；② 题目问了"不重复"，**幂等防重完全没答**；③ 项目里其实还有 DLQ 死信队列 + 重试（`messageRetry + dlq`），答出来直接 8 分。

**参考答案**：

**不丢**（三端）：
- **生产端**：`acks=all` + 重试 + 幂等 Producer（PID 防重复写）
- **Broker**：副本 ISR 同步，`min.insync.replicas` 保证写进多个副本
- **消费端**：**手动提交 offset，先处理后提交**——处理失败不提交，重启后重新消费；失败进**死信队列**兜底

**服务挂了/断网**：消息持久化在 Kafka 不会丢——丢的是"处理进度"。offset 没提交就重新消费，配合幂等不重复副作用。

**不重复**：at-least-once 语义下必有重复 → 消费端**幂等**（唯一业务 ID 去重，如 `UNIQUE(msg_id)`）。

**记忆**：**acks=all+副本保生产端，手动提交+DLQ 保消费端，幂等键防重复；挂了重启靠 offset 重新消费**。

### Go

#### Q14：Go 的 map 是无序的，为什么无序？底层有了解吗？

**我的原回答**：

> map 底层是哈希表，旧实现是用桶去实现的 Go map；新版本改成了 Swiss Table。无序是因为遍历 map 的时候会随机选择一个起始点开始遍历，所以 map 就是无序的状态。

**评分：8/10**

> 全场最佳八股之一：哈希表、桶、Swiss Table（Go 1.24+ 新实现）、**随机遍历起点**全答到，还知道新旧实现切换，超出预期。小扣分：桶（拉链法，每桶 8 个 kv）和"key 经哈希分布、与插入顺序无关"这一层没展开——答上就满分。

**参考答案**：

**底层结构**：
- Go 1.23 及之前：`hmap` + **桶数组（拉链法）**，每个桶 8 个 kv 对，key 经哈希函数定位桶
- Go 1.24+：**Swiss Table**（开放寻址法，内存局部性更好）

**无序的两个原因**：
1. key 经哈希分散到各桶，**存储顺序与插入顺序无关**（本质原因）
2. 遍历时运行时**故意随机化起点**（防止开发者依赖遍历顺序）

需要有序：取出 key 排序后遍历。

**记忆**：**哈希分布与插入无关是本质，随机起点是防御；旧桶拉链 8 kv，1.24 换 Swiss Table 开放寻址**。

#### Q15：（手写 Go）两个 goroutine 交替打印奇数和偶数

**我的原回答**：

> （共享屏幕写了两个 goroutine 交替打印的代码，内容录音未保留；面试官看后说"如果你觉得有问题可以再改一下"，随后表示可以。）

**评分：7/10**

> 按现场反馈代码基本可用。看不到实现细节无法细评——如果用的是 channel 乒乓（无缓冲手递手）就是标准答案；如果用 sleep 凑交替或者锁+标志位轮询，会被追问时序保证。建议能主动说出"用无缓冲 channel 做同步，天然严格交替"。

**参考答案**：

```go
func main() {
    chOdd := make(chan struct{})
    chEven := make(chan struct{})

    go func() { // 奇数：1 3 5 7 9
        for i := 1; i <= 9; i += 2 {
            <-chOdd
            fmt.Println("奇:", i)
            chEven <- struct{}{}
        }
    }()
    go func() { // 偶数：2 4 6 8 10
        for i := 2; i <= 10; i += 2 {
            <-chEven
            fmt.Println("偶:", i)
            if i < 10 {
                chOdd <- struct{}{}
            }
        }
    }()

    chOdd <- struct{}{} // 先触发奇数
}
```

**要点**：无缓冲 channel "手递手"同步——发完才轮到对方，**天然严格交替**，不依赖 sleep/调度运气；`chOdd <- struct{}{}` 启动第一棒。变体：WaitGroup 收尾、条件变量版、buffer=1 版（注意缓冲会破坏严格交替）。

**记忆**：**无缓冲 channel 乒乓：收→打印→发给对方，一棒接一棒；顺序靠同步不靠 sleep**。

### WebRTC / 网络

#### Q1：讲一下 WebRTC

**答案**：

WebRTC（Web Real-Time Communication）是浏览器原生的**实时音视频/数据通信**框架，无需插件，目标是端到端 P2P 低延迟通信。

**三大 API**：

| API | 作用 |
|-----|------|
| `getUserMedia` | 采集摄像头/麦克风/屏幕流 |
| `RTCPeerConnection` | 建立 P2P 连接，传输音视频（SRTP 加密） |
| `RTCDataChannel` | 传任意数据（SCTP over DTLS，可靠/不可靠可配） |

**协议栈**：
- 媒体传输：**SRTP**（加密的 RTP）
- 数据通道：**SCTP over DTLS**
- NAT 穿透：**ICE / STUN / TURN**（见 Q2）
- 信令（不在 WebRTC 标准内）：通过 WebSocket / HTTP 交换 **SDP**（offer/answer）和 ICE candidate

**建立流程**：
1. A 生成 offer SDP → 信令服务器 → B
2. B 回 answer SDP → 信令服务器 → A
3. 双方通过 STUN 收集 candidate（host / srflx / relay）互换
4. ICE 做连通性检测（打洞），选出最优路径 → P2P 媒体流开始传输

**多人通话**：纯 P2P mesh 只适合 4-6 人；多人场景用 **SFU**（选择性转发，如 Janus、mediasoup，只转发不转码）或 **MCU**（混流，服务端转码）。

**应用场景**：视频会议、IM 音视频通话（如 IM 项目的语音/视频消息）、屏幕共享、在线教育白板。

**记忆**：**WebRTC = getUserMedia + RTCPeerConnection + DataChannel；信令走 SDP（WebSocket 传），媒体走 SRTP，穿透靠 ICE/STUN/TURN；多人用 SFU**。

---

#### Q2：STUN 和 TURN 的区别

**答案**：

两者都是 **NAT 穿透**方案，属于 ICE 框架的一部分，解决"双方都在 NAT 后面没有公网地址"的问题。

**STUN（Session Traversal Utilities for NAT）**：
- 轻量服务器，客户端发 Binding Request，服务器把看到的**公网 IP:Port** 回显给客户端
- 客户端拿到反射地址（srflx candidate）后尝试**打洞直连（P2P）**
- 本身不转发媒体流量，只做"地址发现"
- 对全锥形/受限锥形 NAT 有效；对**对称型 NAT**（每个目标映射不同端口）失败

**TURN（Traversal Using Relays around NAT）**：
- **中继服务器**：打洞失败（对称 NAT、防火墙封锁）时，双方都把媒体发给 TURN，由它转发
- 保证连通性兜底，但服务器带宽成本高（所有流量过中继）
- 产生 relay candidate，ICE 优先直连，只把 TURN 当 fallback

**对比**：

| | STUN | TURN |
|---|------|------|
| 角色 | 地址发现 | 流量中继 |
| 是否转发媒体 | 否 | 是 |
| 开销 | 极小 | 大（带宽昂贵） |
| 适用 | 锥形 NAT 打洞 | 对称 NAT / 防火墙兜底 |
| 成功时路径 | P2P 直连 | 经服务器中转 |

**ICE 框架的候选优先级**：host（本机）→ srflx（STUN 发现）→ relay（TURN 中继），逐对做连通性检测，选最优可用路径。

**记忆**：**STUN 查公网地址尝试 P2P 打洞，TURN 打洞失败走中继兜底；ICE 收集候选 host→STUN→TURN 依次尝试**。

### Go 并发

#### Q3：goroutine 怎么限制并发量（用代码实现而不是资源限制）

**答案**：

不靠 `GOMAXPROCS` 等运行时资源限制，而是**代码层面控制同时执行的 goroutine 数量**。

**方案1：带缓冲 channel 当信号量（推荐）**

```go
sem := make(chan struct{}, N) // 令牌桶，容量 = 并发上限
var wg sync.WaitGroup

for _, task := range tasks {
    wg.Add(1)
    sem <- struct{}{} // 满 N 个时阻塞，直到有人归还令牌
    go func(t Task) {
        defer func() {
            <-sem // 归还令牌
            wg.Done()
        }()
        handle(t)
    }(task)
}
wg.Wait()
```

**方案2：errgroup.SetLimit（Go 1.20+，一行搞定）**

```go
g := new(errgroup.Group)
g.SetLimit(N)
for _, task := range tasks {
    g.Go(func() error {
        return handle(task)
    })
}
err := g.Wait()
```

**方案3：Worker Pool（固定 goroutine 数消费任务队列）**

```go
tasks := make(chan Task, len(tasks))
for _, t := range allTasks {
    tasks <- t
}
close(tasks)

var wg sync.WaitGroup
for i := 0; i < N; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        for t := range tasks {
            handle(t)
        }
    }()
}
wg.Wait()
```

**选型**：临时并发上限用信号量/SetLimit；长期跑批用 Worker Pool（goroutine 复用，减少创建销毁）。

**记忆**：**带缓冲 channel 当信号量（容量=上限，拿令牌执行、还令牌放行）或 errgroup.SetLimit；本质是令牌桶/池化**。

#### Q4：channel 的原理

**答案**：

channel 底层是 `hchan` 结构体，核心三件套：**环形缓冲区 + 等待队列 + 互斥锁**。

```go
type hchan struct {
    qcount   uint           // 缓冲区中元素个数
    dataqsiz uint           // 缓冲区容量（make 时指定）
    buf      unsafe.Pointer // 环形缓冲区指针
    sendx    uint           // 发送下标
    recvx    uint           // 接收下标
    sendq    sudog          // 发送等待队列（阻塞的发送方链表）
    recvq    sudog          // 接收等待队列（阻塞的接收方链表）
    lock     mutex
}
```

**发送流程（ch <- v）**：
1. 加锁
2. 若 recvq 有等待的接收方 → **直接把数据拷贝到接收方栈上**（无缓冲 channel 的"手递手"传递），唤醒接收方
3. 否则若缓冲区未满 → 写入环形缓冲区 `buf`，sendx++
4. 否则当前 goroutine 打包成 sudog 挂到 sendq，**park 让出 P**，等待被唤醒

**接收流程（<-ch）** 对称：sendq 有等待者 → 从发送方直接拷数据并唤醒；缓冲区有数据 → 取走；否则挂 recvq 阻塞。

**关键特性**：
- **无缓冲 channel**：数据不经过 buf，发送方栈 → 接收方栈直接拷贝，天然同步（hand-off）
- **有缓冲 channel**：解耦收发节奏，满则发送阻塞、空则接收阻塞
- **close**：置 closed 标志，唤醒所有等待者；接收方可读完存量后拿到零值；向 closed channel 发送 → panic
- **并发安全**：所有操作持 hchan.lock；goroutine 阻塞时被 park 进等待队列，不占线程

**记忆**：**hchan = 环形缓冲区 + sendq/recvq 等待队列 + 互斥锁；无缓冲手递手拷贝同步，有缓冲走环形队列；满发阻塞、空收阻塞，close 后可读不可写**。

### 架构选型

#### Q5：为什么使用 HTTP + JSON 而不是 gRPC + protobuf

**答案**：

本质是 **开发调试效率/生态兼容** 与 **性能/强类型** 的权衡。

| | HTTP + JSON | gRPC + protobuf |
|---|-------------|-----------------|
| 传输 | HTTP/1.1（或 2） | HTTP/2（多路复用、头部压缩） |
| 序列化 | 文本 JSON，人可读 | 二进制 protobuf，体积小、编解码快 |
| 接口契约 | 无强约束（或 OpenAPI） | `.proto` IDL 强类型 + 代码生成 |
| 浏览器/前端 | 原生支持 | 需要 grpc-web + Envoy 代理 |
| 调试 | curl / Postman / 日志直接可读 | 需要 grpcurl / 反射 / 抓包 |
| 网关生态 | Nginx、WAF、CDN、鉴权中间件全兼容 | 边缘设备/网关支持参差 |
| 流式 | 不原生支持（SSE/WebSocket 补） | 原生四种流式（unary/server/client/bidi） |
| 迭代成本 | 改字段即生效 | 改 proto 要多端重新生成、发版协调 |

**选 HTTP + JSON 的常见理由**：
1. **对外/面向浏览器**：前端、移动端、第三方直接调用，无代理层
2. **可观测性**：日志、抓包、网关审计都是明文可读，排障快
3. **生态成熟**：鉴权、限流、WAF、CDN 全在 HTTP 链路上
4. **快速迭代**：小团队不维护多语言 proto 代码生成链路
5. QPS 不极端时，性能差距换开发效率划算

**选 gRPC 的场景**：内部微服务间 RPC、高 QPS 低延迟、强类型契约、多语言、流式传输。

**工业界常态**：**对外 HTTP+JSON（BFF/网关），对内 gRPC**，混合使用。

**记忆**：**HTTP+JSON 胜在浏览器原生、可读易调试、网关生态全；gRPC 胜在性能强类型流式；对外 HTTP 对内 gRPC 混合最常见**。

### 项目 / 消息队列

#### Q6：项目中的 Kafka 如何使用的

**答案**：（结合 IM 项目场景）

**使用场景**：IM 消息的异步化——WebSocket 网关收到消息后不直接同步落库，而是先写 Kafka，由下游服务异步消费。

**架构流程**：
```
客户端 → WebSocket 网关（鉴权、协议解析）
      → 写 Kafka（msgChatTransfer topic，key=conversationId）
      → 立即 ACK 给发送方
task 服务消费 → 消息持久化（MongoDB）+ 路由转发给目标客户端/推送
```

**为什么用 Kafka**：
1. **削峰填谷**：聊天高峰消息先入队，task 服务按自己节奏消费，避免 MongoDB 被打崩
2. **异步解耦**：网关只管接入，不阻塞发送方，降低端到端延迟
3. **持久化兜底**：Kafka 落盘，即使 MongoDB 写失败，消息不丢、可重放
4. **解耦服务**：落库、转发、已读回执、推送各自消费，互不影响

**可靠性保障**：
- **顺序性**：partition key 用 `conversationId`，同一会话消息进同一 partition 保序
- **防丢**：生产端 acks=all + 消费端手动提交 offset + 失败重试
- **防重**：消费端按消息 ID 幂等（重复消费不重复落库）
- **监控**：consumer lag 积压告警，积压时扩消费者/加分区

**记忆**：**网关写 Kafka 削峰异步，task 消费落库转发；conversationId 做 key 保序，acks+幂等+手动 commit 保可靠**。

### 数据一致性 / 可靠性

#### Q7：Outbox 表怎么设计的

**答案**：

Outbox（发件箱）模式解决 **"本地事务 + 发消息"的双写一致性"** 问题：DB 写成功但 MQ 发失败会丢事件，反之产生幽灵事件。

**核心思想**：业务数据和事件消息**在同一个本地事务里写入** outbox 表，再由独立进程把事件可靠投递到 MQ——用本地事务的原子性兜底。

**表设计**：

```sql
CREATE TABLE outbox (
    id            BIGINT PRIMARY KEY AUTO_INCREMENT,
    aggregate_type VARCHAR(64)  NOT NULL,  -- 业务实体类型，如 order
    aggregate_id  VARCHAR(64)  NOT NULL,  -- 业务 ID
    event_type    VARCHAR(64)  NOT NULL,  -- 事件类型，如 order.created
    payload       JSON         NOT NULL,  -- 事件体（完整快照）
    status        TINYINT      NOT NULL DEFAULT 0, -- 0待发送/1已发送/2失败
    retry_count   INT          NOT NULL DEFAULT 0,
    created_at    DATETIME     NOT NULL,
    sent_at       DATETIME     NULL,
    INDEX idx_status_created (status, created_at)
);
```

**工作流程**：
1. 业务操作（如下单）与插入 outbox 记录在**同一个 DB 事务**提交——要么都成功要么都回滚
2. **Relay 投递**，两种方式：
   - **轮询（Poller）**：定时扫 `status=0` 的记录批量发 MQ，成功后标记已发送（可配合 `SELECT ... FOR UPDATE SKIP LOCKED` 防多实例重复）
   - **CDC**（见 Q8）：监听 binlog 解析 outbox 表变更发 MQ，零轮询延迟
3. 消费端按业务 ID **幂等**消费（至少一次投递语义）

**要点**：
- payload 存事件完整内容，避免消费时回查业务表（状态已变）
- 失败重试 + 死信兜底；定期归档清理已发送记录
- 适用 Kafka（无原生事务消息）；RocketMQ 事务消息是另一种方案

**记忆**：**业务写入 + outbox 事件同一本地事务；relay 轮询/CD 发 MQ；至少一次投递 + 消费幂等**。

#### Q8：CDC 是什么，原理

**答案**：

CDC（Change Data Capture，数据变更捕获）：**实时捕获数据库的增删改变更**，以事件流形式分发给下游系统。

**原理**：
1. 数据库所有变更都记录在事务日志里（MySQL 的 **binlog**、PG 的 WAL）
2. CDC 工具伪装成**从库**拉取日志（或解析日志文件），把变更解析成结构化事件
3. 事件（insert/update/delete + 变更前后数据）写入 Kafka 等消息队列
4. 下游系统消费事件做同步

**常见工具**：Canal（阿里，MySQL binlog）、Debezium（基于 Kafka Connect，多数据库）、Maxwell、Flink CDC。

**典型架构**：
```
MySQL binlog → Canal/Debezium → Kafka → 消费者
                                （缓存刷新 / ES 同步 / 数仓 ETL / Outbox relay）
```

**优点**：
- **业务零侵入**：不改业务代码，不加双写逻辑
- **顺序与完整**：按事务提交顺序捕获，不丢变更
- **解耦**：源库只管写，下游按需订阅

**注意点**：
- schema 变更兼容（加列/改类型）
- 位点管理：断点续传，故障恢复
- 消费端必须**幂等**（at-least-once 语义）

**对比双写**：应用双写（DB + ES）有一致性风险且耦合业务；CDC 从日志源头捕获，天然一致。

**记忆**：**CDC = 伪装从库解析 binlog，把数据库变更实时发成 MQ 事件；业务零侵入，Canal/Debezium/Flink CDC；消费端幂等**。

---

#### Q9：怎么理解 binlog？有什么用

**答案**：

binlog 是 **MySQL Server 层**的二进制日志，追加记录所有**数据变更**操作（insert/update/delete，不含 select/show）。

**三大用途**：
1. **主从复制**：从库作为"伪从库"拉取主库 binlog 重放，保持主从数据一致
2. **数据恢复**：全量备份 + binlog 增量重放，可恢复到**任意时间点**（PITR）
3. **CDC 数据同步**：Canal/Debezium 解析 binlog 同步到 ES、缓存、数仓、Outbox

**三种格式**：

| 格式 | 记录内容 | 特点 |
|------|---------|------|
| statement | SQL 语句原文 | 省空间，但非确定性函数（now()、uuid()）主从可能不一致 |
| row | 每行变更前后的值 | 体积大，但精确，CDC 必须用 row |
| mixed | 混合，自动选 | 默认折中 |

**与 redo log 的区别**：

| | binlog | redo log |
|---|--------|----------|
| 层级 | Server 层 | InnoDB 引擎层 |
| 类型 | 逻辑日志（记录变更） | 物理日志（记录页修改） |
| 写入 | 追加写，永久保存 | 循环写，用完覆盖 |
| 用途 | 复制、恢复、CDC | 崩溃恢复（crash recovery） |

两者通过**两阶段提交**保持一致：redo prepare → 写 binlog → redo commit，保证主从一致性和崩溃恢复一致。

**记忆**：**binlog 是 Server 层逻辑日志记数据变更；三用途：主从复制、时间点恢复、CDC；与 redo log 两阶段提交保一致**。

### RAG / 向量检索

#### Q10：RAG 怎么实现的？

**答案**：

RAG（Retrieval-Augmented Generation）= 检索增强生成：把私有知识库检索出来注入 LLM 上下文，解决幻觉和知识过时。

**离线入库流程**：
1. **加载**：文档解析（Markdown/PDF/HTML）
2. **分块（Chunk）**：按字符/语义边界切分（Unicode 感知，避免中文/emoji 切坏），带重叠窗口
3. **向量化**：embedding 模型把文本转成向量
4. **索引**：写入向量索引 + 全文索引（BM25），保存元数据（租户、权限、时间）

**在线问答流程**：
1. **Query Rewrite**：LLM 改写/拆分子意图，提升召回（口语化问题 → 检索友好查询）
2. **混合检索**：稠密向量（语义相似）+ 稀疏检索（BM25 关键词）双路召回
3. **融合重排**：RRF（按排名倒数求和）融合两路结果，取 Top-K
4. **生成**：把 Top-K 文档 + 问题注入 Prompt → LLM 生成答案（带引用来源）
5. **安全护栏**：Prompt 注入检测（规则引擎拦指令注入）、幻觉检测、无召回时拒答

**工程要点**：多租户隔离（行级权限 + 独立索引）、缓存热点问答、评估体系（召回率、答案忠实度）、可观测（检索链路追踪）。

**记忆**：**RAG = 离线切块向量化入库 + 在线改写→混合检索→RRF 重排→注入生成；护栏拦注入，评估保质量**。

---

#### Q11：为什么用 ES 向量拓展

**答案**：

指不引入独立向量数据库（Milvus/Qdrant），而是用 **Elasticsearch 8.x 的 dense_vector + kNN** 做向量检索。核心理由：

1. **混合检索天然融合**：BM25 全文 + kNN 向量在同一引擎内，RRF 一次融合排序，不用跨系统合并结果集
2. **一份数据一份同步**：只维护 ES 一条同步链路，避免 DB → ES + DB → 向量库的双写一致性问题
3. **生态现成**：分片/副本/快照/滚动升级、Kibana、ingest pipeline、TLS/RBAC 安全体系全有
4. **过滤能力强**：结构化过滤（租户 ID、时间范围、权限）与向量检索在同一查询 DSL 里下推，不用后过滤
5. **运维成本**：少一套独立集群的部署、监控、备份、升级

**代价/边界**：
- 十亿级以上向量、极致召回延迟、磁盘索引分层存储等需求，专用向量库（Milvus、Qdrant）更有优势
- ES 资源占用重（JVM），纯向量场景"杀鸡用牛刀"

**结论**：中小规模、需要全文+向量混合检索、已有 ES 技术栈的场景，ES 向量拓展是最省事的选择；超大规模再拆专用向量库。

**记忆**：**ES 向量拓展 = 全文+向量一套引擎混合检索、一次同步、过滤生态全；超大规模/极致性能再上 Milvus/Qdrant**。

#### Q12：对比一下各个向量数据库的区别

**答案**：

| | Milvus | Qdrant | Weaviate | Pinecone | pgvector | Chroma | ES (dense_vector) |
|---|--------|--------|----------|----------|----------|--------|-------------------|
| 形态 | 分布式（K8s） | Rust 单机/集群 | Go 单机/集群 | 全托管云 | PG 扩展 | 嵌入式/轻服务 | 现有 ES 集群 |
| 规模 | 十亿级+，水平扩展 | 亿级（集群版） | 亿级 | 云弹性 | 百万~千万级 | 小规模 | 千万~亿级 |
| 索引 | HNSW/IVF/DiskANN | HNSW + 稀疏向量 | HNSW | 封装黑盒 | IVFFlat/HNSW | HNSW | HNSW + BM25 |
| 过滤 | 标量过滤 + 分区 | payload 过滤强 | 元数据过滤 | 元数据 | SQL 原生 | 元数据 | DSL 强过滤 |
| 混合检索 | 需外接 | 原生稀疏+稠密 | 自带 BM25 混合 | 有限 | 需 pg_trgm 等 | 无 | 原生 BM25+kNN |
| 亮点 | 大规模、生态全（Zilliz） | 高性能、易用 | 模块化、自带 RAG | 免运维 | 复用 PG 事务/SQL/备份 | 上手极快 | 全文+向量混合、运维现成 |
| 短板 | 部署运维复杂 | 超大规模要集群版 | 社区较小 | 成本高、厂商锁定 | 大规模性能弱 | 不适合生产重负载 | 向量极致性能一般 |

**选型口诀**：
- 已有 PostgreSQL、数据量不大 → **pgvector**（零新增组件）
- 需要全文 + 向量混合、已有 ES → **Elasticsearch**
- 十亿级、专用向量场景 → **Milvus** / **Qdrant**
- 不想运维 → **Pinecone**（云托管）
- 本地实验/小项目 → **Chroma** / **FAISS**（库而非库服务）

**记忆**：**pgvector 复用 PG、ES 混合检索、Milvus 大规模、Qdrant 高性能、Pinecone 免运维；按规模 + 现有技术栈选**。

### Agent / AI 工程

#### Q13：（场景题）设计一个 Agent 系统，既能完成业务沟通与交流，又能读问题日志和 debug

**答案**：

**目标**：一个双能力 Agent——对外做业务沟通（客服/咨询），对内做技术排障（读日志、定位问题）。

**总体架构**：编排层 + 双 Agent + 工具层 + 记忆层

```
用户请求 → 意图识别/路由
         ├→ 业务 Agent（沟通）      → RAG 知识库、工单工具
         └→ 排障 Agent（debug）     → 日志/指标/Trace 工具
                    ↓
              工具层（MCP 统一接入）+ 沙箱执行 + 审计
```

**业务沟通 Agent**：
- RAG 知识库：产品文档、FAQ、话术模板
- 工具：创建/查询工单、转人工、发送通知
- 边界：无法解答时升级人工，不许编造承诺

**排障 Agent**：
- 工具：日志检索（Loki/ES Query API）、指标查询（Prometheus）、链路追踪、配置/代码查询
- **ReAct 循环**：提出假设 → 调工具查证（拉日志）→ 分析 → 迭代定位 → 输出结论和修复建议
- 大日志先检索过滤再喂模型（上下文有限），不让模型直接啃原始日志

**关键设计**：
1. **工具统一协议**：全部封装为 MCP server，声明 schema/权限，可插拔
2. **安全**：沙箱执行（Q15）、工具默认只读、敏感信息脱敏、写操作人工确认、全量审计
3. **记忆**：会话内上下文 + 用户/工单历史（Q17）
4. **可观测**：工具调用链路 trace、每次决策留痕，支持回放评估
5. **质量护栏**：注入检测、幻觉检测、置信度低时拒答或转人工

**记忆**：**路由分流 + 业务/排障双 Agent + MCP 工具层（日志/指标/工单）+ 沙箱审计 + 记忆；排障走 ReAct：假设→查日志→定位**。

#### Q15：沙箱机制怎么理解？如何实现

**答案**：

沙箱（Sandbox）= **隔离执行不可信代码的受限环境**：限制资源、限制权限、限制可见范围，代码跑坏了也不影响宿主和其他任务。Agent 场景下用于执行模型生成的命令/代码（如 Codex、Claude Code 的 Bash 工具）。

**实现层次（隔离强度递增）**：

| 层次 | 技术 | 原理 |
|------|------|------|
| 语言级 | V8 isolate、JVM SecurityManager、WASM（WASI） | 运行时能力白名单，禁危险 API |
| 进程/容器级 | Linux namespace + cgroup + seccomp | namespace 隔离视图（PID/NET/MNT），cgroup 限 CPU/内存，seccomp 限系统调用 |
| 用户态内核 | gVisor | 拦截并模拟 syscall，攻击面小 |
| 轻量虚拟机 | Firecracker microVM | VM 级强隔离（AWS Lambda 底层） |

**工程要点**：
- 文件系统：只读挂载 + 可写临时盘，只暴露工作目录
- 网络：默认断网或代理白名单，防数据外带
- 资源：CPU/内存/执行时长限额，防死循环耗尽资源
- macOS Seatbelt / Linux seccomp 常用于开发工具的命令沙箱

**选型**：隔离强度 microVM > 容器 > 进程；开销反之。开发工具/单租户用容器 + seccomp 足够；多租户 SaaS 上 microVM。

**记忆**：**沙箱 = namespace + cgroup + seccomp 限权限限资源；容器轻、microVM 强、WASM 语言级；Agent 跑生成代码必须进沙箱**。

#### Q16：Harness 怎么理解？你的项目里面怎么体现的

**答案**：

Harness（直译"马具/脚手架"）= **套在 LLM 外面的运行时框架**。模型只是"大脑"，harness 提供工具调用循环、上下文装配、权限控制、记忆、沙箱、人机交互——决定模型能力的下限和上限。Claude Code、Codex CLI、OpenHands 都是 harness。

**核心组成**：
1. **Agent Loop**：模型输出 → 解析工具调用 → 执行 → 结果回填 → 再推理，循环到完成
2. **工具注册**：MCP/Function Calling 声明工具 schema
3. **上下文管理**：压缩、检索注入、token 预算（Q17）
4. **权限与沙箱**：危险操作确认、隔离执行（Q15）
5. **会话持久化**：历史、记忆、断点续跑
6. **可观测**：每次决策和工具调用留痕

**关键认知**：同一个模型放进不同 harness，表现差异巨大——工具生态、prompt 工程、上下文策略决定实际能力。

**项目中的体现**：
- **FlexiRAG**：query 改写 → 混合检索 → RRF 重排 → 生成 → 注入检测的**问答管道**，就是围绕 LLM 的 harness——模型只负责生成，检索和安全由 harness 保证
- **Agent 系统（Q13）**：工具循环 + 沙箱 + 记忆管理构成**排障 harness**；日志工具结果回填上下文再推理
- **评测**：eval harness 同理（模型 + 题目 + 工具 = 可复现评测），跑分不看裸模型看"harness + 模型"整体

**记忆**：**Harness 是模型外的运行时：工具循环、上下文、权限、记忆、沙箱；模型是脑，harness 是手脚和工作台；RAG 管道、Agent 循环都是 harness**。

#### Q17：上下文和记忆管理有什么方法？

**答案**：

**上下文管理**（单会话，窗口有限）：
1. **压缩/摘要**：历史过长时滚动摘要（如 Claude Code 的 `/compact`），只留关键结论和未完成事项
2. **检索注入**：长文档不全塞，按需检索相关片段进上下文（RAG 本质就是外部上下文管理）
3. **结构化分区**：system / 工具结果 / 记忆 / 历史用模板分区（如 XML 标签），优先级明确，淘汰时先丢低优先级
4. **Token 预算**：工具输出截断、历史条数限制、给推理预留空间
5. **Prompt Cache**：稳定内容（系统提示、工具定义）放前缀，命中缓存降本降延迟

**记忆管理**（跨会话持久）：
1. **分层**：短期（会话历史）/ 长期（用户偏好、项目事实、稳定规则）
2. **显式记忆文件**：人写稳定规则进 **CLAUDE.md / AGENTS.md**（随仓库走），自动提炼的偏好/事实进 **Auto Memory**（本地）——见 [[60-AI-Agent (前沿探索)/Claude Code/Claude Code记忆管理]]、[[60-AI-Agent (前沿探索)/Codex/Codex记忆管理]]
3. **向量记忆**：历史对话/结论向量化，后续按语义检索召回
4. **状态外置**：任务清单、知识库、数据库当"外部脑"，不全靠上下文硬记

**原则**：强制规则写进指令文件，动态事实走检索，会话细节及时压缩；记忆是辅助召回层，不替代明确指令。

**记忆**：**上下文：压缩摘要 + 检索注入 + 预算控制 + 缓存前缀；记忆：人写规则文件（CLAUDE.md）+ 自动记忆 + 向量检索；规则进文件、事实走检索**。

### 算法

#### Q19：（手撕）合并区间（LeetCode 56）

**答案**：

**思路**：按区间起点排序 + 线性扫描合并。当前区间起点 ≤ 结果中最后一个区间的终点 → 重叠，合并（终点取 max）；否则作为新区间追加。

```go
func merge(intervals [][]int) [][]int {
    sort.Slice(intervals, func(i, j int) bool {
        return intervals[i][0] < intervals[j][0]
    })
    res := [][]int{}
    for _, iv := range intervals {
        if len(res) == 0 || res[len(res)-1][1] < iv[0] {
            res = append(res, iv) // 无重叠，新开区间
        } else if iv[1] > res[len(res)-1][1] {
            res[len(res)-1][1] = iv[1] // 重叠，扩展终点（包含关系时不动）
        }
    }
    return res
}
```

**复杂度**：排序 O(n log n) + 扫描 O(n)，空间 O(1)（不计结果）。

**边界情况**：
- 空数组 / 单区间
- 包含关系 `[1,10] [2,3]`：终点取 max，不缩小
- 端点相接 `[1,2] [2,3]`：题目要求合并为 `[1,3]`（`res[1] < iv[0]` 用严格小于即合并）

**记忆**：**先按起点排序，再线性扫：起点 ≤ 前者终点就合并（终点取 max），否则新开区间**。

### Redis

#### Q1：Redis 使用单线程还是多线程？有多少个库？

**答案**：

**线程模型**：执行命令的主线程是**单线程**，用 IO 多路复用串行处理命令——无锁竞争，命令天然原子。但整个 Redis 不是单线程：

| 线程 | 职责 |
|------|------|
| 主线程（单） | 命令执行（6.0 前网络读写也是它） |
| IO 线程（6.0+，多） | 网络读写/协议解析，**命令执行仍单线程** |
| 辅助线程/子进程 | RDB 快照（fork）、AOF rewrite、异步删除（UNLINK） |

**库数量**：默认 **16 个**（0-15），`databases` 配置可改；`select N` 切换；**集群模式只有 db 0**。注意多库并不隔离故障和资源（同一实例共享内存/CPU），生产更推荐按业务拆多个实例，而不是依赖多库。

**记忆**：**执行单线程无锁保原子，6.0 后网络 IO 多线程，持久化/异步删除在别的线程；默认 16 库 select 切，集群只剩 db0；生产拆实例别靠多库**。

---

#### Q2：Redis 持久化有哪些？各自优势？谁更常用？

**答案**：

| | RDB | AOF |
|---|-----|-----|
| 原理 | 定时内存快照（二进制） | 追加写命令日志 |
| 触发 | `BGSAVE`/`SAVE`/自动策略 | everysec（默认）/always/no |
| 恢复 | 快（直接加载） | 慢（重放命令） |
| 安全 | 可能丢最后一次快照后数据 | everysec 最多丢 1 秒 |
| 文件 | 小、紧凑 | 大，需 rewrite 压缩 |

**混合持久化**（4.0+）：AOF rewrite 时前半段写 RDB 格式、后半段追加增量 AOF——恢复快且安全。

**谁更常用**：生产里**AOF everysec 或混合持久化**更常用（数据安全优先，丢 1 秒可接受）；RDB 单独用于定时备份/快速恢复演练；缓存可丢的场景才纯 RDB。

**记忆**：**RDB 快照快但可能丢，AOF 每秒刷安全但文件大，混合两者兼得；生产常用 AOF everysec/混合，RDB 做备份**。

### 消息队列 / 容器 / 微服务

#### Q4：RabbitMQ 的消息模型都有哪些？有哪些参数

**答案**：

**消息模型（工作模式）**：

| 模式 | 特点 |
|------|------|
| Simple | 点对点，一生产一消费 |
| Work queues | 竞争消费，多消费者分摊 |
| Publish/Subscribe | fanout 广播到所有队列 |

### 分布式 / 服务发现

#### Q6：几个相同的服务 A、B、C，挂了一个 A，REST API 怎么知道 A 挂了并调用 B

**答案**：

核心是 **注册发现 + 健康检查 + 客户端负载均衡** 三件套：

1. **注册**：A/B/C 启动时向注册中心（Nacos/Consul/Eureka）注册实例，调用方从注册中心拉取实例列表并**订阅变更**
2. **健康检查**：注册中心心跳/探活（或调用方探测 `/health`），A 失联后被**摘除**，变更推送给调用方
3. **客户端负载均衡**：调用方本地维护可用列表，A 被摘除后按轮询/随机/权重把请求路由到 B、C
4. **容错**：超时 + 重试（换实例重试）+ 熔断（连续失败断路，防止继续打故障节点）
5. 也可以在**网关层**集中转发和故障转移

**记忆**：**注册中心注册订阅 + 心跳摘除故障实例 + 客户端负载均衡换路由 + 超时重试熔断兜底**。

### Go 并发

#### Q7：go 中用 for 遍历多次执行 goroutine 会存在什么问题？怎么改进

**答案**：

**问题**：

1. **循环变量捕获**（Go 1.22 之前）：for 的循环变量整个循环复用一个，goroutine 闭包引用的是同一个变量，执行时全拿到**最后一个值**
2. **数据竞争**：goroutine 与主协程/彼此共享变量，`-race` 能检测出竞态
3. **无序完成**：goroutine 调度乱序，结果顺序不确定
4. **goroutine 爆炸**：循环量大时瞬间起海量 goroutine，内存/调度压力大

**改进**：

```go
var wg sync.WaitGroup
for _, v := range tasks {
    v := v // Go 1.22 前必须拷贝；1.22+ 每次迭代新变量可省略
    wg.Add(1)
    go func(t Task) {
        defer wg.Done()
        handle(t) // 或以参数传入闭包
    }(v)
}
wg.Wait() // 等全部完成，防主协程提前退出
```

- 用**参数传入**（比 `v := v` 更不易漏）
- `WaitGroup` 等待收尾；并发量大时用带缓冲 channel/信号量限并发（见上文 Q3）

**记忆**：**1.22 前循环变量复用要 v:=v 或传参；WaitGroup 等完成；信号量限并发防爆炸**。

#### Q8：如果要在每个 goroutine 中都获取返回值（捕获参数），有哪些方案？

**答案**：

| 方案 | 做法 | 特点 |
|------|------|------|
| **channel** | 结果写入带缓冲 channel，主协程 `range` 收集 | 解耦清晰，注意缓冲大小和 close 时机 |
| **共享变量 + 锁** | 结果写 slice/map，`sync.Mutex`/`atomic` 保护 | 简单，但易争用；注意下标分配 |
| **闭包/指针捕获** | 写外层声明的变量或传指针进闭包 | 轻量，但有循环变量捕获坑（见 Q7） |
| **errgroup** | `g.Go` 返回 error，`g.Wait` 收集第一个错误 | 适合"全成功或快速失败"场景 |

典型 channel 写法：

```go
ch := make(chan Result, len(tasks))
var wg sync.WaitGroup
for _, t := range tasks {
    wg.Add(1)
    go func(t Task) {
        defer wg.Done()
        ch <- handle(t)
    }(t)
}
wg.Wait()
close(ch) // 全部完成后关闭，range 才会退出
for r := range ch { collect(r) }
```

注意 Go 1.22 前后循环变量语义差异（Q7）；`close` 必须由发送方在全部完成后做，否则 panic 或死锁。

**记忆**：**channel 收集解耦、加锁写共享、errgroup 管错误；close 时机归发送方，循环变量记得拷贝**。

### 网络 / RPC

#### Q9：gRPC 用的什么协议？TCP 三次握手？四次挥手？FIN-WAIT-2 是什么时候的

**答案**：

**gRPC**：基于 **HTTP/2** 传输 + **protobuf** 序列化，`.proto` IDL 定义接口并生成多语言 stub；底层 TCP 长连接，HTTP/2 多路复用（一条连接并行多请求流）。

**三次握手**（SYN → SYN+ACK → ACK）：
- 同步双方初始序列号、确认双向收发能力
- 两次不够：服务端的"发"和"收"都要被确认，第三次 ACK 让服务端确认自己能被对方收到

**四次挥手**（FIN → ACK → FIN → ACK）：
- TCP 全双工，两个方向要**分别关闭**；服务端收到 FIN 后可能还有数据没发完，所以 ACK 和 FIN 分开发，多一次

**FIN-WAIT-2**：**主动关闭方**发出 FIN 并收到对方 ACK 后进入——此时己方"发"方向已关（不能再发数据），但仍在等对方的 FIN，对方数据还能收。对方一直不发 FIN 就一直停在此状态（需保活/超时处理）。

**状态迁移补充**：
- 被动关闭方收到 FIN 后进 **CLOSE_WAIT**（等应用 close）；大量 CLOSE_WAIT 常是代码没关连接
- 主动关闭方最后进 **TIME_WAIT**，等 2MSL 防止旧报文影响新连接

**记忆**：**gRPC = HTTP/2 + protobuf；握手 SYN/SYN+ACK/ACK 同步序号，挥手 FIN/ACK/FIN/ACK 两方向分开；FIN-WAIT-2 = 主动方已收 FIN 的 ACK、等对方 FIN**。

#### Q10：RPC 有哪几种？流式 RPC 怎么处理

**答案**：

**按调用方式分四类**：
1. **同步请求-响应**（unary）：最常用，调用阻塞等返回
2. **异步/单向调用**（fire-and-forget）：不等结果，或 Future/Promise 回调拿结果
3. **回调式**：结果由回调函数通知
4. **流式 RPC**：gRPC 分四种——unary、**server streaming**、**client streaming**、**bidirectional streaming**（基于 HTTP/2 多帧与 stream 实现）

**流式适合**：大文件传输、实时推送、长连接订阅、双向交互。

**流式处理要点**：
1. **生命周期管理**：流的创建、**半关闭（half-close）**、取消（cancel）、deadline 传播——双向流中一方提前结束要能通知对端
2. **背压（backpressure）**：HTTP/2 流控窗口天然限速，消费慢时生产方自动被压住，不能无限灌
3. **错误传播**：错误经 **status code + trailers** 传到对端；双向流一方出错，另一端要能感知并收尾
4. **资源回收**：流结束/异常都要 close，防连接泄漏

**记忆**：**unary/单向/回调/流式四类；流式盯三件事：生命周期半关闭、背压流控窗口、错误走 trailers 传播**。

### MongoDB

#### Q11：MongoDB 讲一下？与 MySQL 的区别？为什么快？

**答案**：

MongoDB 是**文档型 NoSQL**：数据以 BSON（二进制 JSON）文档存储在集合（collection）中，同一集合字段可以不同（动态 schema）；副本集做高可用，分片（sharding）做水平扩展。

**与 MySQL 对比**：

| | MongoDB | MySQL |
|---|---------|-------|
| 模型 | 文档（BSON） | 关系表 / 行 |
| Schema | 动态灵活，字段可变 | 固定 DDL，改表要迁移 |
| 扩展 | 原生分片水平扩展 | 主从 / 分库分表 |
| 事务 | 4.0+ 多文档事务（副本集） | 成熟完整 ACID |
| 查询 | 聚合管道、嵌套文档 | SQL、强 JOIN |
| 场景 | 日志/内容/画像、快速迭代 | 强一致、复杂关系、强事务 |

**为什么快**：
1. **无 JOIN**：数据按访问模式冗余嵌入，一次读取拿全
2. **弱 schema**：无 DDL 校验、无强类型约束
3. **内存优先**：WiredTiger 缓存热点数据，内存读写
4. **索引**：B 树索引、复合索引、多键/数组索引
5. **写入友好**：批量插入、可选无 journal 的激进配置

注意：快是**取舍**——复杂关联查询、强一致事务场景反而不如 MySQL。

**记忆**：**Mongo 文档 BSON、动态 schema、分片扩展；快在免 JOIN 冗余、内存缓存、弱校验；强关系强一致还是 MySQL**。

### 算法

#### Q16：go 手写二分查找

**答案**：

```go
func binarySearch(nums []int, target int) int {
    lo, hi := 0, len(nums)-1
    for lo <= hi {
        mid := lo + (hi-lo)/2 // 防溢出，等价 (lo+hi)/2
        if nums[mid] == target {
            return mid
        } else if nums[mid] < target {
            lo = mid + 1
        } else {
            hi = mid - 1
        }
    }
    return -1
}
```

**要点**：
- 前提：数组**有序**
- 边界：`lo <= hi`（闭区间），`mid = lo+(hi-lo)/2` 防溢出
- 复杂度：O(log n)，空间 O(1)

**常见变体**（被追问时写）：
- 查**第一个**等于 target 的位置：命中后不返回，`hi = mid - 1` 收缩右边界，最后检查 `nums[lo]`
- 查**插入位置**（LeetCode 35）：找不到时返回 `lo` 即应插入下标

**记忆**：**lo<=hi 闭区间，mid 防溢出，小了 lo=mid+1、大了 hi=mid-1；求边界变体命中后继续收缩**。
